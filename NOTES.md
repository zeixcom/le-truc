## LT-037 — server-data `@for` (Pass 1) silently dropped reactive attrs/events on any element other than the loop's single output root — fixed
**Date:** 2026-08-25 | **Skill:** le-truc-dev
**Issue (found):** Migrating `form-radiogroup.ts` to `.tsrx` (options → `@for` over a plain array prop, each item a `<label>` wrapping a native `<input type="radio">` + `<span>` text) compiled with **zero diagnostics** but silently dropped every reactive attribute and event handler on the nested `<input>` (`checked={() => …}`, `tabindex={() => …}`, `onChange={() => (...)}`) — the generated client's `each()` callback only emitted a `watch()` for the `class` binding on the loop's output root (`<label>`), nothing for its children. `analysis/loops.ts`'s effect-gathering only read `loop.output.attrs` (the single JSXElement `lowerFor` takes as `outputNode`) — nothing walked the output's *children* for reactive attrs/events, and no diagnostic fired for the orphaned constructs. Every existing `@for` precedent (`module-tabgroup.tsrx`) sidestepped this because its loop's one interactive unit (`<button>`) IS the output root.
**Fix applied:** `analysis/loops.ts`'s Pass 1 now recursively walks `output`'s descendant elements (`collectDescendants`) for `reactive`/`class-map`/`event` attrs; each such descendant gets a selector resolved *within the loop item's own subtree* (`resolveSelectorIn(output, descendant)` — scoped uniqueness counting, not global), with an `unaddressableElement` diagnostic if no unique selector exists. `LoopEffectPlan`'s three variants (`analysis/plan.ts`) gained a `target: string | null` field (`null` = output root itself, matching prior behavior exactly). `emit-client.ts`'s `emitEachBlock` now queries each distinct non-null target once per item (`const <name> = ${itemParam}.querySelector('<selector>')!`, deduped and name-collision-safe via `sanitizeVarName` + numeric suffix) and directs `watch`/`on` at that cached local instead of always at `itemParam`. Verified via `bun test server/tests/tsrx` (224 pass / 4 fail both before and after — the 4 are a pre-existing unrelated golden-snapshot staleness on `form-checkbox.tsrx`, confirmed via `git stash`) and `bun run check:tsrx` (whole corpus + `form-radiogroup.tsrx` compiles with zero diagnostics, nested `checked`/`tabindex`/`onChange` on `<input>` now correctly emitted and sharing one `querySelector` call).
**Adjacent, deliberately NOT fixed:** the `watch-attr` dispatch choice (`bindAttribute` vs `bindProperty`) is unchanged — it still only picks `bindProperty` for a bare host-prop mirror thunk (`() => host.x`), same as the pre-existing root-level logic (`hostPropOf` in `analysis/effects.ts`). A comparison thunk like `checked={() => host.value === optValue}` still lowers to `bindAttribute`, which is subject to the native `checked` "dirty checkedness" attribute/property divergence in some browsers after user interaction — a real but pre-existing, non-loop-specific nuance (root-level `checked={() => …}` thunks would hit the same thing), out of scope for this fix.

## LT-038 — selector resolution only tried one discriminator attribute (`type` before `class`), so sibling buttons sharing `type="button"` were unaddressable — fixed
**Date:** 2026-08-25 | **Skill:** le-truc-dev
**Issue (found):** Migrating `form-spinbutton.tsrx` (decrement/increment `<button type="button" class="decrement">` / `<button type="button" class="increment">` siblings), both buttons hit TSRX007 "No unique selector for <button>" even though `class` clearly disambiguates them. `analysis/selectors.ts`'s `buildSelector(el, 'discriminator')` picked the FIRST present name from `['type', 'class']` — since both buttons have `type="button"`, it built `button[type="button"]` for both (non-unique) and never tried `class` at all; `resolveSelectorIn`'s "first unique candidate wins" loop only ever saw that one discriminator candidate.
**Fix applied:** added `discriminatorCandidates()` (`analysis/selectors.ts`) returning ALL present discriminators (`type`, `class`, every `data-*`) as separate selector strings instead of `buildSelector`'s single pick; `resolveSelectorIn` now spreads all of them into its candidate list, so uniqueness is checked per-candidate until one hits, falling through past `type` to `class` when needed. `buildSelector('discriminator', …)` itself is untouched (still used elsewhere for its single-pick semantics where that's correct). Verified via `bun test server/tests/tsrx` (224 pass / 4 fail, same pre-existing baseline as LT-037) and `bun run check:tsrx` (whole corpus + `form-spinbutton.tsrx` compiles with zero diagnostics).

## LT-036 — map/computed-thunk-rendered signals over plain consts still fall to TSRX004 (initializer not client-portable)
**Date:** 2026-08-24 | **Skill:** le-truc-dev
**Issue:** LT-036 now credits signals read through `style-map`/`class-map` objects and computed (non-direct) reactive thunks as rendered, seeding them by verbatim initializer reuse (`analyze.ts` `thunkRendered` set → `substituteArgExpr`'s `allowVerbatim`). But that reuse passes through `substituteArgExpr`'s free-name gate, which only accepts JS globals, server args, sibling signals, context names, and refs. A signal like `const DEFAULT = 'red'; const color = createCell(DEFAULT)` used only through a style-map thunk still fires TSRX004 — with a misleading "never rendered" message, since it IS rendered, just not seedable client-side. Allowing plain-setup/import names in the gate is NOT a one-line fix: the emitted client initializer would reference a name that `computeClientNeededNames` (`plain-imports.ts`) may have excluded from the client module, because that fixpoint walks IR attribute thunks, not generated harvest expressions — harvesting plans would have to be fed into it first (they exist by emit time, but the plumbing isn't there). Workaround is trivial (inline the constant, or add a direct render site).
**Options:** (a) leave the gate strict; improve the diagnostic message for the credited-but-not-portable case (distinguish "never rendered" from "rendered but initializer not client-portable") so the message stops misleading. (b) thread harvest expressions into `computeClientNeededNames` as client-needed seed positions, then widen the gate to plain-setup and import-local names — makes real initializer shapes work but touches the import-placement fixpoint.
**Question:** Is (b) worth the plumbing, or is (a)'s honest diagnostic plus the inline-the-constant workaround enough given `deriveCell` callbacks have the same restriction today?
**Decision (2026-08-26, architect):** Deferred until the compiler conformance refactoring (LT-051…LT-060, LT-069) is complete, then revisit under LT-071. Option (a)'s "stays hand-written permanently" is ruled out as a matter of policy: no example component stays hand-written — the compiler is to fit every example, expressed in an easy-to-understand way. Re-evaluate this entry once `&{}`, the lift rule, `first()` and the widened setup gate have landed; several of these walls may move or disappear.

## LT-035 — card-mediaqueries.tsrx reshaped from light-DOM enhancer to template owner; demo/e2e spec now stale
**Date:** 2026-08-25 | **Skill:** le-truc-dev
**Issue:** `card-mediaqueries.ts` (hand-written) is a light-DOM ENHANCER: it queries pre-existing `.motion`/`.theme`/`.viewport`/`.orientation` elements the PAGE AUTHOR supplies inside `<card-mediaqueries>` (its own `<h5>`/`<dl>` markup — see `card-mediaqueries.html`), guarding each independently since any subset may be present. Migrating it to `.tsrx` (the LT-035 acceptance case) required making the component OWN its template instead — same category of mismatch as `card-blogmeta` (below), but here there WAS a workable prop to convert to: a `label` prop replaces the page author's own `<h5>` heading, and all four `<dd>` slots are now unconditionally rendered. This is a real behavior change (not just a source-of-truth swap like `card-collapsible`'s `open`), and it makes two existing artifacts stale: (1) `card-mediaqueries.html`'s demo markup, which writes its own `<h5>`/`<dl>` structure per instance (now redundant/conflicting with the component's own template) and uses two side-by-side instances captioned "Without Context"/"With Context" (now expressible via the `label` prop instead); (2) `card-mediaqueries.spec.ts`'s e2e test `'multiple components receive same context values'`, which dynamically appends a NEW `card-mediaqueries` element with hand-authored `innerHTML` at runtime — that test's premise (arbitrary light-DOM enhancement) no longer holds against a template-owning component.
**Options:** (a) update `card-mediaqueries.html` to drop its own `<h5>`/`<dl>` and pass `label="Without Context"`/`label="With Context"` instead, and rewrite the "multiple components" e2e test to append a plain `<card-mediaqueries label="…">` (no manual `innerHTML`) — accepts the reshaping as the new permanent behavior. (b) treat this the same as `card-blogmeta` — leave `card-mediaqueries.ts` hand-written too, since both are light-DOM enhancers by the same underlying constraint, and don't migrate it at all (the LT-035 compiler feature itself doesn't need this specific component as proof — the new `server/tests/tsrx/context.test.ts` fixtures already exercise both `requestContext`/`provideContexts` directions in isolation).
**Question:** Should the demo `.html`/e2e spec be updated to match the reshaped `.tsrx` version (option a), or should `card-mediaqueries.ts` stay hand-written like `card-blogmeta` and the `.tsrx` file be reverted/removed (option b)?
**Decision (2026-08-26, architect):** Deferred until the compiler conformance refactoring (LT-051…LT-060, LT-069) is complete, then revisit under LT-071. Option (a)'s "stays hand-written permanently" is ruled out as a matter of policy: no example component stays hand-written — the compiler is to fit every example, expressed in an easy-to-understand way. ## LT-033 — card-blogmeta: component shape doesn't fit `.tsrx`'s template-ownership model
**Date:** 2026-08-24 | **Skill:** le-truc-dev
**Issue:** `card-blogmeta.ts` doesn't render a template at all — it takes whatever light DOM the page author writes inside `<card-blogmeta>` (an `.author` span with an optional `<img>`, a `time.published`, an optional `.modified time`) and, once at connect time, reformats/rewrites specific descendants in place (locale-formats `datetime` attributes into text, conditionally removes a `.modified` span if the modified date is invalid, inserts a fallback avatar SVG if `.author` has no `<img>`). There are no reactive props and no signals — the component's exposed-props type is `{}`. Every `.tsrx` component compiles its own JSX into the canonical template (server-rendered once, client-addressed by compile-time selectors); there's no mechanism for "arbitrary, structurally-varying author-supplied children, addressed and mutated once at connect." This is a step beyond the already-precedented "can't express missing-element fallback" deviation (`basic-button.tsrx`'s doc comment) — that case converts optional DOM-harvested props into typed attribute-driven props; blogmeta has no prop to convert to, since its job *is* the light-DOM rewrite. Left unmigrated.
**Options:** (a) out of scope for TSRX by design — components in this shape (light-DOM enhancers with no owned template) stay hand-written permanently, document as an explicit boundary in ARCHITECTURE.md/ADR 0024. (b) some future `{children}`-adjacent mechanism for addressing/transforming individual named descendants of composed-in content — large, speculative, no concrete second use case yet.
**Question:** Should ADR 0024 gain an explicit "out of scope" note for light-DOM-enhancer components, so future migration passes don't re-discover this same wall?
**Decision (2026-08-26, architect):** Deferred until the compiler conformance refactoring (LT-051…LT-060, LT-069) is complete, then revisit under LT-071. Option (a)'s "stays hand-written permanently" is ruled out as a matter of policy: no example component stays hand-written — the compiler is to fit every example, expressed in an easy-to-understand way.
