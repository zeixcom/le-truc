## LT-092 — form-radiogroup cutover STOPPED: boolean `checked` comparison thunks in loop bodies lower to `bindAttribute`, and the dirty-checkedness divergence breaks mutual exclusion (compiler gap)
**Date:** 2026-08-29 | **Skill:** le-truc-dev
**Issue (found):** The compiled `form-radiogroup.client.ts` mirrors selection with `watch(() => host.value === optValue, bindAttribute(input, 'checked'))`. `checked` is a dirty-flag IDL attribute: once the user clicks a radio (or any JS write sets the property), later attribute removal does NOT clear the live property — and the loop's radios carry no `name`, so there is no native radio group to enforce exclusion either. Verified in a real browser: click Female then Male → Female stays checked (spec 'selects radio button when clicked' fails), and a controlled `el.value = '…'` write after interaction doesn't move the live checks either ('value property is mutable' fails). The hand-written twin wrote `radio.checked = isChecked` — a property write — inside its `each()` callback. This is exactly the nuance the LT-037 NOTES entry deferred ("a real but pre-existing nuance... out of scope of this fix"): the watch-attr dispatch only picks `bindProperty` for a bare `() => host.<prop>` mirror thunk, and a loop-body comparison thunk (`host.value === optValue`) can never be one.
**Consequence:** twin restored (`examples/form/radiogroup/form-radiogroup.ts`, import normalized to `@zeix/le-truc`), demo/spec reverted to hand-written contract, main.ts mounts the twin, CEM exclusion re-added. The restored twin keeps its own `each()` with property writes, so it is unaffected.
**Fix direction:** teach the reactive-attr dispatch (or a loop-body special case in `analysis/loops.ts`/`emit-client.ts`) to lower boolean thunks targeting `checked`/`selected`/`value` on native form controls to `bindProperty`-style property writes, or emit `el.checked = thunk()` callbacks for those three dirty-flag attributes inside `each()` bodies. Note `form-checkbox.tsrx`'s root-level `checked` uses the managed form machinery instead and is unaffected; the gap is specific to loop-body/native-control boolean mirrors.

## LT-037 — server-data `@for` (Pass 1) silently dropped reactive attrs/events on any element other than the loop's single output root — fixed
**Date:** 2026-08-25 | **Skill:** le-truc-dev
**Issue (found):** Migrating `form-radiogroup.ts` to `.tsrx` (options → `@for` over a plain array prop, each item a `<label>` wrapping a native `<input type="radio">` + `<span>` text) compiled with **zero diagnostics** but silently dropped every reactive attribute and event handler on the nested `<input>` (`checked={() => …}`, `tabindex={() => …}`, `onChange={() => (...)}`) — the generated client's `each()` callback only emitted a `watch()` for the `class` binding on the loop's output root (`<label>`), nothing for its children. `analysis/loops.ts`'s effect-gathering only read `loop.output.attrs` (the single JSXElement `lowerFor` takes as `outputNode`) — nothing walked the output's *children* for reactive attrs/events, and no diagnostic fired for the orphaned constructs. Every existing `@for` precedent (`module-tabgroup.tsrx`) sidestepped this because its loop's one interactive unit (`<button>`) IS the output root.
**Fix applied:** `analysis/loops.ts`'s Pass 1 now recursively walks `output`'s descendant elements (`collectDescendants`) for `reactive`/`class-map`/`event` attrs; each such descendant gets a selector resolved *within the loop item's own subtree* (`resolveSelectorIn(output, descendant)` — scoped uniqueness counting, not global), with an `unaddressableElement` diagnostic if no unique selector exists. `LoopEffectPlan`'s three variants (`analysis/plan.ts`) gained a `target: string | null` field (`null` = output root itself, matching prior behavior exactly). `emit-client.ts`'s `emitEachBlock` now queries each distinct non-null target once per item (`const <name> = ${itemParam}.querySelector('<selector>')!`, deduped and name-collision-safe via `sanitizeVarName` + numeric suffix) and directs `watch`/`on` at that cached local instead of always at `itemParam`. Verified via `bun test server/tests/tsrx` (224 pass / 4 fail both before and after — the 4 are a pre-existing unrelated golden-snapshot staleness on `form-checkbox.tsrx`, confirmed via `git stash`) and `bun run check:tsrx` (whole corpus + `form-radiogroup.tsrx` compiles with zero diagnostics, nested `checked`/`tabindex`/`onChange` on `<input>` now correctly emitted and sharing one `querySelector` call).
**Adjacent, deliberately NOT fixed:** the `watch-attr` dispatch choice (`bindAttribute` vs `bindProperty`) is unchanged — it still only picks `bindProperty` for a bare host-prop mirror thunk (`() => host.x`), same as the pre-existing root-level logic (`hostPropOf` in `analysis/effects.ts`). A comparison thunk like `checked={() => host.value === optValue}` still lowers to `bindAttribute`, which is subject to the native `checked` "dirty checkedness" attribute/property divergence in some browsers after user interaction — a real but pre-existing, non-loop-specific nuance (root-level `checked={() => …}` thunks would hit the same thing), out of scope for this fix.

## LT-038 — selector resolution only tried one discriminator attribute (`type` before `class`), so sibling buttons sharing `type="button"` were unaddressable — fixed
**Date:** 2026-08-25 | **Skill:** le-truc-dev
**Issue (found):** Migrating `form-spinbutton.tsrx` (decrement/increment `<button type="button" class="decrement">` / `<button type="button" class="increment">` siblings), both buttons hit TSRX007 "No unique selector for <button>" even though `class` clearly disambiguates them. `analysis/selectors.ts`'s `buildSelector(el, 'discriminator')` picked the FIRST present name from `['type', 'class']` — since both buttons have `type="button"`, it built `button[type="button"]` for both (non-unique) and never tried `class` at all; `resolveSelectorIn`'s "first unique candidate wins" loop only ever saw that one discriminator candidate.
**Fix applied:** added `discriminatorCandidates()` (`analysis/selectors.ts`) returning ALL present discriminators (`type`, `class`, every `data-*`) as separate selector strings instead of `buildSelector`'s single pick; `resolveSelectorIn` now spreads all of them into its candidate list, so uniqueness is checked per-candidate until one hits, falling through past `type` to `class` when needed. `buildSelector('discriminator', …)` itself is untouched (still used elsewhere for its single-pick semantics where that's correct). Verified via `bun test server/tests/tsrx` (224 pass / 4 fail, same pre-existing baseline as LT-037) and `bun run check:tsrx` (whole corpus + `form-spinbutton.tsrx` compiles with zero diagnostics).
