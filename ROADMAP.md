# Le Truc — Roadmap

> This document describes _where the project is heading_ across releases: what's landed, what's next, and what we've deliberately decided not to pursue. For the problem, users, and constraints behind these decisions, see [REQUIREMENTS.md](REQUIREMENTS.md). For architectural rationale, see [ARCHITECTURE.md](ARCHITECTURE.md) and the [ADRs](adr/).

---

## Where we're heading: server components (v3.0)

Le Truc's contract today is **the server renders HTML; components upgrade in place** (ADR [0003](adr/0003-attributes-drive-state-at-connect-time-only.md)). There is no client-side templating and no VDOM — not even for lists, which are DOM-driven (`each()`) rather than data-driven.

The long-term goal is a **TSRX-based isomorphic authoring format** for server components, so a component is written once instead of as three hand-maintained files (`.html` + `.css` + `.ts`) that drift against each other. The server half renders HTML (and extracts scoped CSS); the client half is a **generated** `defineComponent()` module. This is a **split compiler**, not a rendering framework: the server produces the truth, the client never re-renders, and Le Truc's "enhance, don't render" posture is preserved end to end.

The Phase 0 spikes verified this is doable with less friction than expected, so the **TSRX dual compiler is a v3.0 deliverable in full** — v3.0 ships once TSRX reaches 1.0. Until then, the compiler lives **inlined in this repo** and migrates our docs and examples to TSRX; no separate package ships before TSRX is stable. That keeps us free to explore the rough edges, absorb upstream format changes, and fine-tune our compilation strategy.

### Landed toward this goal: `reconcile()` (v2.3)

Server components need a client-side answer to `.map()` in JSX / `for ... of` in TSRX — a way to keep a reactive list of data in sync with rendered DOM elements without re-rendering. That's `reconcile()` (ADR [0017](adr/0017-keyed-template-clone-reconciliation-for-lists.md)): a keyed template-clone reconciler that adopts server-rendered, keyed children as the source of truth on first run, then syncs additions, removals, and reorders from a `List`/`Collection` against the DOM by key — no client-side template language, one root `<template>` supplied by the author.

It replaces the hand-written, brittle reconciliation code that `module-list` and `module-todo` had to duplicate, and is Le Truc's first (deliberately bounded) primitive that creates DOM from data rather than only enhancing what the server already rendered.

### Next: TSRX as a server-side component format

The full design history lives in git history (`PLAN-tsrx-server-components.md`, superseded by this roadmap, and the now-removed `spike/tsrx-phase0/` feasibility spike) and is recorded as **[ADR 0024](adr/0024-adopt-tsrx-as-isomorphic-component-format.md)** — **Accepted (2026-08-22)**: all four milestones of the inlined compiler are verified and reviewed (emitter core + client codegen; extension activation and CEM generation, the two format gates; reactive `@for` over a `List` via `reconcile()`; type flow with the projection approach reconsidered — child-module imports, the `globals.d.ts` ambient contract, emit-then-check in CI, span-table mappings as the LT-011 follow-up). In short:

- **What TSRX is.** A JSX-shaped template language (`.tsrx`, from the Ripple ecosystem) with real control flow (`@if`, `@for`, `@switch`), scoped `<style>` blocks, and a shared parser (`@tsrx/core`) with per-framework codegen targets (React, Preact, Solid, Vue, Ripple). There is no server/HTML target today — Le Truc would be the first.
- **The semantic gap.** Every existing TSRX target assumes the component renders and re-renders its own DOM. Le Truc's components never do. The isomorphic format classifies every expression as server-definitive (renders once, ships zero client JS) or reactive (needs a binding) **by author declaration** — function-valued bindings and `&{ }` lazy children are reactive, everything else is server-definitive — no compiler inference.
- **The recommended starting point (Option C)** is an authored split, not compiler inference: a single `.tsrx` file contains a plain-TypeScript client export (unchanged `defineComponent()` code) alongside a server template compiled to an HTML-string render function, with the `<style>` block extracted and tag-scoped. No binding classification yet — that's a later phase, once the format itself is proven. _Update 2026-08-22: Option C served as the feasibility proof; the **isomorphic client+server format** (client component generated from the same source) is the planned target — see ADR [0024](adr/0024-adopt-tsrx-as-isomorphic-component-format.md)._
- **Sequencing.** `reconcile()` had to land first (done, v2.3) because reactive `@for` lowers directly onto it. After that: a no-compiler-code spike hand-writing the target design against two real components ✅ (done 2026-08-21 — GO on `@tsrx/core` 0.1.60 pinned), plus a second spike validating the isomorphic format ✅ (done 2026-08-22 — all positions grammar-native, lowering rules specified, convergence with hand-written code shown, pre-ADR decisions recorded). The **inlined isomorphic compiler** then landed its first two milestones ✅ (done 2026-08-21, `server/tsrx/` + `server/effects/tsrx.ts` — server render functions, verbatim tag-scoped CSS, and generated `defineComponent()` clients for the sanctioned subset, golden-tested in `server/tests/tsrx/` including emit-then-check). The two format verifications gating acceptance landed next ✅ (2026-08-22, LT-005/LT-006: extension activation via `export const config`, CEM generation with the plugin unchanged), followed by milestones 3–4 ✅ (2026-08-22, LT-003/LT-004 + the tsrx.dev feature sweep LT-013 — reactive lists via `reconcile()`, `@if`/`@switch`/`@try` directives, `html={dataRef}` dynamic rendering, all architect-reviewed with an independent reviewer pass). **ADR 0024 accepted 2026-08-22.** Next: post-acceptance refinement (LT-011 diagnostics mapping, LT-012 async rendering residue), then migrating docs and examples to `.tsrx`.
- **Packaging.** `@zeix/le-truc` stays the backend-agnostic client layer it already is. The compiler ships as **`@tsrx/le-truc`** with v3.0, once TSRX reaches 1.0; until then it is inlined in this repo (`server/tsrx/`), with our own docs as the migration vehicle. No separate package ships before TSRX is stable.
- **What we're not chasing.** Compiler-inferred reactivity (taint-walk classification from declared roots) — author-declared markers make inference unnecessary. TSRX as server-templating-only with hand-authored components staying as three files (Option B) — doesn't deliver the actual goal, since components would still drift.

## Server-side rendering strategies (general guidance)

Independent of the TSRX direction, this is how to structure a server layer around Le Truc components today — and remains valid regardless of how the authoring format evolves. Le Truc has no SSR of its own: the server produces HTML, and Le Truc components take over from `connectedCallback` onward, reading initial state from attributes, JSON attributes, slots, or Declarative Shadow DOM.

- **Static Site Generation** — pre-render at build time, serve plain files. What the docs site (`server/`) does today. Best for content that changes on a known schedule.
- **Server-Side Rendering** — render per request when content depends on the requester (auth, query params, personalization). Any HTTP server works; streaming lets above-the-fold components upgrade before slow data resolves.
- **Fragment-based navigation** — a router component intercepts link clicks, fetches only the changed region as an HTML fragment, and swaps it in; persistent components (nav, header) keep their signals alive across navigations. Degrades to full page loads without JS.
- **Optimistic mutations** — update signals immediately on user action, fire a background fetch, let the authoritative server response confirm or correct via `Store.update()` (which diffs and only propagates real changes).
- **Templating choice is independent of Le Truc.** Tagged template literals (what `server/templates/` uses today), JSX-without-React (`@kitajs/html`-style), traditional template engines, or Astro all produce valid input HTML — the reactive layer doesn't care how the HTML was made, only that it's correct.

## Dead ends: deprecated in 2.x, removed in 3.0

Two 2.x escape hatches are being retired because they undermine guarantees the rest of the library depends on. Both already emit `DEV_MODE` deprecation warnings in 2.3.

- **`pass()` writable-signal short forms.** `pass(child, { value: 'value' })` (property-key form) and `pass(child, { value: someState })` (bare-writable-signal form) hand a child component unrestricted `.set()` access to parent-owned state, with no chokepoint for the parent to validate or veto writes (ADR [0012](adr/0012-deprecate-unrestricted-write-short-forms-in-pass.md)). **Migration:** `() => host.value` for read-only access, or `{ get: parentSignal.get, set: parentSignal.set }` to keep writes mediated.
- **Returning an array of `EffectDescriptor`s from a factory.** The explicit-return contract (ADR 0007) is a silent footgun: dropping a descriptor from the returned array — a bare `watch(task, fn)` statement, a missed spread after a refactor — produces no error and no warning; the effect simply never runs. `watch()`, `on()`, `pass()`, `each()`, and `provideContexts()` now register themselves when called (ADR [0018](adr/0018-implicit-effect-collection-via-ambient-context.md)); explicit `return [...]` still works in 2.3 for compatibility but is removed in 3.0. For the one case explicit return was still needed — a hand-authored `EffectDescriptor` wrapping a non-Le-Truc primitive — `watch(() => true, descriptor)` registers it the same way the others do, since a dependency-free thunk runs once and `watch()`'s internal `createEffect()` call self-registers the cleanup. After 3.0, `FactoryResult`/`EffectDescriptor` are no longer part of the public return contract at all.

**Migration path:** both changes are non-breaking in 2.3 (dual support) and breaking in 3.0. Projects should adopt implicit collection and mediated `pass()` bindings now to avoid a cliff at the next major version.

## Cause & Effect 2.0 alignment (3.0)

Le Truc 3.0 follows Cause & Effect 2.0: the deprecated 2.5 re-exports are removed and the type surface collapses to the v2 shapes. This track is blocked on the CE 2.0 release — verify against it when it finalizes, and record an ADR at that point. CE's [ADR-0018](https://github.com/zeixcom/cause-effect/blob/main/adr/0018-shape-indexed-signal-types.md) is Accepted (2026-08-17) with a working prototype on `v2/shape-exploration` (package version `2.0.0-next.1`, unreleased), so planning can rely on these **verified** v2 facts:

- **`isSignal`/`isMutableSignal` stay the umbrella match — this reverses what earlier drafts of this section assumed.** ADR-0018's original wording narrowed `isSignal` to single-value only; a same-day revision reversed that after the narrow naming proved confusable with the umbrella concept in practice (see [CE's `MIGRATION-2.0.md`](https://github.com/zeixcom/cause-effect/blob/main/MIGRATION-2.0.md), "Second flip"). In v2, `isSignal`/`isMutableSignal` match any signal shape (`Cell`, `List`, `Store`, structurally `Slot`) by `.get()`/`.set()` presence — exactly their 1.x behavior. The narrow single-value guards are `isCell`/`isMutableCell` instead, already backported to 1.5.2. **Consequence: none of our `isSignal` call sites need to change for v2** — `src/helpers/events.ts:212`, `src/helpers/reactive.ts:532`, `src/component.ts:454`, and `src/extensions/form.ts:160,170,409` all use `isSignal` as umbrella dispatch and stay correct as-is.
- **`Signal<T>` stays the umbrella type — no union redesign needed.** The redesign this section previously flagged as "the single biggest 3.0 design item" — reworking `Reactive<T,P>`/`MaybeSignal<T>` and `toSignal`'s return type into a `Signal<T> | List<T> | Store<T> | Slot<T>` union — is no longer required. `Signal<T>` keeps its 1.x meaning end to end.
- **`List`/`Store` still flip meaning at v2 — this part of the original decision stands.** `List`/`isList` and `Store`/`isStore` become the readonly base (what `DerivedList`/`isDerivedList` and `DerivedStore` meant in 1.5.x); the 1.x mutable meaning moves to `MutableList`/`isMutableList`/`MutableStore`/`isMutableStore`, unchanged bridge names we already re-export. `DerivedList`/`isDerivedList`/`DerivedStore` are removed, folded into the recycled `List`/`Store`/`isList`. Our own `src/` has no internal use of the bare `List`/`Store` type names today — the exposure is entirely in `index.ts`'s re-export of the deprecated aliases, which needs updating at the 3.0 boundary.
- **`createTask`/`createSensor` are no longer exported from the CE package root.** Both stay reachable through `deriveCell`'s dispatch — `deriveCell(asyncFn, { initial? })` for what `createTask` did, `deriveCell(seed, { watched })` for what `createSensor` did. `index.ts` currently re-exports both names directly from `@zeix/cause-effect`; that re-export breaks at 2.0 and needs either to drop the names (breaking, matching upstream) or wrap `deriveCell` locally to preserve them for one more Le Truc major.
- **`createMemo` is renamed to `deriveComputed`.** Same signature and behavior. `index.ts` re-exports `createMemo` directly; needs `deriveComputed` added (and `createMemo` dropped or kept as a local deprecated alias).
- **`SignalOptions`/`DeriveSignalOptions`/`SignalCallback` are renamed to `CellOptions`/`DeriveCellOptions`/`CellCallback`, absorbing `ComputedOptions`/`SensorOptions`/`SensorCallback`.** Type-only renames, no runtime impact. `index.ts` re-exports the old names (`SignalOptions`, `ComputedOptions`, `SensorOptions`, `DeriveSignalOptions`) — these need remapping.
- **`State`/`isState`, `Memo`/`isMemo`, `Task`/`isTask`, `Sensor`/`isSensor`, `Collection`/`isCollection`, `isComputed` are removed outright**, with no mechanical replacement — origin is no longer part of the public type/guard surface once types are indexed by shape and mutability alone. `index.ts` currently re-exports all of these; each needs a call-site audit (`isState(x) || isMemo(x)` does not mechanically become `isSignal(x)` once the value can be a composite), not a blanket rename.
- **`createSignal`'s 1.x shape-sniffing coercion (array → `List`, record → `Store`, function → `Memo`/`Task`, signal → itself) is removed with no replacement export.** `createCell(value)` is single-value only and never coerces. If Le Truc still needs a coercing constructor at its own boundary (e.g. `expose()`'s "anything else" initializer branch — see `ARCHITECTURE.md` § Signals and Properties), CE's `MIGRATION-2.0.md` documents a three-line `coerceSignal` helper as the replacement pattern. This is CE's own recipe, not something our ADR 0018 ([implicit effect collection](adr/0018-implicit-effect-collection-via-ambient-context.md)) assigns us — that citation in earlier drafts of this section conflated our ADR 0018 with CE's differently-numbered one.
- **CE core budget: under 3 kB gzipped for the synchronous core (`createState`, `deriveComputed`, `createEffect`); full library 8036 B (~7.9 kB) gzipped** (per CE's current `README.md`, superseding this section's earlier "state/memo/sensor trio" figure, which named types v2 no longer has). Our own ≤9 kB consumer budget is unaffected.
- Remaining workstreams: `index.ts` re-export surface rewrite per the points above (mostly additive/renaming — internal `src/` usage already avoids the removed origin types), `types/` regeneration, coordinated release once CE 2.0 actually ships (still `2.0.0-next.1`, unreleased).
