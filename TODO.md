- [ ] LT-005: Unified format for form components — extensions, attribute-driven props, `internals` (ADR 0023 acceptance gate)
  **Skill:** le-truc-dev
  **Context:** The sanctioned subset cannot activate `defineComponent`'s third argument — `formAssociated()` / `formAssociatedCheckbox()` (which must lead the array and widen the factory context to `FormFactoryContext`, ADR 0019) and `observedAttributes([...])` — nor use `internals`/`relayValidity`, Parser-backed attribute-driven `expose()` props, or `defineMethod()` members. Form components (`form-textbox`) cannot be authored in `.tsrx` today. Spike first, record the format decision as ADR 0023 sub-design 8, then implement in `server/tsrx/`.
  **Leading design (to validate in the spike):** a zero-import, statically-analyzable `export const config = { formAssociated: true, observedAttributes: [...] }` in the `.tsrx` source; the compiler validates keys against the known extensions, auto-imports the extension factories from `@zeix/le-truc` into the generated client (preserving the formAssociated-first rule), and recognizes `internals` as an ambient when `formAssociated` is on. Attribute-driven props and `defineMethod` need an `expose()` authoring form whose initializer the compiler can lower to Parser calls (e.g. `expose({ value: asString() })`-equivalent with `as*` recognized as ambients). Alternatives considered: an attribute on the root element (rejected — class configuration is not markup), decorator syntax (rejected — requires imports, breaking the zero-import rule). Corpus: author a `form-textbox`-shaped fixture; golden + emit-then-check tests must show the widened `FormFactoryContext` typing in the generated client.

- [ ] LT-006: Custom Element Manifest generation for `.tsrx` components (ADR 0023 acceptance gate)
  **Skill:** le-truc-dev
  **Context:** `custom-elements.json` is generated by `cem analyze` with `@zeix/cem-plugin-le-truc` over `examples/**/*.ts` (the hand-written trio). The plugin extracts the tag from `defineComponent(...)`, the component description and `@slot`/`@fires`/`@csspart`/`@cssprop`/`@demo`/`@attribute` tags from the JSDoc above `export default`, members from the `Props` type via the TypeScript checker, attributes from Parser-call `expose()` initializers, and extension-derived members from the third argument. Generated clients break three of those inputs today: the component JSDoc is dropped (the compiler slices the function declaration without its leading doc comment), Parser-expose does not exist yet (LT-005), and no extensions array is emitted (LT-005).

Make the compiler carry the source's component JSDoc (with all tags) above the generated `export default defineComponent(`, then point `custom-elements-manifest.config.mjs` globs at the generated clients (build order: tsrx effect before `cem analyze`; note generated output is gitignored and `@zeix/le-truc` self-imports resolve via the tracked `types/` artifact — verify). Equivalence check: `bun run verify:cem` must accept a manifest whose corpus entries match the hand-written trio's. If the TS checker cannot resolve self-imports from generated output, decide between adapting the plugin and having the compiler emit CEM declaration fragments from its registry — record the decision in ADR 0023.
