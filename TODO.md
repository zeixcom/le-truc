v2.3 implementation of implicit effect collection — see [ADR 0018](adr/0018-implicit-effect-collection-via-ambient-context.md). Goal: `watch()`/`on()`/`pass()`/`each()`/`provideContexts()` register into an ambient collector when called, so the factory no longer needs to `return` a `FactoryResult` array. Explicit `return [...]` keeps working unchanged (dual support) — the array is simply unused, since collection already happened via the push. No type-signature break: the factory return type is already `FactoryResult | Falsy | void`.

- [x] LT-003: Wire `each()` into a nested per-element collector — reviewed ✓
  **Skill:** le-truc-dev
  **Context:** `each()` (`src/helpers/reactive.ts`) currently expects its `mount(element)` callback to return a `FactoryResult | EffectDescriptor | Falsy` which `each()` activates itself. Change `keyedScopes`' `mount` invocation to push a fresh local collector before calling `mount(element)` and pop it (in `try`/`finally`) after — descriptors created by `watch()`/`on()`/`pass()` calls inside the callback register into this local collector instead of (in addition to, for back-compat) being returned. Must support arbitrary nesting depth (an `each()` callback that itself calls `each()`, e.g. a grid of rows containing columns) — verify by construction, not just by the two-level examples that exist today. Depends on LT-001, LT-002.
  **Changed:** `src/helpers/reactive.ts` — `each()` now builds its own outer descriptor as a `const` and calls `pushDescriptor(undefined, 'each', descriptor)` (no host — `each()` isn't host-bound, unlike `watch`/`on`/`pass`). Internally, the per-element `mount` closure wraps `callback(element)` in `withCollector(collected, ...)`, then activates `collected` via the existing `activateResult()`, then activates anything in the callback's legacy return value that *isn't already in* `collected` (new local helper `activateUnseen()`, dedup by reference via a `Set`).
  **How:** Two things had to be solved beyond "call `withCollector`": (1) `each()`'s own outer descriptor (the thing `each()` itself returns) needed to push into whatever collector is active when `each()` is called — otherwise a *bare* nested `each()` call (no `return`) inside another `each()`'s callback would silently do nothing, which is exactly the bug this ADR exists to eliminate, and it's also literally the grid/nesting case you asked about. That's why `each()` needed `pushDescriptor` too, not just `keyedScopes`. (2) Dedup: since `watch()`/`on()`/`pass()` now push unconditionally, an old-style `return watch(...)` inside an `each()` callback means the descriptor is *both* pushed into `collected` *and* returned — activating both would run it twice. `activateUnseen()` recursively flattens the legacy return value and skips anything already in `collected` (checked by reference, via `Set`). Verified this is necessary and sufficient with a test (`does not double-activate a descriptor that is both collected and returned`).
  **Check:** (1) `activateUnseen()` is a new exported-from-nowhere (module-private) helper alongside `activateResult()` — consider whether it should be merged into `activateResult()` itself (optional `seen` param) instead of a separate function, for a smaller surface; I kept them separate to avoid changing `activateResult()`'s signature (also used by `component.ts` for the top-level `#setup` today). (2) Nesting: added a 3-level (row/col/cell) test (`src/tests/reactive.test.ts`, `each — implicit collection` describe block) confirming unbounded depth works, as `withCollector`'s stack-via-recursion design predicted in LT-001 — no surprises there. (3) Ran into a TypeScript inference quirk at 3+ levels of nested `each()`/`watch()` calls with inline arrow callbacks — overload resolution for `watch()` picked the wrong (array) overload. Worked around by extracting named handler functions with explicit parameter types instead of inline arrows; didn't dig into *why* TS's inference broke at that depth specifically, since the runtime behavior is what's under test — flagging in case it recurs in real component code at that nesting depth, though inline arrows work fine through 2 levels (all real examples today) and only broke at 3.
  **Review:** Approved, with a design-consistency finding to fold into LT-005 (see LT-005's updated Context below): `each()`'s merge+dedup strategy (`activateUnseen()`) and the planned top-level strategy (LT-005 ignores the factory's return value entirely) solve the same "descriptor is both collected and returned" problem two different ways. Resolve by making both levels ignore the return value outright — simpler, consistent, and removes `activateUnseen()`/the `Set` dedup entirely rather than just relocating it. Item (3), the TS inference quirk, is promoted to its own follow-up task (LT-009) below rather than left as a workaround, since the grid-nesting case it affects is ADR 0018's flagship justification, not an edge case.

- [x] LT-009: Root-cause the TypeScript overload-resolution failure at 3+ nested `each()`/`watch()` levels — done ✓
  **Skill:** le-truc-dev
  **Context:** Found during LT-003 verification: an inline arrow callback passed to `watch()` inside a 3-level-deep `each(rows, () => each(cols, () => each(cells, () => watch(state, v => ...))))` structure makes TypeScript's overload resolution pick `watch()`'s array-source overload instead of the signal overload, producing a spurious type error — even though the identical call compiles fine at 1–2 levels of nesting (`src/tests/reactive.test.ts`, `each — implicit collection` describe block worked around this by extracting named handler functions with explicit parameter types instead of inline arrows). This matters because arbitrary-depth nesting (the "grid" case: rows containing columns containing cells) is ADR 0018's flagship justification for moving off explicit `return` — if real component authors hit this at 3 levels with the natural inline-arrow style, it's a rough edge on the headline feature, not an edge case. Investigate whether it's fixable via a type-signature change to `each()`/`watch()` (e.g. an explicit generic default, or restructuring the overload set to reduce inference ambiguity) versus something to document as a known limitation (recommend named handlers past 2 levels). Depends on LT-003 shipping; not required before LT-005/LT-006, but should land before LT-007's docs claim arbitrary-depth nesting works seamlessly.
  **Changed:** `src/tests/reactive.test.ts` — the 3-level nested test now uses plain inline block-body arrows (no named handler functions, no explicit `each<Element>` type args), proving the earlier workaround was masking the real cause rather than fixing a depth-related one. No changes to `src/helpers/reactive.ts` — no signature fix needed.
  **How: root cause, isolated with a standalone `tsc --noEmit` repro (scratch file, deleted after).** **Nesting depth is a red herring — it has nothing to do with the failure.** The original 3-level test's handler bodies were `(v: string) => seen.push(...)` — expression-bodied arrows whose inferred return type is `number` (`Array.prototype.push`'s return value). `watch()`'s handler parameter type is `(value: T) => MaybePromise<MaybeCleanup>`, and `MaybeCleanup = Cleanup | undefined | void` (from `@zeix/cause-effect`) — a `number` return is a genuine, correct type error against every overload whose handler position expects `MaybeCleanup`. Confirmed empirically: the exact same `v => seen.push(...)` handler shape fails identically at **1 level of nesting**, not just 3+ (repro case A in isolation, no `each()` nesting at all involved). Confirmed the converse too: 3-level-deep nesting with a proper void-returning handler (`v => { seen.push(...) }`, block body, no explicit return) compiles cleanly with **no** named-handler workaround and **no** explicit `each<Element>` type argument. TypeScript's overload-resolution error message is genuinely misleading here — when an argument fails to match *every* overload, TS reports the failure against the *last* overload tried (the array-source one) regardless of why the earlier, semantically-intended overload actually failed, so the reported error ("source isn't an array") points at the wrong argument entirely. That diagnostic-quality issue is a known, general TypeScript behavior (not something in `each()`/`watch()`'s control) — not a le-truc bug, and not fixable via a signature change here.
  **Check:** (1) This closes LT-009 as "not a real limitation" — LT-007's docs can claim arbitrary-depth `each()` nesting works with plain inline arrows, full stop, **as long as handlers return void** (which is already the documented contract, just not one anyone had reason to double-check against this specific misleading error before). (2) Worth a small doc callout for LT-007: if someone hits `No overload matches this call` / `... not assignable to parameter of type 'Reactive<...>[]'` on a `watch()` call that looks obviously correct, the real culprit is very likely a non-void handler body (classic case: `arr => items.push(arr)` or similar one-liners) — the error message won't point at the handler. (3) All 320 tests pass unchanged, lint clean, `tsc --noEmit` clean.
