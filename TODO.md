v2.3 implementation of implicit effect collection — see [ADR 0018](adr/0018-implicit-effect-collection-via-ambient-context.md). Goal: `watch()`/`on()`/`pass()`/`each()`/`provideContexts()` register into an ambient collector when called, so the factory no longer needs to `return` a `FactoryResult` array. Explicit `return [...]` keeps working unchanged (dual support) — returned descriptors already in the collector are deduped by reference (`forEachUnseen()`), and a hand-authored `EffectDescriptor` not produced by any helper is picked up via `return` or, as of LT-010, via the new `run()` helper. No type-signature break: the factory return type is already `FactoryResult | Falsy | void`.

- [x] LT-009: Root-cause the TypeScript overload-resolution failure at 3+ nested `each()`/`watch()` levels — done ✓
  **Skill:** le-truc-dev
  **Context:** Found during LT-003 verification: an inline arrow callback passed to `watch()` inside a 3-level-deep `each(rows, () => each(cols, () => each(cells, () => watch(state, v => ...))))` structure makes TypeScript's overload resolution pick `watch()`'s array-source overload instead of the signal overload, producing a spurious type error — even though the identical call compiles fine at 1–2 levels of nesting (`src/tests/reactive.test.ts`, `each — implicit collection` describe block worked around this by extracting named handler functions with explicit parameter types instead of inline arrows). This matters because arbitrary-depth nesting (the "grid" case: rows containing columns containing cells) is ADR 0018's flagship justification for moving off explicit `return` — if real component authors hit this at 3 levels with the natural inline-arrow style, it's a rough edge on the headline feature, not an edge case. Investigate whether it's fixable via a type-signature change to `each()`/`watch()` (e.g. an explicit generic default, or restructuring the overload set to reduce inference ambiguity) versus something to document as a known limitation (recommend named handlers past 2 levels). Depends on LT-003 shipping; not required before LT-005/LT-006, but should land before LT-007's docs claim arbitrary-depth nesting works seamlessly.
  **Changed:** `src/tests/reactive.test.ts` — the 3-level nested test now uses plain inline block-body arrows (no named handler functions, no explicit `each<Element>` type args), proving the earlier workaround was masking the real cause rather than fixing a depth-related one. No changes to `src/helpers/reactive.ts` — no signature fix needed.
  **How: root cause, isolated with a standalone `tsc --noEmit` repro (scratch file, deleted after).** **Nesting depth is a red herring — it has nothing to do with the failure.** The original 3-level test's handler bodies were `(v: string) => seen.push(...)` — expression-bodied arrows whose inferred return type is `number` (`Array.prototype.push`'s return value). `watch()`'s handler parameter type is `(value: T) => MaybePromise<MaybeCleanup>`, and `MaybeCleanup = Cleanup | undefined | void` (from `@zeix/cause-effect`) — a `number` return is a genuine, correct type error against every overload whose handler position expects `MaybeCleanup`. Confirmed empirically: the exact same `v => seen.push(...)` handler shape fails identically at **1 level of nesting**, not just 3+ (repro case A in isolation, no `each()` nesting at all involved). Confirmed the converse too: 3-level-deep nesting with a proper void-returning handler (`v => { seen.push(...) }`, block body, no explicit return) compiles cleanly with **no** named-handler workaround and **no** explicit `each<Element>` type argument. TypeScript's overload-resolution error message is genuinely misleading here — when an argument fails to match *every* overload, TS reports the failure against the *last* overload tried (the array-source one) regardless of why the earlier, semantically-intended overload actually failed, so the reported error ("source isn't an array") points at the wrong argument entirely. That diagnostic-quality issue is a known, general TypeScript behavior (not something in `each()`/`watch()`'s control) — not a le-truc bug, and not fixable via a signature change here.
  **Check:** (1) This closes LT-009 as "not a real limitation" — LT-007's docs can claim arbitrary-depth `each()` nesting works with plain inline arrows, full stop, **as long as handlers return void** (which is already the documented contract, just not one anyone had reason to double-check against this specific misleading error before). (2) Worth a small doc callout for LT-007: if someone hits `No overload matches this call` / `... not assignable to parameter of type 'Reactive<...>[]'` on a `watch()` call that looks obviously correct, the real culprit is very likely a non-void handler body (classic case: `arr => items.push(arr)` or similar one-liners) — the error message won't point at the handler. (3) All 320 tests pass unchanged, lint clean, `tsc --noEmit` clean.
