- [ ] LT-028: No sanctioned lowering for reactive host-level style/CSS-custom-property updates (found migrating `basic-gauge.tsrx`, LT-026; depends on LT-029)
  **Skill:** le-truc-dev
  **Context:** `basic-gauge.ts`'s hand-written original reactively sets two CSS custom properties on the HOST itself (`host.style.setProperty('--basic-gauge-degree', …)`, `host.style.setProperty('--basic-gauge-color', …)`) and a descendant's `.textContent`, all from ONE `watch(computedFn, arbitraryCallback)` call. Two things currently block a sanctioned lowering: (1) sub-design 4's `pass`-only custom-element interop rule rejects ANY function-valued attribute on a custom element outright (`reactiveAttrOnCustomElement`), including the ROOT itself — so `style={() => …}` on `<basic-gauge>` doesn't compile, even though inline style, unlike `pass`, isn't custom-element interop at all — it's a native DOM property every element has; (2) `bindStyle(element, prop)` (`src/bindings.ts`) only sets ONE CSS property per binding — the gauge needs to set TWO (`--basic-gauge-color`, `--basic-gauge-degree`) from one computed value, and multiple bindings from one `watch()` source isn't how the existing `bind*` helpers compose. `basic-gauge.tsrx` (LT-026) works around this by rendering the ring's color/rotation as a STATIC `style` attribute computed once at server-render time (correct initial paint) and dropping live updates after connect entirely — a real, user-visible regression versus the hand-written component, not a cosmetic one.
  **Decision (scope, not yet implemented):** Considered a compiler-only `style:<prop>={…}` or `style={() => ({ '--a': …, '--b': … })}` map syntax (mirroring the existing `class={{ … }}` class-map lowering, one `watch()`+`bindStyle()` call per key) — set aside in favor of fixing the underlying LIBRARY gap first (LT-029: `bindStyle()` itself should accept a map so ONE binding can set several properties, matching how a real hand-written component would call it once). Once LT-029 lands, this ticket is: (a) exempt `style={() => …}` from the custom-element reactive-attribute gate (`reactiveAttrOnCustomElement`) the same way `class-map` already is (no `isCustom` check on that code path today), and (b) lower a `style={() => ({ … })}` object-literal-bodied thunk to one `watch(reactive, bindStyle(el, map))` call, analogous to (but simpler than) the existing per-key `class-map` lowering since `bindStyle`'s new map form takes the whole object in one call.

- [ ] LT-029: Extend `bindStyle()` (`src/bindings.ts`) to accept a map of CSS properties, not just one (proposed while investigating LT-028; library API change, not yet implemented)
  **Skill:** le-truc-dev
  **Context:** `bindStyle(element, prop): SingleMatchHandlers<string>` sets/removes exactly ONE inline style property per binding (`el.style.setProperty(prop, value)` / `el.style.removeProperty(prop)`). A component whose computed value drives SEVERAL CSS custom properties at once (`basic-gauge`'s ring: color AND rotation degree, from one threshold lookup) currently needs either N separate `watch()` calls (fine if the properties are independently computable, awkward when they share one underlying computed value) or an arbitrary callback body `bind*` doesn't support at all. Suggested by the owner while reviewing LT-028, as a separate task rather than folding a compiler-side workaround into the TSRX example.
  **Decision (proposal, not yet implemented):** Add an overload (or a second exported helper) accepting a map: `bindStyle(element, map: Record<string, string | null>): SingleMatchHandlers<Record<string, string | null>>` — `ok(map)` iterates the entries, `setProperty`/`removeProperty` per key (`null`/`undefined` value removes that one property, mirroring the single-prop overload's `nil` semantics per-key instead of only whole-binding); `nil` removes every key the map has ever contained (needs tracking previously-set keys across calls, similar in spirit to how `bindClass`/`cls()` reconciles a class list, so a value that disappears from the map on a later call doesn't leave a stale CSS property behind). Needs a design pass on exact typing/overload shape (single-prop and map overloads coexisting cleanly) and whether `nil` should clear ALL previously-set keys or only ones absent from a `null` map — an owner decision, not unilaterally picked here.
  **Check:** New unit tests in `src/bindings.ts`'s existing test suite for the map form: multiple properties set in one `ok`, a key with a `null`/`undefined` value removed individually, `nil` clearing everything the binding has ever set. Existing single-prop `bindStyle` usage/tests unaffected (additive, not a breaking change).
