# ADR 0022: `debug()` Extension for Visual and Console Instrumentation

## Status

✅ Accepted

## Context

[REQUIREMENTS.md S3](../REQUIREMENTS.md#s3-development-mode-with-enhanced-diagnostics) commits to enhanced `DEV_MODE` diagnostics beyond today's dependency-timeout and deprecation warnings — specifically, effect execution visibility. [N1](../REQUIREMENTS.md#n1-debug-flag-per-component-instance) asks for that visibility scoped to a single component instance via a `debug` flag, not every instance in the app at once. [ADR 0019](0019-extension-based-dependency-injection-for-definecomponent.md) anticipated this exact need when it generalized `defineComponent`'s third parameter into a `ComponentExtension[]` array: "Per-instance debug instrumentation ... the mechanism only needs to accommodate it later." This ADR is that later.

Two facts about the current architecture shape the design:

- **`ComponentExtension` can't see individual effects.** It exposes `onConnect` (once, post-factory) and `onAttributeChanged` — no hook into individual `watch()`/`on()`/`pass()` calls. Visual/console instrumentation of those calls needs a different mechanism than the extension hooks themselves.
- **Every `watch()`, `on()`, `pass()`, `each()` call registers an `EffectDescriptor` through the `collect()` chokepoint in `src/internal.ts`** before activation — the one place in the codebase that already sees every effect a component registers, regardless of kind.

A brainstorm of six candidate strategies (console logging, DOM attribute/CSS marking, an in-library overlay panel, a browser DevTools extension, console custom formatters, and a forward-compat global hook for a future extension) is recorded in full at `../DEBUG_EXTENSION_IDEAS.md`, including the per-strategy effort/pros/cons assessment and the design work that resolved the two hard sub-problems (attributing `watch()`'s opaque handler to an element; choosing an interaction model that doesn't clutter the app). This ADR distills that brainstorm into a single accepted design.

## Decision

Ship `debug()` (`src/extensions/debug.ts`), a `ComponentExtension` shaped like `formAssociated()`/`observedAttributes()` (same interface from ADR 0019), adding a reactive `debug: boolean` property (default `false`) — but **not exported, and not something an author opts into.** `defineComponent()` itself appends it to the merged extensions array unconditionally whenever `process.env.DEV_MODE === 'true'`, regardless of what the caller passed as the third parameter. Instrumenting a component requires no change to that component's own source: any component defined anywhere in a `DEV_MODE` build gets a `debug` property and the behavior below for free, the moment the app is rebuilt in dev mode. Everything it does is additionally gated at every call site inside `debug()` itself, so a bundler that doesn't fold `process.env.DEV_MODE` still can't ship it accidentally live — but the primary gate, and the one that keeps it out of production bundles at all, is `defineComponent()`'s own conditional append. `debug=true` in a production build does nothing, because the extension providing the property was never merged in; it is not a substitute for `DEV_MODE`, only a per-instance narrowing of it.

This is a deliberate, narrow exception to [ADR 0019](0019-extension-based-dependency-injection-for-definecomponent.md)'s "`component.ts` never imports a concrete feature module" invariant: `component.ts` must statically `import` `debug()` from `src/extensions/debug.ts` so it has something to conditionally append, whereas every other bundled extension is reachable only through the array a caller explicitly passes. The invariant existed to make tree-shaking a structural guarantee rather than something a bundler's dead-code elimination merely happens to achieve — `debug()` gives that up on purpose, because "zero code changes in user-written components" is the actual requirement here, and an opt-in-only mechanism can't deliver it. Production safety instead rests on the same `process.env.DEV_MODE === 'true'` constant-fold + DCE pattern the rest of the codebase's dev-only diagnostics already rely on (see the 2.3.0 fix that made `DEV_MODE` guards fold correctly, `CHANGELOG.md`) — an established, if now more heavily leaned-on, pattern rather than a new risk.

Scope is deliberately two of the six candidate strategies, chosen for being cheap, in-DOM, and additive rather than requiring the library to render its own UI:

**1. `console.debug` logging.** One entry per `on()`/`pass()`/`watch()` firing that also drives a visual effect (below) — log volume tracks visual activity, not all reactive activity indiscriminately. Minimal fields: kind (`on`/`pass`/`watch`), element (if attributable), value. Deliberately minimal at first; no `%c` styling or `console.group` nesting until plain output proves insufficient.

**2. DOM-level visual marking**, entirely via mechanisms the library already has:

- **Host indicator.** While `debug` is on, the host carries `:state(debug)` (via `bindState(internals, 'debug')`, the same custom-state mechanism every other component-owned state already uses) and a permanent `box-shadow: 0 0 0 1px <pink>` (sharp, no blur) — visible even when nothing is happening. Any `on()`/`pass()`/`watch()` firing for that host — attributed to an element or not — snaps the blur to `0 0 0 4px <pink>` immediately, then eases back to the sharp 1px baseline slowly. Because this lives at the `collect()` chokepoint, it needs no element attribution: it is the only visual signal available for a `watch()` handler that can't be mapped to a DOM node.
- **Per-element markings.** `on()`, `pass()`, and any `watch()` whose handler is a `bind*`-produced closure additionally set a presence-only `data-le-truc-on`/`-pass`/`-watch` attribute on the target element (color-coded purple/orange/green respectively, via a small injected stylesheet scoped under `*:state(debug) [data-le-truc-*]`), pulsing the same 4px blur on firing but fading to fully transparent rather than easing to a baseline shadow — elements have no permanent resting indicator, only the attribute itself.
- **Attribution.** `on(target, ...)` and `pass(target, ...)` know their element from their own signature. `watch(source, handler)` does not: `handler` is an opaque closure. Every `bind*` helper (`bindText`, `bindAttribute`, `bindClass`, `bindProperty`, `bindStyle`, `bindState`, `bindVisible`) already closes over `element` and returns a plain setter — in `DEV_MODE`, each registers that returned closure in a module-level `WeakMap<Function, Element>` singleton in `bindings.ts` at creation time. `watch()`'s `DEV_MODE` wrapper looks the handler up there before running it. This is exact tagging of a fact the helper already has, not inference — a hand-authored `watch()` handler that doesn't go through a `bind*` helper is not guessed at; it falls back to host-level-only visibility (see host indicator above), because a wrong highlight is worse than none.
- **Augmentation is always additive.** `on()`/`pass()`/`watch()` push a second, independent `EffectDescriptor` (or, for `on()`, a sibling `addEventListener` on the same target/type) through the same `collect()` chokepoint whenever `DEV_MODE && host.debug`. The author's own descriptor or listener is never wrapped, modified, or replaced — debug instrumentation cannot change an app's actual behavior (ordering, error propagation, `stopImmediatePropagation()` semantics) merely by being switched on.
- **Scheduling.** Pulses are scheduled and deduplicated per element via the existing `schedule()` in `src/scheduler.ts` — the same mechanism `dangerouslyBindInnerHTML` already uses — so a burst of same-element activity collapses to one visible pulse instead of a flicker.

**Toggling `debug`** has two entry points: the browser inspector's properties panel (`debug` is a plain reactive property, works today with no extra code, and remains the reliable fallback for elements a click can't reach) and, in `DEV_MODE`, a single document-level capture-phase click listener that toggles the nearest custom-element ancestor's `debug` property on `metaKey`+click. `metaKey` is provisional — Cmd/Ctrl+click on an `<a>` natively opens a new tab, but custom element hosts are themselves unlikely to be links, so the collision surface is judged small; easy to swap for a different modifier during implementation if that judgment proves wrong in practice.

## Alternatives Considered

- **A `Sensor`/`Signal`-based state list and dependency-graph overlay** (candidate strategy 3 in the brainstorm): a small custom element, code-split, rendering a live state list and dependency graph. Rejected for this ADR — it's the only candidate that would have the library render its own UI, which is in real tension with the "no client-side rendering" principle, and is a materially bigger feature (layout, cross-instance registry, its own z-index/`Shadow DOM` isolation concerns) than a debug flag. May be revisited later, in a different project, or not at all — not planned.
- **A real signal dependency graph.** `@zeix/cause-effect` holds a doubly-linked-list representation internally but doesn't expose it. Building this would require either a Cause & Effect API addition (a separate proposal, not assumed here) or Le Truc re-deriving graph structure itself from `collect()` registrations. Out of scope.
- **A browser DevTools extension** (Chrome/Firefox panel, à la React/Vue/Redux DevTools) with a forward-compatible global hook (`window.__LE_TRUC_DEVTOOLS_HOOK__`) for it to attach to later. Rejected, not deferred: separate codebase, store review and packaging for multiple browsers, ongoing maintenance as a second deliverable, no near-term consumer to justify the hook's compatibility burden. Not this project.
- **Heuristic attribution for `watch()`** (e.g. parsing `Function.prototype.toString()` for identifier names to guess a target element). Rejected: a wrong highlight actively misleads during debugging, which is worse than the honest "no element, but the component did something" host-level signal the design ships instead.
- **Per-state-change flashing** (flash the host on every individual reactive property write, independent of `on`/`pass`/`watch`). Tried first, dropped: it fired simultaneously with — and was visually redundant with — the effect-level markings and their own pulses, adding noise without new information. Replaced by the effect-triggered host pulse described in the Decision.
- **Two-key modifier chord (`Alt+Shift+click`)** for the toggle gesture, to sidestep both `metaKey`'s and `ctrlKey`'s native-conflict risk (link navigation; `ctrlKey`'s additional macOS secondary-click emulation). Set aside in favor of the simpler single-modifier `metaKey`, on the judgment that custom element hosts are rarely links themselves and the practical collision surface is small — revisitable during implementation.
- **An opt-in, exported extension** — `debug()` passed explicitly in the `extensions` array, the same way `formAssociated()`/`observedAttributes()` are used, keeping `component.ts`'s "never imports a concrete feature module" guarantee fully intact. Rejected: it would require editing every component an author wants to instrument (and un-editing it afterward), which fails the actual goal — inspecting *any* component, including ones an author didn't anticipate needing to debug, without touching its source. Auto-injection is the only shape that delivers "no code change necessary."

## Consequences

**Good:**
- Zero cost in production: every code path is `DEV_MODE`-gated and constant-folds away, including the `debug` property's own instrumentation — `debug=true` shipped to production by accident does nothing.
- No new binding primitive or effect-collection mechanism: marking reuses `bindAttribute`/`bindState`-shaped writes and the existing `collect()`/`schedule()` chokepoints, keeping the addition small relative to the rest of M5's toolkit.
- Every reactive firing is visible at some granularity — element-level where attribution is possible, host-level always — so there is no silent gap for unattributed `watch()` handlers, only a coarser signal.
- Works on every component automatically in a `DEV_MODE` build, including third-party components an author didn't write and can't edit — no `expose()`/`defineComponent()` call site anywhere needs to change to get instrumentation.
- Reuses the `ComponentExtension` shape from ADR 0019 (same `onConnect`/hooks interface `formAssociated()`/`observedAttributes()` use), so it needed no new extension mechanism — only a new place that array gets assembled (inside `defineComponent()` itself, rather than by the caller).

**Bad:**
- `watch()` attribution is real but partial: a handler not produced by a `bind*` helper gets no per-element mark, only the host-level pulse. Authors debugging a custom `watch()` handler need to know this distinction to interpret what they're seeing.
- The `metaKey` toggle gesture has a known, if judged-small, collision with native Cmd/Ctrl+click-opens-link-in-new-tab behavior, and no `preventDefault()` mitigation is specified in this ADR — left as an implementation-time judgment call, with the properties panel as the documented fallback.
- Every `bind*` helper gains a `DEV_MODE`-gated `WeakMap.set()`, and `on()`/`pass()`/`watch()` gain a `DEV_MODE`-gated companion-descriptor push — small, but it is new surface area in code paths that are otherwise on the hot path for every component's setup.
- Ships without the state-list/dependency-graph views some readers may expect from "debug mode" in other frameworks' devtools; this ADR explicitly does not attempt that (see Alternatives).
- `component.ts` gains a static import of `src/extensions/debug.ts`, breaking ADR 0019's structural "core never imports a concrete feature module" guarantee for this one case. Production safety now depends on the bundler correctly folding `process.env.DEV_MODE` and eliminating the now-dead import along with it, rather than being provably unreachable by construction the way every opt-in extension is. Worth a dedicated bundle-size regression test (`test/regression-bundle.test.ts`) asserting the minimal-entry fixture doesn't grow, the same way ADR 0019's tiers were verified empirically rather than assumed.
- `debug` becomes a reserved property name on **every** component in a `DEV_MODE` build, even ones that never reference `debug()` — `expose({ debug: ... })` anywhere will collide with the auto-appended extension's `reservedMembers`. This reservation doesn't exist at all in production (the extension isn't merged in), so the same component can be valid in production and throw in dev — a footgun worth surfacing prominently in developer-facing docs, not just this ADR.
