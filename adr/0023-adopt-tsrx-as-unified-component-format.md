# ADR 0023: Adopt TSRX as the Unified Component Format

## Status

✅ Accepted (2026-08-22, owner decision). All four milestones are verified in the inlined compiler (`server/tsrx/`, golden-tested in `server/tests/tsrx/`): the emitter core and client codegen for the sanctioned subset (milestones 1–2, [`REPORT-unified.md`](../spike/tsrx-phase0/REPORT-unified.md)), the two format verifications that gated acceptance — extension activation (sub-design 8, the `form-textbox` fixture proves the widened `FormFactoryContext` overload end to end) and Custom Element Manifest generation (sub-design 9, byte-equal extraction from generated clients) — reactive `@for` over a `List` via `reconcile()` (milestone 3, the `module-list` lowering spec implemented and reviewed), and type flow (milestone 4, delivered with the projection approach reconsidered — child-module side-effect imports, the `globals.d.ts` ambient contract, and emit-then-check in CI; see the sub-design 6 amendment and LT-011 for the CLI-first span-table follow-up). The corpus (`basic-counter`, `module-tabgroup`, `module-list`, `form-textbox`, `form-checkbox`) compiles end to end, and the tsrx.dev feature sweep is handled deliberately (`@if`/`@switch`/`@try` supported, beyond-pin constructs diagnosed with hints, async boundaries gated). Residual work is queued as post-acceptance refinement, not blockers: diagnostics mapping (LT-011), async rendering and the gated dynamic-HTML/error-boundary residue (LT-012), then the docs/examples wholesale migration.

## Context

Every Le Truc component is authored as three hand-maintained files (`.ts` / `.html` / `.css`) whose mutual contract is checked only at runtime — `first()` failures are the symptom, drift is the disease. REQUIREMENTS.md [§1](../REQUIREMENTS.md#the-core-insight) requires server-rendered HTML with a thin reactive enhancement layer, [§5](../REQUIREMENTS.md#5-technical-constraints) prohibits client-side rendering and any SSR layer *in the library*, and [§7](../REQUIREMENTS.md#7-out-of-scope) anticipated a companion project for the server half. TSRX (Ripple ecosystem) is a TypeScript superset with a shared parser (`@tsrx/core`) and per-target codegen; every existing target renders and re-renders its own DOM — Le Truc would be the first server-oriented target. Two Phase 0 spikes ([Option C](../spike/tsrx-phase0/REPORT.md), [unified](../spike/tsrx-phase0/REPORT-unified.md)) validated the direction on `@tsrx/core` 0.1.60: every syntactic position needed is grammar-native, and hand-compiling unified sources reproduces today's hand-written components statement for statement.

## Decision

Adopt a **unified single-file `.tsrx` format** — server args, signals, `expose()`, markup, event handlers, and scoped styles in one source — compiled by a **split compiler** built in-repo on pinned `@tsrx/core`. Sub-designs:

1. **One format, no coexistence.** The unified format is the only authoring format. No authored-client fallback, no escape hatches; event delegation is a compiler optimization for bubbling events. The Option C spike remains a feasibility proof, never a shipping format.
2. **Split compiler, isolated dependency.** Server evaluation runs the `@{ }` setup once (signals as plain values) and renders HTML; client generation emits a `defineComponent()` factory that imports solely from `@zeix/le-truc` (CE v2 names via the 2.5.1 bridge) — sources import nothing. `@tsrx/core` is pinned at 0.1.60 behind one emitter module; upgrades are reviewed changes; loss of `stylesheet.source` is a conscious pin-breaker. CSS is emitted verbatim, tag-scoped, no class hashing. The compiler is **inlined in this repo — no separate package ships before TSRX reaches 1.0**; with Le Truc v3.0 it ships as `@tsrx/le-truc`, while `@zeix/le-truc` remains the backend-agnostic client layer.
3. **DOM-is-truth seeding, end to end.** The server renders each reactive expression's initial value; the client harvests its initial state from that DOM (ADR [0003](0003-attributes-drive-state-at-connect-time-only.md) preserved; no serialized state payload). Lists seed from server args server-side and are adopted from the rendered HTML client-side. Harvest canonical site: first by document order, DEV_MODE warns on disagreement. Thunk attributes are server-evaluated when their dependency closure is server-known (args, seeded list state); otherwise omitted — `<template>` clones auto-augment on client insertion — with authored static markup controlling the no-JS initial state.
4. **Author-declared reactivity, no marker identifiers.** A function-valued attribute is a reactive binding; `on*`-prefixed are events (stripped server-side); `{ get, set }` object literals are mediated `pass()` (ADR [0012](0012-deprecate-unrestricted-write-short-forms-in-pass.md)); `&{ }` is the grammar-native reactive child. No upstream grammar changes required.
5. **Dual `@for` lowering.** Over server data: rendered once, enhanced via `each()` per-element scopes (ADR [0014](0014-keyed-per-element-scopes-for-memo-collections.md)). Over a reactive `List`: server-rendered keyed items + extracted `<template>` whose holes become `<slot>` markers, reconciled by `reconcile()` (ADR [0017](0017-keyed-template-clone-reconciliation-for-lists.md)). Loop context crosses to the client via **hoisted-const rebinding** (server-data consts rebind to element-derived attribute reads); direct loop-variable references inside reactive thunks are compile errors with a hoist-first diagnostic.
6. **Type flow by projection.** The generated client module is the primary Volar projection (`createVolarMappingsResult` over the generated-TS source map); element interfaces are authored inline via `declare global` `HTMLElementTagNameMap` augmentations and resolved in generated code by [M4](../REQUIREMENTS.md#m4-type-safe-dom-queries) selector inference; CI type-checks by emit-then-check. Wiring remains, invention does not. *(Amended at acceptance, 2026-08-22: the probe showed `createVolarMappingsResult` is transform-coupled — it throws unless the source map covers every source-AST token, an invariant only Ripple's own esrap-shaped transforms satisfy, and a split compiler cannot provide it through the client module alone. Type flow therefore stands on three delivered mechanisms — child-module side-effect imports (every addressed child component's `declare global` entry is in the generated client's scope), the `globals.d.ts` ambient contract (parity-tested against the compiler's recognized vocabulary), and emit-then-check in CI — and the projection follow-up (LT-011) builds our own span-table mappings, CLI-first. Sparse mappings suffice: TS diagnostics only arise in code positions, and every code position lowers into the client module.)*
7. **Library boundary unchanged.** The compiler is separate build-time tooling; `@zeix/le-truc` stays browser-only and never renders initial HTML — the generated client enhances, and `reconcile()` remains the only DOM-creation primitive. This realizes §7's anticipated companion project as build-time compilation, not a server runtime.
8. **Extension activation via `export const config`.** A `.tsrx` source declares `defineComponent`'s third argument as a zero-import, statically-analyzable data object — `export const config = { formAssociated: true, observedAttributes: ['value'] }`. The compiler validates keys against the known bundled extensions (unknown key, non-`true` form flag, combined form variants → TSRX009), and every `observedAttributes` name must be a Parser-exposed prop — otherwise the extension is inert at runtime and the diagnostic says so. The generated client auto-imports the extension factories from `@zeix/le-truc` and emits them as the third argument with the form variant leading — ADR [0019](0019-extension-based-dependency-injection-for-definecomponent.md)'s ordering rule is enforced structurally, because there is no authored order to get wrong — which is what selects the widened `FormFactoryContext` overload; `FormAssociatedElement` is carried as a type import when the authored `declare global` uses it. Attribute-driven props use Parser-call `expose()` initializers (`expose({ value: asString('') })`): the host attribute seeds the prop at connect (ADR [0003](0003-attributes-drive-state-at-connect-time-only.md)) and `observedAttributes` re-parses it on later mutations; `as*` factories and `defineMethod()` are compiler-recognized ambients — imported on the client, inert shims on the server harness. `host` and `internals` are ambient context names in every client code position. A reactive attribute thunk reading `host.<parserProp>` — the value mirror, `value={() => host.value}` — lowers to `watch(() => host.<prop>, bindProperty(el, attr))` and server-renders from the root attribute's expression: the host attribute IS the prop's server truth (DOM-is-truth, sub-design 3). Managed form props appear as string-literal lazy children — `&{'validationMessage'}` lowers to `watch('validationMessage', bindText(el))` and server-renders empty; that watch source exists only on `FormFactoryContext`, so emit-then-check proves the widened typing end to end.
9. **CEM generation, staged: plugin now, compiler-direct at v3.** The Custom Element Manifest is generated by `cem analyze` with `@zeix/cem-plugin-le-truc` **unchanged**. The compiler carries the component JSDoc verbatim above the generated `export default defineComponent(` — identical comment text yields identical extraction — and the analyzer globs read the generated clients while the migrated components' hand-written `.ts` twins are excluded (they stay on disk as golden-test references). Equivalence is pinned by golden tests: `basic-counter` and `module-tabgroup` declarations are byte-equal to the hand-written entries; `form-textbox` is structural (its fixture is a deliberate subset) and proves the two extractions the hand-written corpus never had from generated code — a Parser-exposed attribute with its default, and extension-derived members from the emitted third argument. `build:cem` compiles the corpus before analyzing (the generated clients are gitignored), and `verify:cem` fails when a migrated tag is missing. **When the migration deletes the last hand-written component (v3), the analyzer+plugin dependency is dropped in favor of compiler-emitted CEM declaration fragments from the registry** — the compiler already holds every input (tag, JSDoc, Props members, Parser-expose, config), the endgame couples the manifest to the stable source contract instead of the derived client's shape, and equivalence is anchored by the final plugin-generated golden manifest.

## Alternatives Considered

- **Status quo (hand-written trio)**: rejected — the drift problem is the motivation; runtime contract errors are the tax.
- **Option B — TSRX as server templating only**: rejected — components stay three files; drift unsolved.
- **Option C — authored split (client export alongside the template)**: validated as feasible (the first spike), rejected as a shipping format — two truths still coexist per component, and coexistence doubles format maintenance.
- **Compiler-inferred reactivity (taint walk from declared roots)**: rejected — author-declared markers (thunks, `&{ }`) eliminate the inference entirely; a `live()` marker identifier was likewise dropped once grammar-native thunks proved sufficient.
- **`useExtensions([…])` hook inside the `@{ }` setup**: rejected — it is a directive that never executes anywhere (stripped client-side, shimmed as a no-op server-side), unlike every other setup statement, which runs on at least one half; and it hands ADR 0019's formAssociated-first ordering rule back to the author instead of enforcing it structurally. The extension universe is compiler-known either way — generated imports must be materialized by name — so the hook buys no openness.
- **Module-level `export const extensions = [formAssociated(), …]` (verbatim slice into the third argument)**: viable — authored shape equals emitted shape, mirroring the runtime API — but it requires validating array element shapes (spreads, conditionals) plus a first-position check for the form variant, for no gain over the closed config key space. Rejected as the primary surface; the runtime vocabulary remains visible in the *generated* client.
- **Compiler-emitted CEM fragments as the migration bridge (bypass `@custom-elements-manifest/analyzer` immediately)**: viable — the compiler already holds every extraction input — but ~30 hand-written examples still need the analyzer until the migration completes, so it means a fragment-merge step plus two extraction implementations kept in parity exactly while the format is still moving (milestones 3–4). Adopted as the v3 endgame instead (sub-design 9).
- **Reusing `createVolarMappingsResult` for the projection (sub-design 6 as originally drafted)**: rejected after probe (2026-08-22) — the API walks every source-AST token and throws unless the source map covers each one, an invariant tied to Ripple's own transform outputs. The split compiler emits its own span-table mappings instead (LT-011).
- **JSX instead of TSRX**: rejected — no first-class control flow, no host-owned scoped styles, no shared parser to build on; TSRX's lazy `&` semantics already match Le Truc's reactive reads.

## Consequences

**Good:**

- Single source of truth per component; the HTML contract is checked at compile time (root-tag match, selector uniqueness, hoist-rule enforcement) instead of surfacing as `MissingElementError` in the browser.
- Generated client code is exactly today's idiomatic Le Truc — the existing examples corpus doubles as golden-test expectations.
- Zero-import, fully co-located authoring; runtime semantics match the Solid/Ripple first-pass-then-pinpoint model.
- No state payload to hydrate from; pages are correct before JavaScript loads.

**Bad / accepted tradeoffs:**

- The rewrite rules (hoisted-const rebinding, harvest rules, dual `@for`) are now product surface — exhaustive specification and golden tests are mandatory; a wrong rewrite is a wrong component.
- `@tsrx/core` is 0.x and fast-moving: the pin holds, but upgrade churn is expected and reviewed.
- Raw `.tsrx` files are untyped without the projection toolchain; the Volar wiring is the largest residual implementation risk.
- Thunk attributes with non-server-known dependencies render client-corrected (flash risk accepted; authored statics mitigate).
- The examples corpus migrates wholesale — no coexistence path — and authors debug generated factories (mitigated by the DEV_MODE `debug()` extension, ADR 0022).
