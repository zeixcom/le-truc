# ADR 0027: Server Simulation — Render Initial HTML by Executing the Client Module

## Status

🔄 Proposed — **owner accepted the direction 2026-09-02**; formal acceptance is sequenced behind the driver-portability and substrate spikes and the compiler-consequences plan (TODO LT-149–LT-153, with the acceptance milestone in LT-153), and implementation resumes at LT-154. Not yet implemented. Amended pre-publication: the simulation substrate is **jsdom**, adopted after a working spike under Bun replaced this draft's hand-rolled shim design. Amended again pre-publication after architect review (2026-09-02): sub-design 1's "one component artifact" claim was **wrong** and is corrected in place — template lowering cannot move into the client module; sub-designs 8–10 add the fixed-point, synchronous-serialization/hermeticity, and render-isolation requirements the review surfaced; a real browser is now on the record as the rejected maximal-fidelity alternative. On acceptance this retires ADR [0024](0024-adopt-tsrx-as-isomorphic-component-format.md) sub-design 3's splice-and-evaluate server-evaluation rule (including the LT-085/LT-118 fold routes) in favor of execution.

## Context

The split compiler decides renderability syntactically: the evaluability rule (`server/tsrx/evaluability.ts`, LT-043) checks a thunk's free names against the render scope, and `hostDerivedFold` splices `host.<prop>` reads with root-attribute expressions. LT-143 hit the ceiling of that grammar from three directions at once: a setup-const helper called with `host` as a bare argument is refused wholesale; a value-passing reshape fails the other module (`TSRX005` — server args do not exist in client-emitted thunks); and config args that are not exposed props have no route into the fold set at all (`bindsExposedArg` requires an exposed prop), whose only remedy seemed to be exposing them — making static connect-time config reactive and colliding with the native `HTMLElement.lang` IDL for `lang`. The structural facts that dissolve the dilemma: the generated client factory already runs **at connect time** against the real upgraded element (Le Truc enhances parsed HTML; it does not client-render, so `host.hasAttribute('ordinal')` is ordinary connect-time DOM reading), and Cause & Effect is environment-agnostic — a dependency-tracking state graph with arbitrary IO at the leaves. Nothing principled prevents the server from running the same client module the browser runs, against a model of that environment. Before building such an environment, existing DOM simulations were evaluated: jsdom covers every load-bearing behavior (spike-verified under Bun, jsdom 30.0.1 — see Decision), and hand-rolling a smaller DOM would be maintaining a less complete version of a solved problem.

## Decision

**Server Simulation**: the server renders initial HTML by executing the generated client module against jsdom, letting Cause & Effect evaluate the reactive graph once; the emitted HTML is that graph's initial state. The client remains ground truth and corrects on connect — DOM-is-truth (ADR [0003](0003-attributes-drive-state-at-connect-time-only.md)) and the accepted flash trade (ADR 0024 s3, s15) are unchanged. Sub-designs:

1. **One evaluation mechanism, not one artifact**. The server render becomes a driver: obtain the component's initial markup, parse it into the simulated document, register the generated client module against a jsdom `customElements`, let the upgrade run, serialize. What retires is `emit-server`'s **evaluation half** — the evaluability gate, the fold routes, and the splice machinery — because the client module now computes every initial value by running.
What does **not** retire is template lowering. The generated client module contains no markup construction: `basic-pluralize.client.ts` only queries and binds, while every `__html.push` lives in `basic-pluralize.server.ts`, and the library creates DOM nowhere except `reconcile()`. Executing the client module against an empty document therefore produces nothing. Server args, `@if`, `@for` over server data, composition splicing, and escaping have no other home and stay server-side; the spike concedes this by calling `renderFormColorgraph()` for markup before importing the client. The honest claim is narrower than the draft's and still worth the change: **one mechanism answers "what is this expression's initial value", and the drift class shrinks from "two hand-shaped modules" to "markup vs. selectors" — which simulation closes too, by executing the selectors** (see Consequences).

2. **The substrate is jsdom — no hand-rolled DOM.** The driver owns one shared jsdom document per build; components are authored `HTMLElement` subclasses extending jsdom's base class, defined after the SSR'd markup is parsed so the real upgrade path runs. Spike-verified under Bun: pre-parsed custom elements upgrade with `connectedCallback` firing **child before parent** (the native bottom-up order the child-await relies on), `whenDefined` resolves, `instanceof` is clean within the window's realm, IDL reflection (`lang`) is spec-faithful for free, and connect-time DOM writes land in the serialized `outerHTML`. Driver responsibilities, spike-derived: (a) **normalize `attachInternals()` to throw** so the run takes the library's own graceful-degradation path — jsdom's *skeletal* `ElementInternals` is worse than none, silently defeating the guard (`form.ts` reads `internals.validationMessage` → `createState(undefined)` → `NullishSignalValueError` per form-associated element); (b) **stub absent constructors as no-ops** (`ResizeObserver`, `matchMedia`, `IntersectionObserver`, `requestAnimationFrame`) so runs-once-at-connect effects are harmless — a bare missing global can even surface process-fatal instead of per-element; (c) **contain per component**: wrap register+upgrade in try/catch so a throwing component degrades to the plain SSR output and never blocks the build; (d) **close the realm's IO**: `fetch` (and any other ambient network global the host runtime supplies — Bun's survives into the jsdom realm untouched) is replaced with a rejecting no-op, so a build can never depend on the network. (d) is the hermeticity half of sub-design 9's serialization boundary.

3. **Bindings write the simulated document.** No recording layer: `watch()` installs normally into Cause & Effect (which runs server-side verbatim), the `bind*` helpers write the jsdom DOM, and the driver serializes the tree after the connect pass. The "virtual DOM" is the simulation document; there is no diffing and no client-side VDOM.

4. **Simulated connect.** jsdom supplies the upgrade order natively; the server `defineComponent` driver additionally honors the library's own child-await (`customElements.whenDefined`), so a parent's connect-time reads of child state never error — the same dependency-resolution semantics as the browser (REQUIREMENTS M8).

5. **Helper contract under simulation.** `host`: the real simulated element — attribute reads, reflection, and `closest` are jsdom-native, so the locale walk resolves own-attribute-or-null naturally and config reads like `hasAttribute('ordinal')` run as authored. `first`/`all`: real `querySelector(All)` against the component-owned subtree (the compiler's selector IR remains available for cross-check diagnostics, not for resolution). `expose`: runs as the authored connect code, reading attributes seeded from the server args through the component's own parsers. `pass`: the existing `truc:pass` lowering (wiring live signals between simulated components is a later depth). `on`: no-op. `provideContexts`/`requestContext`: no-op, the consumer holding its fallback signal — the s15 fallback-render precedent. `internals`: deferred with evidence — jsdom 30's `attachInternals()` exists but the `ElementInternals` surface is skeletal (`states` absent), and nothing in the corpus renders through internals at connect.

6. **The determinism gate retires.** No AST impure-ambient analysis: a thunk reading `Date.now()` folds to the build machine's answer — accepted owner trade, since a server-defined value beats omission for the no-JS worst case and the client corrects instantly otherwise. Queries the server genuinely cannot answer keep the other half of the same stance: they resolve to jsdom's best effort (a bare fragment has no page ancestors, so `closest` walks only the rendered subtree) or to silent defaults — the client corrects. **Fidelity statement:** the simulation models the rendered fragment and nothing beyond it; consumer-authored attributes on the tag that the pipeline did not parse into args, and layout reads (`getBoundingClientRect` returns silent zeros), are the documented wrong-answer corners — the corpus stays fixture-pinned precisely so such drift is caught, not assumed absent.

7. **Staged path.** Stage 1: driver + jsdom substrate for `host` reads and reactive attributes (this alone unblocks LT-143 — `pluralCategory(host)` runs as authored), **including sub-design 8's fixed-point gate** — that gate is what makes stage 1 safe to ship, not a stage-3 refinement. Stage 2: ref resolution and composition against the simulated tree. Stage 3: full driver-based rendering, retiring the hand-shaped render functions. Capability stages, not contract stages. **Stress-case evidence:** `form-colorgraph` — the heaviest corpus component (canvas drawing, `ResizeObserver`, form-associated, three composed spinbutton children) — simulated end to end under the driver posture above: with internals normalized and `ResizeObserver` stubbed, its connect completes cleanly (knob/thumb positioning, `aria-valuenow`/`-text`, and the three axis pushes all land with real computed values; the sole residual notices are jsdom's `getContext` not-implemented, neutralized by the component's own `if (!ctx) return` guard — canvas pixels do not serialize to HTML anyway), and the serialized HTML is a strict improvement over today's SSR (3302 vs 2274 chars — the host-derived state the current pipeline omits as the flash class now ships).

8. **Connect must be a fixed point, and the driver proves it.** Today's served HTML is *pre*-connect by construction; under simulation it is *post*-connect, and the browser then runs connect **again over the simulation's own output**. Nothing in the library or the compiler requires enhancement to be idempotent over what enhancement produced — that invariant is newly load-bearing, and it is not free. `reconcile()` is the sharp case (`form-tokenbox`, `module-list`): the simulation materializes the keyed items and consumes the `<template>`/`<slot>` markers, and the browser's adoption path (ADR [0017](0017-keyed-template-clone-reconciliation-for-lists.md), ADR 0024 s5) then runs against already-reconciled DOM. Harvest is the quiet case: `expose()` reads a `textContent` the simulation may itself have written. **Rule:** the driver runs the connect pass twice and requires byte-identical `outerHTML`; a component whose second pass differs is a build error, reported against that component. Corpus-wide, in stage 1.

9. **The arm that ships is a compiler decision; the serialization boundary is synchronous.** ADR 0024 s13 does not merely observe that the server render is synchronous — it *guarantees* it ("server render is synchronous and never awaits"), and the tri-state arm choice rests on that guarantee. Execution replaces the guarantee with a race: whichever microtasks happen to drain between instantiation and serialization would otherwise decide which `@try` arm ships.

   **What makes a resolved arm safe is not timing but harvestability.** The hazard is never the resolved arm in the HTML — it is a resolved arm contradicted by an unseeded client task. `match()` routes on whether the task holds a value (`effect.ts:214-236`, precedence `nil > err > stale > ok`): an unseeded task throws `UnsetSignalValueError` on first read and routes to **`nil`**, so rendered content is replaced by the loading arm and returns — a *regression*, worse than the ordinary flash trade, which only ever fills a value in. A task seeded with a value routes to **`stale`** instead, and the content stays put while it revalidates; `module-lazyload` already ships exactly that handler (dimming to `--opacity-dimmed`). Seeding does not prevent the re-computation — a fresh task node is `FLAG_DIRTY` regardless of `options.value` (`task.ts:132`) — and it does not need to. It only has to stop the content from disappearing.

   The seed's channel is the DOM, like every other prop's (ADR 0024 s3, one-site-three-roles): for `module-lazyload` the resolved value is already in the served markup, written into `.content`. Seeding is a harvest — `createTask(fn, { value: <read back from the site> })`, using the existing `{ value: T }` overload — not a state payload, and not per-definition data smuggled into a per-instance-agnostic client module. **Rule:** ship the resolved arm when the resolved value is harvestable from the markup the component rendered; otherwise ship `@pending`. Either way the choice is made by the compiler, and serialization is synchronous — no `await` between instantiation and serialization — so that the compiler's decision is the *only* thing that determines the arm. (Pin the harvest round-trip in a fixture: reading `innerHTML` back is not byte-identical to the fetched string, so `equals` will see one redundant write on revalidation.)

   **Two phases, and only the second is synchronous.** The no-`await` rule governs the instantiate→serialize window, not the build. A resolution phase *before* the simulation may await deliberately — that is what a build-time data dependency needs (see the `@try` shake case, CHECKLIST §9), and by the time connect runs those values are already settled. Correspondingly sub-design 2d's closed network is scoped to **inside the realm, during connect**: an accidental fetch from a component's connect code is what must not reach the network, while a declared build-time data dependency resolved in the resolution phase is an ordinary SSG data source. Accidental non-hermeticity is the target; declared data dependencies are not.

10. **Renders stay isolated enough to be a function of their args.** `renderBasicPluralize(args)` is today a pure function; goldens are order-independent and a render is memoizable on `(component, args)`. One shared document plus one module cache per build puts that at risk — module-level mutable state, `customElements.define` ordering, id collisions (CHECKLIST §10). No corpus component holds module-level mutable state today, so this is pinned as an invariant rather than assumed: **the corpus renders in two different orders and must produce identical output.**

## Alternatives Considered

- **A hand-rolled virtual DOM shim** (lazy Proxy elements, virtual `customElements` registry, a spec-derived reflection table, throw-on-unknown reads) — this draft's original design: rejected after the jsdom spike. The registry would have re-implemented upgrade ordering and `whenDefined` (fiddly spec code), the reflection table would have been a less complete duplicate of a spec fact, and throw-on-unknown buys refusal-as-diagnostic at the price of answering nothing the table didn't hand-implement. Maintaining a less complete simpler version of a solved problem.
- **happy-dom / linkedom as the substrate**: happy-dom is the named fallback (lighter, implements `matchMedia`) if a jsdom gap bites or Bun friction appears; linkedom lacks custom elements and is disqualified. The spike ran on jsdom first because it is the conservative, spec-est option. **Qualified 2026-09-03:** the fallback is conditional on sanitizer consolidation. DOMPurify's supported server DOM is jsdom, and happy-dom is not a supported target; if consolidation is adopted (see Consequences), happy-dom drops from "named fallback" to "viable only if we keep two sanitizers." LT-152 verifies this rather than inheriting it, and must not recommend on weight alone.
- **Widen the splice grammar** (exempt setup-const/plain-import names from `hostDerivedFold`'s free-name refusal; add a third fold route for self-mirrored config args behind a reflection allowlist): rejected — every new idiom needs its own proof rule, and the grammar grows per expression form while the simulation answers all forms at once; it also perpetuates the two-module drift.
- **Expose config props** (make `lang`/`ordinal` reactive so they enter the fold set): rejected — reactivity is machinery, not semantics, for connect-time config; `lang` collides with the native IDL (an own property shadows the reflected getter in both directions); and a compiler limitation must not dictate a component's public contract — the principle that killed ADR 0024's enhancer mode.
- **Transplant server args into client scope** (fix TSRX005 by emitting arg bindings into the client module): rejected — invents a channel for values that already have a client home on the element's own attributes; the attribute is the client home.
- **A real browser as the substrate** (Playwright, already a devDependency): the maximal-fidelity option and the one a reviewer asks about first, so it is on the record rather than passed over. It answers every gap jsdom leaves — no `attachInternals` normalization (sub-design 2a exists *purely* because of a jsdom deficiency), real layout for `getBoundingClientRect`, real `matchMedia`, real canvas, and the executed code path would be the same one the shipped page takes. Rejected on cost and shape: a browser process per build in CI, orders of magnitude slower than an in-process document across a corpus this size, and page/driver orchestration that dwarfs the "import, register, instantiate, serialize" driver jsdom permits. Revisit if the stub posture stops being containable — this rejection is about cost, not about correctness, and it is the escalation path if the fidelity statement's wrong-answer corners start biting.
- **Retain the determinism gate alongside simulation**: rejected, and for a sharper reason than over-engineering. Two mechanisms answering the same question is the exact hazard `evaluability.ts`'s own header exists to prevent — LT-043 collapsed three copies of the rule into one because "a divergence between the copies would be a wrong COMPONENT, not a wrong error message." A static gate beside an executing one is that divergence reintroduced, with the executing one always right. Separately, the fold/refuse taxonomy the gate serves dissolves, and baking `Date.now()`'s build answer is the strictly better no-JS fallback per the owner trade above.

## Consequences

**Good:**

- The authored thunk is always the executed truth: no reshape, no expose mandate, no per-idiom grammar. The evaluability machinery (`isServerEvaluable`, `hostDerivedFold`, `spliceHostDerivedFold`, the fold-set routes) becomes deletable, and the `TSRX005` server-only-names class vanishes.
- The riskiest hand-rolled surface — custom element upgrade machinery and IDL reflection — is jsdom's spec-faithful code, not ours; the driver shrinks to import, register, instantiate, serialize.
- Cross-component initial state: a composing parent's connect-time reads see its children's defined reactive state, so composed renders stop being independent string splices.
- The no-JS story improves: every thunk renders its best server answer instead of being omitted.
- **Element references stop being an unprovable claim.** ADR 0024 s11 checks `first()` selectors *structurally* against the owned template and is deliberately weak by design — "the template proves what a component RENDERS; it never proves what the component will FIND." Under simulation the selectors are **executed** against the actually rendered markup, so ref drift — the disease ADR 0024 opens with, of which `first()` failures were only the symptom — becomes build-caught by construction. This is worth at least as much as the fold deletion.
- **The whole silent-empty-render class dissolves, not just LT-143.** A `{host.<prop>}` text child renders empty today with zero diagnostics (LT-144); under simulation the markup emits the empty span and `bindText` fills it at connect. LT-145 (a Parser-exposed prop with no server arg) resolves the same way, by running the Parser. This is the LT-092 class the data account exists to prevent, retired by mechanism instead of by a diagnostic that was about to be built.
- Goldens police behavior rather than two hand-shaped modules — though the two emit paths remain (sub-design 1): what unifies is the *evaluation*, not the artifact count.
- jsdom is build-time tooling only — nothing ships to clients, and the library boundary of ADR 0024 s7 (browser-only `@zeix/le-truc`, no SSR layer in the library) holds.
- **One sanitizer becomes possible for the first time.** `sanitize-html` was never a production dependency — `configureHtmlSanitizer` is called only from `server/tests/tsrx/features.test.ts`, so the docs build renders `truc:html` through the escape-all default (`runtime.ts:335`) — and it was chosen only because no DOM existed server-side. With jsdom in the build, DOMPurify's documented Node path (`createDOMPurify(new JSDOM('').window)`) serves both channels, retiring a real divergence: two sanitizers with different allowlists mean a value that survives the server's can be altered by the client's at connect, as a `truc:html` hydration diff. ADR [0010](0010-trusted-types-support-via-sanitize-hook.md)'s policy is untouched — the library still ships no sanitizer and the consumer still supplies the hook; this is about what the compiler runtime is configured with, and what we recommend. Substrate consequence in Alternatives; verification in LT-152.

**Bad / accepted tradeoffs:**

- The server executes arbitrary authored code at build time inside a full DOM — an extension of today's IIFE evaluation, now with element access; the driver's stub posture is product surface.
- jsdom's failure modes are **silent by default** where the hand-rolled design refused loudly: layout reads return zeros, absent APIs are `undefined`. A wrong initial value ships (client corrects — flash) unless a fixture catches it; the fixture-pinned corpus is load-bearing, and the virtualConsole is the diagnostic channel rather than throw-reasons.
- jsdom is a heavy dependency tree, and "slower per render than string pushes" understates it: instantiate-and-connect through a full DOM plus the reactive graph is a different order of cost, not a margin, across ~3,700 component tag occurrences in the docs sources. LT-152 must produce the number, not the adjective. Note the second-order cost: today's pure-function render is memoizable on `(component, args)` for free, and a shared document takes that away — an argument for keeping renders as isolated as the substrate permits (sub-design 10).
- **Simulation deliberately runs a code path no shipping browser runs.** Normalizing `attachInternals()` to throw (sub-design 2a) puts every component on the Safari<16.4 degradation branch — `internals` is null (`component.ts:322`), and every `bindAria(internals, …)` handler becomes a no-op (`bindings.ts:345`). Nothing wrong ships, but the served HTML is the *degraded* branch's output, so anything expressible only through internals renders as nothing — permanently, not merely deferred. With ADR [0026](0026-aria-reflection-via-elementinternals-and-bindaria.md)'s LT-148 routing host ARIA to internals, host ARIA server-renders empty; that is consistent (0026 deletes it at hydration anyway), but it means "the no-JS story improves" has an internals-shaped hole, and 0026 and this ADR must be read together.
- **The diagnostics loss is structural, not a wording problem.** Today the compiler refuses and names the author's mistake; after, a wrong answer ships quietly. Fixture-pinning is necessary but is not a channel. The driver therefore treats any `virtualConsole` `jsdomError`, unhandled rejection, or contained per-component throw during connect as a **build warning attributed to that component**, under a baseline — the corpus reaches zero warnings under LT-146, so the baseline is free and any regression is loud. That restores refusal-as-diagnostic without the hand-rolled shim's throw-on-unknown.
- jsdom gaps need driver answers as components reach them: `matchMedia`/`IntersectionObserver`/rAF stubs now, `ElementInternals.states` whenever internals-dependent rendering lands (ADR 0026's LT-147/LT-148).
- Existing server-side diagnostics (`TSRX005`, `TSRX034` wording, `TSRX039`'s server half) and the warning baseline need re-grounding in the new mechanism — inventoried before task planning reopens (LT-143/LT-144 reshaping deferred).
