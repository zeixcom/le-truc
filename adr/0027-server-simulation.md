# ADR 0027: Server Simulation — Render Initial HTML by Executing the Client Module

## Status

✅ Accepted

## Context

The split compiler decided renderability syntactically: an evaluability rule checked a thunk's free names against the render scope, and a fold mechanism spliced `host.<prop>` reads with root-attribute expressions. That grammar has a ceiling — some authored idioms (bare `host` arguments to setup-const helpers, value-passing reshapes, config args that are not exposed props) have no route into the fold set, and the only remedy would be making static connect-time config reactive, colliding with native IDL reflection (e.g. `lang`).

The structural fact that dissolves the dilemma: the generated client factory already runs at connect time against the real upgraded element — Le Truc enhances parsed HTML, it does not client-render — and Cause & Effect is environment-agnostic: a dependency-tracking state graph with arbitrary IO at the leaves. Nothing principled prevents the server from running the same client module the browser runs, against a model of that environment. Existing DOM simulations were evaluated before building one: jsdom covers every load-bearing behavior a spike required, and hand-rolling a smaller DOM would mean maintaining a less complete version of a solved problem.

## Decision

**Server Simulation**: the server renders initial HTML by executing the generated client module against jsdom, letting Cause & Effect evaluate the reactive graph once; the emitted HTML is that graph's initial state. The client remains ground truth and corrects on connect — DOM-is-truth (ADR [0003](0003-attributes-drive-state-at-connect-time-only.md)) and the accepted flash trade (ADR [0024](0024-adopt-tsrx-as-isomorphic-component-format.md) s3, s15) are unchanged.

1. **One evaluation mechanism, not one artifact.** The server render becomes a driver: obtain the component's initial markup, parse it into the simulated document, register the generated client module against a jsdom `customElements`, let the upgrade run, serialize. What retires is the evaluability gate, the fold routes, and the splice machinery, because the client module now computes every initial value by running. Template lowering does not retire: the generated client module contains no markup construction, so it stays server-side. One mechanism now answers "what is this expression's initial value"; the drift class shrinks from two hand-shaped modules to markup vs. selectors — and simulation closes that gap too, by executing the selectors.

2. **The substrate is jsdom — no hand-rolled DOM.** The driver owns one shared jsdom document per build; components are authored `HTMLElement` subclasses extending jsdom's base class, defined children-before-parents so upgrade order is a driver guarantee rather than an accident of import order. `whenDefined` resolves, `instanceof` is clean, IDL reflection is spec-faithful for free, and connect-time DOM writes land in the serialized `outerHTML`. Driver responsibilities: normalize `attachInternals()` to throw so the library's own graceful-degradation path runs (jsdom's skeletal `ElementInternals` is worse than none); stub absent constructors as no-ops (`ResizeObserver`, `matchMedia`, `IntersectionObserver`, `requestAnimationFrame`); contain per component (a throwing component degrades to plain SSR output and never blocks the build); and close the realm's IO — `fetch` and any other ambient network global is replaced with a no-op that reports at call time and then never settles, so a build can never depend on the network and a fetching component routes to the `@pending` arm rather than `@catch`.

   jsdom was confirmed over happy-dom as the substrate; see Alternatives.

3. **Bindings write the simulated document.** No recording layer: `watch()` installs normally into Cause & Effect, the `bind*` helpers write the jsdom DOM directly, and the driver serializes the tree after the connect pass. There is no diffing and no client-side VDOM — the simulation document *is* the intermediate representation.

4. **Simulated connect.** jsdom supplies upgrade order natively; the driver additionally honors the library's own child-await (`customElements.whenDefined`), so a parent's connect-time reads of child state never error — the same dependency-resolution semantics as the browser (REQUIREMENTS M8).

5. **Helper contract under simulation.** `host`: the real simulated element — attribute reads, reflection, and `closest` are jsdom-native. `first`/`all`: real `querySelector(All)` against the component-owned subtree. `expose`: runs as authored, reading attributes seeded from server args through the component's own parsers. `pass`: existing lowering. `on`: no-op. `provideContexts`/`requestContext`: no-op, the consumer holds its fallback signal (the s15 fallback-render precedent). `internals`: deferred — jsdom's `ElementInternals` surface is skeletal and nothing in the corpus renders through internals at connect.

6. **The determinism gate retires.** No AST impure-ambient analysis: a thunk reading `Date.now()` folds to the build machine's answer — a server-defined value beats omission for the no-JS worst case, and the client corrects instantly otherwise. Queries the server genuinely cannot answer resolve to jsdom's best effort or to silent defaults, and the client corrects. The simulation models the rendered fragment and nothing beyond it — layout reads (`getBoundingClientRect`) return silent zeros; the fixture-pinned corpus exists so such drift is caught, not assumed absent.

7. **Staged rollout.** Stage 1: driver + jsdom substrate for `host` reads and reactive attributes, including sub-design 8's fixed-point gate — the gate is what makes stage 1 safe to ship, not a later refinement. Stage 2: ref resolution and composition against the simulated tree. Stage 3: full driver-based rendering, retiring the hand-shaped render functions. These are capability stages, not contract stages.

8. **Connect must be a fixed point, and the driver proves it.** Today's served HTML is pre-connect by construction; under simulation it is post-connect, and the browser then runs connect again over the simulation's own output. Nothing in the library or the compiler previously required enhancement to be idempotent over what enhancement produced — that invariant is now load-bearing. **Rule:** the driver runs the connect pass twice and requires byte-identical `outerHTML`; a component whose second pass differs is a build error, reported against that component.

9. **The arm that ships is a compiler decision; the serialization boundary is hermetic quiescence.** A strictly synchronous window is incorrect for composition: dependency resolution defers effect activation by a microtask whenever a component queries a custom child, so a composing parent's effects have not run when a synchronous window ends. **Rule:** the window performs no driver IO and advances no timer; it drains the realm's microtask queue to a bounded quiescence and then serializes. Exhausting the bound is a `non-quiescent` build warning attributed to the component, not a hang. The drain is safe only because the realm is hermetic (sub-design 2's closed network): a rejecting stub would route every fetching component to `@catch`; a never-settling one keeps it at `@pending`, which is the correct SSG behavior. The hazard to avoid is not a resolved arm in the HTML — it is a resolved arm contradicted by an unseeded client task, which reads as `nil` and regresses to the loading arm on the client. **Rule:** ship the resolved arm only when the resolved value is harvestable from the markup the component itself rendered (seeding the client task from that markup); otherwise ship `@pending`. Either way the compiler makes the choice, and the closed realm ensures no IO can settle a task inside the window to override it. A resolution phase *before* the simulation may still await deliberately for build-time data dependencies — the hermetic boundary applies only to the instantiate→serialize window, not the whole build.

10. **Renders stay isolated enough to be a function of their args.** A generated client registers its element as an import side effect, so a module can be registered exactly once per process — a driver that re-imports per render silently gets no definitions and plain un-upgraded SSR markup on every render after the first. The driver therefore loads each component once and renders it many times against that single shared registry, with disposal deferred to end-of-process. Under that shared-registry constraint, renders remain a pure function of `(component, args)` for caching purposes: the corpus renders in different orders and reproduces identical per-tag output, and repeat renders of the same component are byte-stable.

## Alternatives Considered

- **A hand-rolled virtual DOM shim** (lazy Proxy elements, virtual `customElements` registry, a spec-derived reflection table, throw-on-unknown reads): rejected. The registry would re-implement upgrade ordering and `whenDefined`, the reflection table would be a less complete duplicate of a spec fact, and throw-on-unknown buys refusal-as-diagnostic at the price of hand-implementing everything the table doesn't answer — maintaining a less complete, simpler version of a solved problem.
- **happy-dom / linkedom as the substrate**: linkedom lacks custom elements and is disqualified outright. happy-dom is disqualified as a fallback because DOMPurify fails open on it — hostile payloads (`<script>`, `on*` handlers, `javascript:`) pass through untouched where jsdom strips them — which would force two sanitizers with divergent allowlists. happy-dom is faster per render, but that gap is not build-blocking and is not worth two sanitizers.
- **Widen the splice grammar** (exempt more free-name forms, add fold routes for self-mirrored config args): rejected — every new idiom needs its own proof rule, the grammar grows per expression form, and it perpetuates the two-module drift that simulation eliminates outright.
- **Expose config props** (make connect-time config like `lang`/`ordinal` reactive so it enters the fold set): rejected — reactivity is machinery, not semantics, for connect-time config; some names collide with native IDL reflection; and a compiler limitation must not dictate a component's public contract.
- **Transplant server args into client scope** (emit arg bindings directly into the client module): rejected — invents a channel for values that already have a client home on the element's own attributes.
- **A real browser as the substrate** (e.g. Playwright): the maximal-fidelity option — it answers every gap jsdom leaves (real internals, layout, `matchMedia`, canvas), and executes the same code path the shipped page takes. Rejected on cost and shape: a browser process per build is orders of magnitude slower than an in-process document across a corpus this size, with orchestration overhead the jsdom driver doesn't need. Revisit if the stub posture stops being containable.
- **Retain the determinism gate alongside simulation**: rejected. Two mechanisms answering the same question is exactly the hazard the original gate's own design existed to prevent — a static gate beside an executing one reintroduces divergence, with the executing one always right. The fold/refuse taxonomy the gate served dissolves under simulation, and baking `Date.now()`'s build-time answer is the strictly better no-JS fallback.

## Consequences

**Good:**

- The authored thunk is always the executed truth: no reshape, no expose mandate, no per-idiom grammar. The evaluability machinery becomes deletable.
- The riskiest hand-rolled surface — custom element upgrade machinery and IDL reflection — is jsdom's spec-faithful code, not ours; the driver shrinks to import, register, instantiate, serialize.
- Cross-component initial state: a composing parent's connect-time reads see its children's defined reactive state, so composed renders stop being independent string splices.
- The no-JS story improves: every thunk renders its best server answer instead of being omitted.
- Element references stop being an unprovable claim: selectors are executed against the actually rendered markup rather than checked only structurally against the owned template, so ref drift becomes build-caught by construction.
- The whole silent-empty-render class dissolves, not just one grammar gap: content that previously rendered empty with no diagnostics now emits real markup, because the driver runs the same parser and binding code the browser does.
- Goldens police behavior rather than two hand-shaped modules — the emit paths for template and client logic remain separate, but what unifies is the evaluation, not the artifact count.
- jsdom is build-time tooling only — nothing ships to clients, and the library's browser-only boundary (ADR [0024](0024-adopt-tsrx-as-isomorphic-component-format.md) s7) holds.
- One sanitizer becomes possible for the first time: with jsdom in the build, DOMPurify's Node path can serve both server and client sanitization, retiring a real divergence where two sanitizers with different allowlists could disagree on a `truc:html` value at connect. ADR [0010](0010-trusted-types-support-via-sanitize-hook.md)'s policy is untouched — the library still ships no sanitizer and the consumer still supplies the hook.

**Bad / accepted tradeoffs:**

- The server executes arbitrary authored code at build time inside a full DOM — an extension of prior server evaluation, now with element access; the driver's stub posture is product surface.
- The window is quiescent, not instantaneous, which is a genuinely weaker guarantee than a synchronous window — accepted in exchange for composition rendering at all.
- jsdom's failure modes are silent by default where a hand-rolled design would refuse loudly: layout reads return zeros, absent APIs are `undefined`. A wrong initial value ships (and the client corrects) unless a fixture catches it — the fixture-pinned corpus is load-bearing, and the DOM's own error channel is the diagnostic surface rather than throw-reasons.
- Build cost increases from simulating and connecting every component occurrence. The increase is contained per the current staged rollout and mitigated by `(component, args)` memoization, which measurement shows is highly effective against a shared registry; it is not eliminated, and the cost should be re-measured as later stages widen the driver's scope.
- Simulation deliberately runs a code path no shipping browser runs: normalizing `attachInternals()` to throw puts every component on the same degradation branch as browsers without `ElementInternals` support, so anything expressible only through internals renders as nothing in the served HTML — permanently, not merely deferred, until internals support is added to the driver (see ADR [0026](0026-aria-reflection-via-elementinternals-and-bindaria.md)).
- The diagnostics loss is structural, not cosmetic: where prior server evaluation refused and named the author's mistake, simulation ships a wrong answer quietly unless caught by a fixture. The driver treats DOM errors and contained per-component throws during connect as build warnings attributed to that component, which restores refusal-as-diagnostic without a hand-rolled shim's throw-on-unknown.
- jsdom gaps need driver answers as components reach them (e.g. `matchMedia`/`IntersectionObserver`/rAF stubs now, `ElementInternals.states` whenever internals-dependent rendering lands).
- Existing server-side diagnostics tied to the retired evaluability mechanism need re-grounding in the new one.
