# ADR 0032: Adopt `.tsx` as the Primary Authored Component Surface (`.tsrx` Retained)

## Status

✅ Accepted — spike verdict **GO** (LT-183, `spike/tsx/FINDINGS.md`); owner acceptance 2026-09-17, carrying the dual-front-end amendment recorded the same day: `.tsrx` is not deleted.

## Context

ADR [0024](0024-adopt-tsrx-as-isomorphic-component-format.md) adopted `.tsrx` — a bespoke grammar on pinned `@tsrx/core` 0.1.x — as the authoring surface for the isomorphic single-file format. The 2026-09-06 architecture review split that compiler into **machinery** (tiered server evaluation, harvest, analysis, emitters, simulation — format-independent, ~10k of ~17k lines) and **surface** (the grammar, its parser pin, and everything the grammar's JSX-adjacency costs: the TSRX021–024 React near-miss family, the `className`/`htmlFor` rename table, broken editor support, span tables + emit-then-check remapping so `tsc` can check authored code at all). The LT-183 spike (TSX_SPIKE.md) re-targeted the front end onto the `typescript` package's own parser (`ScriptKind.TSX`) and measured parity: all four ported components render **byte-identical** server output and CSS through the unmodified machinery; the corpus's two Simulated-tier components match through the unmodified `sim/` realm; a deliberate compose-site type error is reported by plain `tsc` **on the authored parent file**; both hard control-flow shapes (async boundary, statement arms/loops) have workable spellings through the unmodified analysis. REQUIREMENTS [§5](../REQUIREMENTS.md#5-technical-constraints) (no client-side rendering, no SSR in the library) and [§7](../REQUIREMENTS.md#7-out-of-scope) are untouched: this is an authoring-surface decision; every shipped library contract and the whole machinery layer are identical.

The owner's acceptance modifies the spike's default GO shape (full switch): **keep the door for TSRX open** — its statement-context control flow is more natural to author than ternary/IIFE shapes — while `.tsx` delivers a mature, well-understood format for v3 without waiting for TSRX 1.0 on a still-evolving 0.x grammar. The result is a **dual front end**.

## Decision

Adopt standard **`.tsx`** as the **primary** authored component surface — parsed by the repo's `typescript` dependency (^6.0.3) via `ts.createSourceFile(..., ScriptKind.TSX)` and lowered through a small TS→estree converter so every downstream stage (`ComponentIR` consumers: `analysis/*`, both emitters, `tier.ts`, `sim/`) is reused **unmodified** — and **retain `.tsrx` as a supported authoring surface**: one machinery layer, two front ends, one registry. Sub-designs (superseding ADR 0024's surface sub-designs **1, 4, 6, 14** and amending **16** *for `.tsx`-authored components*; the `.tsrx` sub-designs remain in force for `.tsrx` sources; 0024's 3, 5, 7–13, 15 carry over unchanged for both):

1. **Module shape.** One exported component function per file: its single destructured parameter is the server args (types flow to compose sites for free — see 3); statements before the single `return` are the setup (the `@{ }` block's replacement); the returned JSX — bare root element or fragment — is the template; a `<style>` sibling inside the fragment carries the CSS as a **template-literal child** (`<style>{`…`}</style>`): JSX text cannot contain raw CSS braces. `export const i18n` / `export const config` / type declarations / `declare global` carry over unchanged. The `{count}` attribute shorthand spells `count={count}` (identical server-attr IR).

2. **Control flow as expressions (§5 of TSX_SPIKE.md, proven).** `{c ? <a/> : <b/>}` / `{c && <a/>}` → `if`; `{xs.map((x, i) => …)}` → `for` (over server data `each()`, over a declared `createList` the `reconcile()` path — the dual lowering stays the analysis's decision, keyed by iterable type, not spelling; the `key k` clause retires, keyed by the list's own `keyConfig`); `@switch` → an IIFE around a statement `switch` returning JSX per arm; the plain error boundary → a try/catch IIFE; the async boundary → the recognized ambient `boundary({ ok, pending, err })` call — all three arms render, which ships stays the compiler decision it was. **Statement-context arms and bare `client-stmt` inside a branch are unexpressible in `.tsx`** (0024 s11 already restricted them) — statements live in setup. This is the ergonomic boundary the dual ruling exists to soften: where these shapes read better as statements, author `.tsrx`.

3. **Authored sources are type-checked directly; the span-table detour retires for `.tsx` authored code.** The spike tsconfig sets `jsx: preserve` (authored files are never emitted by `tsc`; generated modules keep their own check path for generated-code diagnostics). TS 6 type-checks namespaced JSX attribute names per element, so `truc:pass` / `truc:case` / `truc:case-type` survive verbatim AND become type-checkable: the ambient `JSX.IntrinsicElements` host profile declares the light-DOM surface per element (`class`/`for`, function-valued thunk overloads — `className`/`htmlFor` simply have no entry, so the React prior produces a plain tsc error; the TSRX021–024 family stays in force for `.tsrx` only). A composed child declares its compiler-consumed pass surface on its args type (`'truc:pass'?: { filter?: () => string }`) so a parent's `truc:pass={{ … }}` checks against the child's real shape; compose type errors surface on the authored parent (pinned by the spike's negative test). Span tables + remapping survive for **generated** modules and for **`.tsrx` authored code**.

4. **Parser boundary.** `typescript` joins `@tsrx/core` as the second front end's parser: `core.ts`, `core-shim.d.ts`, `newerGrammarHint`, and pin-upgrade reviews are **retained** for the `.tsrx` front end (deferred, not deleted — see 6). The `.tsx` front end keeps one-module boundary discipline (the converter is the only `typescript`-API leaf; oxc-parser stays a future swap behind it — rejected now for recreating the pinned-0.x-parser situation). No Babel anywhere: the transform is source-to-source, emitting the same artifact classes as today; JSX semantics never execute.

5. **Machinery boundary (the spike's thesis, now evidence).** `server/tsrx/`'s `analysis/*`, `emit-server.ts`, `emit-client.ts`, `runtime.ts`, `sim/*`, `evaluability.ts`, `reactivity.ts`, `tier.ts`, `first-refs.ts`, and `imports.ts` are reused **byte-identical** — the spike changed zero lines there. ADR 0024 s2's packaging gate ("no separate package before TSRX reaches 1.0") dissolves: the standalone core ships with no upstream dependency on the `.tsx` path; a Vite adapter comes at packaging time (Bun stays primary; adapters are thin and last).

6. **The dual front end (owner ruling, 2026-09-17).** Both surfaces are first-class inputs to the same machinery: the corpus scan globs `.tsrx` AND `.tsx` into one registry, and a tag declared by two sources fails the corpus compile naming both files (**channel: compiler, tier 1 Prevented** — statically decidable, no runtime half exists). `.tsx` is the **default for new authoring** (editors work through tsserver, authored code is checked directly by `tsc`, no upstream parser pin); `.tsrx` **remains a supported authoring surface** where its statement-context control flow (`@if`/`@for`/`@try`) is the better ergonomics, and the upstream TSRX bet stays live. The parity suite (`server/tests/tsrx-tsx/parity.test.ts`) is the standing **equivalence contract**: the same component authored in both surfaces must render byte-identically — the mechanical form of "the door stays open", and the guard against front-end drift alongside the shared extraction modules (the production merge extracts the setup-extraction loop and element/children lowering shared by both front ends, deleting the spike's ~950 copied lines). The surface set is **closed** — no third surface. Stated honestly, the ruling **defers rather than deletes** the `.tsrx`-specific costs: the `@tsrx/core` pin + shim, the TSRX018/020/021–024 families, `REACT_ATTR_RENAMES`, span tables for `.tsrx` authored code, and pin-upgrade reviews remain while `.tsrx` lives, and every new front-end capability must be expressed and paid for in both surfaces. In exchange: the forced migration of the 22 `.tsrx` corpus components is **cancelled** (the codemod becomes an optional consolidation pass), and the two parser dependencies isolate each other's churn — a `typescript` major's AST drift cannot break `.tsrx`, and `@tsrx/core` 0.x churn cannot break `.tsx`.

**The capability rule's first test, and its exception mechanism (LT-205, ruled 2026-09-17).** The four-arm `boundary({ ok, nil, err, stale? })` cannot be paid for in both surfaces: upstream's async boundary is exactly three arms — the try body, `@catch`, `@pending` — and no stale-arm construct exists in any published `@tsrx/core` through 0.2.3 (verified 2026-09-17 against the registry, the AST type vocabulary, and the draft specification). The ruling: `boundary()` stays `.tsx`-only vocabulary; the `.tsrx` surface keeps its three arms — a `.tsrx` author who needs the stale arm authors `.tsx` or accepts the three-arm fallback. Le Truc introduces **no host-invented construct** to bridge the gap (owner directive: no syntax unavailable to other TSRX hosts). So the capability rule carries a stated exception: a capability lands in one surface only when the other's grammar cannot express it, and the gap re-opens when upstream grows the construct — caught at the next pin-upgrade review. The pin stays at 0.1.63: nothing in 0.1.64–0.2.3 bears on this gap, and 0.2.x's headline (scoped styles and theme machinery) cuts against this host's unscoped-light-DOM profile decision.

**Measured ledger (LT-183).** New `.tsx` front end: 3,335 lines — 747-line TS→estree converter (new; work the pinned parser used to do upstream), ~950 verbatim-copied from `compiler.ts`/`lower-template.ts` (a production merge extracts the shared setup-extraction loop and element lowering into shared modules, deleting the copies → projected ≈2.4k), ~430 adapted, plus the 104-line host profile. Under the dual ruling this **adds** to the `.tsrx` front end's ~3.4k direct lines + ~2k tooling/diagnostic surface rather than replacing them; the deferred-deletion column of the spike plan (~5.4k) becomes reclaimable if `.tsrx` is ever retired.

## Alternatives Considered

- **Full switch to `.tsx` (delete `.tsrx`)** — the spike's default GO shape: sheds the pin, the near-miss families, and the `.tsrx` span tables immediately, at the price of a forced 22-component codemod. **Rejected by the owner (2026-09-17):** the grammar's statement-context control flow is more natural to author, the upstream TSRX bet is worth keeping alive, and the proven IR seam makes retention cheap — the parity suite plus shared front-end modules bound the drift risk.
- **Keep `.tsrx` only** (the NO-GO path): retains the upstream-parser bet and the near-miss diagnostics; forfeits direct tsc checking of authored sources and working editors. The spike now has counter-evidence on every claimed cost of switching.
- **oxc-parser** instead of `typescript`: fast, but 0.x with an evolving API — recreates the pinned-parser boundary problem ADR 0024 just paid to contain.
- **Babel transform**: structurally avoided (§2.3 of the spike): the concern was buying a transform step that does not fit server-rendered HTML; the chosen pipeline changes no artifact classes.

## Consequences

**Good:** editors work through plain tsserver for `.tsx` (LT-014 retires as moot); the React JSX prior becomes *correct* instead of diagnosed on `.tsx`; compose type-flow runs through real parameter types with errors on the authored file; the `.tsx` front end has no upstream dependency at all; attribute/internationalization/reactivity semantics and every shipped contract are unchanged (byte-identical renders proven across all three tiers' mechanisms); **no forced corpus migration** — the 22 `.tsrx` components stay as they are, green and pinned by the parity suite's goldens; the two parser dependencies isolate each other's churn; TSRX's authoring ergonomics and the upstream format bet survive; "the door stays open" is a mechanical contract (parity + shared modules), not a promise.

**Bad:** every new front-end capability is built and paid twice (both surfaces must express it — the imports filter widening is the first concrete instance); the `.tsrx`-specific costs are retained, not deleted (the `@tsrx/core` pin + shim + `newerGrammarHint`, TSRX018/020/021–024, `REACT_ATTR_RENAMES`, `.tsrx` authored-code span tables, pin-upgrade reviews); two parser dependencies to track (`typescript` majors AND `@tsrx/core` 0.x); the corpus is permanently mixed-surface and every "which surface?" answer needs the default rule (`.tsx` unless statement-context control flow argues otherwise); on `.tsx`, grammar-native statement arms are gone (ternaries/`&&`/IIFEs instead — the ergonomics loss the dual ruling accepts for `.tsx`-authored components), `boundary({ … })` is host vocabulary an author must learn, CSS requires template-literal wrapping inside `<style>`, and the `{count}` shorthand is gone; the converter must track `typescript`-major AST drift (`IfStatement.thenStatement`, `isSequenceExpression`/`isAssignmentExpression`/`isJsxMemberExpression` dropped from the d.ts) — the same discipline the old pin had, at a slower-moving target.
