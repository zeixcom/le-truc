# ADR 0032: Adopt `.tsx` as the Primary Authored Component Surface (`.tsrx` Retained)

## Status

✅ Accepted — spike verdict **GO** (LT-183, [spike findings](archive/0032-spike-findings.md)); owner acceptance 2026-09-17, carrying the dual-front-end amendment recorded the same day: `.tsrx` is not deleted. Amended in place 2026-09-18 (LT-208/209/211, owner rulings): the boundary is three-arm in both surfaces with the reactive `isPending` idiom beside it, and the authored `.tsx` factory context is typed by an annotated second parameter. Amended 2026-09-21 (LT-238, owner ruling): sub-design 6's one-source-per-tag rule is relaxed to canonical-plus-variants — [ADR 0039](0039-canonical-plus-variants-authored-surfaces.md).

## Context

ADR [0024](0024-adopt-tsrx-as-isomorphic-component-format.md) adopted `.tsrx` — a bespoke grammar on pinned `@tsrx/core` 0.1.x — as the authoring surface for the isomorphic single-file format. The 2026-09-06 architecture review split that compiler into **machinery** (tiered server evaluation, harvest, analysis, emitters, simulation — format-independent, ~10k of ~17k lines) and **surface** (the grammar, its parser pin, and everything the grammar's JSX-adjacency costs: the TSRX021–024 React near-miss family, the `className`/`htmlFor` rename table, broken editor support, span tables + emit-then-check remapping so `tsc` can check authored code at all). The LT-183 spike re-targeted the front end onto the `typescript` package's own parser (`ScriptKind.TSX`) and measured parity: all four ported components render **byte-identical** server output and CSS through the unmodified machinery; the corpus's two Simulated-tier components match through the unmodified `sim/` realm; a deliberate compose-site type error is reported by plain `tsc` **on the authored parent file**; both hard control-flow shapes (async boundary, statement arms/loops) have workable spellings through the unmodified analysis. REQUIREMENTS [§5](../REQUIREMENTS.md#5-technical-constraints) (no client-side rendering, no SSR in the library) and [§7](../REQUIREMENTS.md#7-out-of-scope) are untouched: this is an authoring-surface decision; every shipped library contract and the whole machinery layer are identical.

The owner's acceptance modifies the spike's default GO shape (full switch): **keep the door for TSRX open** — its statement-context control flow is more natural to author than ternary/IIFE shapes — while `.tsx` delivers a mature, well-understood format for v3 without waiting for TSRX 1.0 on a still-evolving 0.x grammar. The result is a **dual front end**.

## Decision

Adopt standard **`.tsx`** as the **primary** authored component surface — parsed by the repo's `typescript` dependency (^6.0.3) via `ts.createSourceFile(..., ScriptKind.TSX)` and lowered through a small TS→estree converter so every downstream stage (`ComponentIR` consumers: `analysis/*`, both emitters, `tier.ts`, `sim/`) is reused **unmodified** — and **retain `.tsrx` as a supported authoring surface**: one machinery layer, two front ends, one registry. Sub-designs (superseding ADR 0024's surface sub-designs **1, 4, 6, 14** and amending **16** *for `.tsx`-authored components*; the `.tsrx` sub-designs remain in force for `.tsrx` sources; 0024's 3, 5, 7–13, 15 carry over unchanged for both):

1. **Module shape.** One exported component function per file: its single destructured parameter is the server args (types flow to compose sites for free — see 3); statements before the single `return` are the setup (the `@{ }` block's replacement); the returned JSX — bare root element or fragment — is the template; a `<style>` sibling inside the fragment carries the CSS as a **template-literal child** (`<style>{`…`}</style>`): JSX text cannot contain raw CSS braces. `export const i18n` / `export const config` / type declarations / `declare global` carry over unchanged. The `{count}` attribute shorthand spells `count={count}` (identical server-attr IR).

2. **Control flow as expressions (§5 of TSX_SPIKE.md, proven).** `{c ? <a/> : <b/>}` / `{c && <a/>}` → `if`; `{xs.map((x, i) => …)}` → `for` (over server data `each()`, over a declared `createList` the `reconcile()` path — the dual lowering stays the analysis's decision, keyed by iterable type, not spelling; the `key k` clause retires, keyed by the list's own `keyConfig`); `@switch` → an IIFE around a statement `switch` returning JSX per arm; the plain error boundary → a try/catch IIFE; the async boundary → the recognized ambient `boundary({ ok, nil, err })` call — all three arms render, which ships stays the compiler decision it was. **Statement-context arms and bare `client-stmt` inside a branch are unexpressible in `.tsx`** (0024 s11 already restricted them) — statements live in setup. This is the ergonomic boundary the dual ruling exists to soften: where these shapes read better as statements, author `.tsrx`.

3. **Authored sources are type-checked directly; the span-table detour retires for `.tsx` authored code.** The spike tsconfig sets `jsx: preserve` (authored files are never emitted by `tsc`; generated modules keep their own check path for generated-code diagnostics). TS 6 type-checks namespaced JSX attribute names per element, so `truc:pass` / `truc:case` / `truc:case-type` survive verbatim AND become type-checkable: the ambient `JSX.IntrinsicElements` host profile declares the light-DOM surface per element (`class`/`for`, function-valued thunk overloads — `className`/`htmlFor` simply have no entry, so the React prior produces a plain tsc error; the TSRX021–024 family stays in force for `.tsrx` only). A composed child declares its compiler-consumed pass surface on its args type (`'truc:pass'?: { filter?: () => string }`) so a parent's `truc:pass={{ … }}` checks against the child's real shape; compose type errors surface on the authored parent (pinned by the spike's negative test). Span tables + remapping survive for **generated** modules and for **`.tsrx` authored code**. The boundary arms are typed precisely, not `unknown`: a branded `JSX.Element` (an element expression satisfies it by construction; a string or function arm is a tsc error — the generic-`T` and empty-`{}` shapes are recorded as rejected in the task) and `err`'s contextual `Error` parameter, matching cause-effect's wrap-before-dispatch contract (**LT-208**, owner precision ruling 2026-09-17; channel TypeScript, tier 1 Prevented).

   **The factory context is typed by an annotated second parameter (LT-209, owner ruling 2026-09-18).** The authored component function takes a second, destructured, author-annotated context — `, { host, first, expose }: FactoryContext<Props>` (form-associated components annotate `FormFactoryContext<Props>` so `host` carries the managed form members) — because global ambients cannot see a file's type parameters and importing generated artifacts for typing is unwanted (the generated client "may not exist yet"). The annotation makes the WHOLE context P-precise (`watch`/`on`/`pass` prop-key overloads; `expose()` drift against `Initializers<P>` is a free tsc error) and is the wave-4 convention: destructure every factory name you use from the context param. The compiler validates the vocabulary (TSRX049) and the annotation's surface agreement with `config.formAssociated` (TSRX050) — both channel compiler, tier 1. The global ambients remain for the migration period (per-file destructures shadow them at function scope); their fate after migration is explicitly deferred (owner, 2026-09-18). `.tsrx` keeps the ambient vocabulary — no parameter grammar; the asymmetry is designed. `i18n` stays a member of the ARGS destructure, never the context: the generated client has zero i18n (server-render-time data). There are no silent type fallbacks — an unannotated parameter is an implicit-`any` hard error under the strict tsconfigs; omitting the context parameter entirely is the ambient form and stays legal until the deferred ambient retirement.

4. **Parser boundary.** `typescript` joins `@tsrx/core` as the second front end's parser: `core.ts`, `core-shim.d.ts`, `newerGrammarHint`, and pin-upgrade reviews are **retained** for the `.tsrx` front end (deferred, not deleted — see 6). The `.tsx` front end keeps one-module boundary discipline (the converter is the only `typescript`-API leaf; oxc-parser stays a future swap behind it — rejected now for recreating the pinned-0.x-parser situation). No Babel anywhere: the transform is source-to-source, emitting the same artifact classes as today; JSX semantics never execute.

5. **Machinery boundary (the spike's thesis, now evidence).** `server/tsrx/`'s `analysis/*`, `emit-server.ts`, `emit-client.ts`, `runtime.ts`, `sim/*`, `evaluability.ts`, `reactivity.ts`, `tier.ts`, `first-refs.ts`, and `imports.ts` are reused **byte-identical** — the spike changed zero lines there. ADR 0024 s2's packaging gate ("no separate package before TSRX reaches 1.0") dissolves: the standalone core ships with no upstream dependency on the `.tsx` path; a Vite adapter comes at packaging time (Bun stays primary; adapters are thin and last).

6. **The dual front end (owner ruling, 2026-09-17).** Both surfaces are first-class inputs to the same machinery: the corpus scan globs `.tsrx` AND `.tsx` into one registry, and a tag declared by two sources fails the corpus compile naming both files (**channel: compiler, tier 1 Prevented** — statically decidable, no runtime half exists). `.tsx` is the **default for new authoring** (editors work through tsserver, authored code is checked directly by `tsc`, no upstream parser pin); `.tsrx` **remains a supported authoring surface** where its statement-context control flow (`@if`/`@for`/`@try`) is the better ergonomics, and the upstream TSRX bet stays live. The parity suite (`server/tests/tsrx-tsx/parity.test.ts`) is the standing **equivalence contract**: the same component authored in both surfaces must render byte-identically — the mechanical form of "the door stays open", and the guard against front-end drift alongside the shared extraction modules (the production merge extracts the setup-extraction loop and element/children lowering shared by both front ends, deleting the spike's ~950 copied lines). The surface set is **closed** — no third surface. Stated honestly, the ruling **defers rather than deletes** the `.tsrx`-specific costs: the `@tsrx/core` pin + shim, the TSRX018/021–024 families (TSRX020 retired at the LT-210 pin bump — 0.2 dropped lazy destructuring from the grammar, so the parser's own syntax error enforces what the scan used to), `REACT_ATTR_RENAMES`, span tables for `.tsrx` authored code, and pin-upgrade reviews remain while `.tsrx` lives, and every new front-end capability must be expressed and paid for in both surfaces. In exchange: the forced migration of the 22 `.tsrx` corpus components is **cancelled** (the codemod becomes an optional consolidation pass), and the two parser dependencies isolate each other's churn — a `typescript` major's AST drift cannot break `.tsrx`, and `@tsrx/core` 0.x churn cannot break `.tsx`.

**The capability rule's first test, withdrawn by the owner (LT-211, ruled 2026-09-18).** The four-arm `boundary({ ok, nil, err, stale? })` could not be paid for in both surfaces: upstream's async boundary is exactly three arms, and no stale-arm construct exists in any published `@tsrx/core` (verified 2026-09-17 against the registry, the AST type vocabulary, and the draft specification — LT-205 ruled the asymmetry stands, `boundary()` `.tsx`-only). The owner then withdrew the fourth arm outright: the client never re-renders arm content — it toggles `hidden`/`disabled` on server-rendered arms — so a re-fetching-with-retained-value state has **no arm to show**; the idiom for the in-flight state is a reactive `isPending(signal)` read beside the boundary (`class={() => isPending(data) ? 'dimmed' : null}`), which the compiler folds server-side (at build time a task is resolved, rejected, or unsettled) and the generated `watch` re-fires on settle (`isPending` is a real package export, tracked via cause-effect's `pendingSubscribe`). The boundary is **three-arm in both surfaces**, `staleChildren` never existed in `.tsrx`, and the s6 asymmetry LT-205 ruled on evaporates — that ruling stands as history, and no upstream `@stale` construct will ever be needed. The withdrawal also removed two latent defects before they could bite: the emitted `stale: value => …` handler assumed a retained value cause-effect never passes (type AND runtime), and a set `staleText` would have rendered the literal string `"undefined"`. The capability rule and its exception mechanism remain defined for future capabilities; this first instance dissolved rather than set precedent. The pin stayed at 0.1.63 through LT-205 (nothing in 0.1.64–0.2.3 bore on that gap) and moved to **0.2.3** at LT-210 (2026-09-18): the corpus byte-identical, the one casualty being TSRX020's retirement (0.2 dropped lazy destructuring from the grammar outright, so the parser's own syntax error now enforces what the scan used to).

**Measured ledger (LT-183).** New `.tsx` front end: 3,335 lines — 747-line TS→estree converter (new; work the pinned parser used to do upstream), ~950 verbatim-copied from `compiler.ts`/`lower-template.ts` (a production merge extracts the shared setup-extraction loop and element lowering into shared modules, deleting the copies → projected ≈2.4k), ~430 adapted, plus the 104-line host profile. Under the dual ruling this **adds** to the `.tsrx` front end's ~3.4k direct lines + ~2k tooling/diagnostic surface rather than replacing them; the deferred-deletion column of the spike plan (~5.4k) becomes reclaimable if `.tsrx` is ever retired.

## Alternatives Considered

- **Full switch to `.tsx` (delete `.tsrx`)** — the spike's default GO shape: sheds the pin, the near-miss families, and the `.tsrx` span tables immediately, at the price of a forced 22-component codemod. **Rejected by the owner (2026-09-17):** the grammar's statement-context control flow is more natural to author, the upstream TSRX bet is worth keeping alive, and the proven IR seam makes retention cheap — the parity suite plus shared front-end modules bound the drift risk.
- **Keep `.tsrx` only** (the NO-GO path): retains the upstream-parser bet and the near-miss diagnostics; forfeits direct tsc checking of authored sources and working editors. The spike now has counter-evidence on every claimed cost of switching.
- **oxc-parser** instead of `typescript`: fast, but 0.x with an evolving API — recreates the pinned-parser boundary problem ADR 0024 just paid to contain.
- **Babel transform**: structurally avoided (§2.3 of the spike): the concern was buying a transform step that does not fit server-rendered HTML; the chosen pipeline changes no artifact classes.

**[Amended 2026-09-19, owner, at LT-241: the parity contract is repo-internal at v3.0; the published package is TSX-only.** [ADR 0034](0034-distribution-tsx-only-compiler-package-and-template-emission.md) s2 ships only the `.tsx` front end in `@zeix/le-truc-compiler` at v3.0, so publishing `.tsrx` — its format, its pinned pre-1.0 `@tsrx/core` parser, and its `TSRX###` codes as public API — waits for `@tsrx/core` 1.0 and a later 3.x. Nothing in this ADR changes in-repo: `.tsrx` stays a first-class authored surface and the dual-surface parity contract holds unchanged. Decoupling the release from that milestone is the reason the TSX surface was adopted.]

**[Amended 2026-09-19, owner, at the LT-239 follow-up (brainstorming session): front ends are a stated extension point; component-model connectors are third-party.** The boundary this ADR built for two surfaces is the one an arbitrary front end would use, and it is already minimal — a front end is `source → { component, diagnostics, routingSignals }`, handed to `compileFromIR`; both existing front ends are the *same shell* over it (sub-design 6's anti-drift contract). Four positions follow.

*Front ends are pluggable; component models are not the same axis.* Syntax is cheap — the two front ends are 3,731 lines against 16,751 lines of shared machinery, so ~18% of the compiler and ~1,850 lines to add one. A connector for another framework's *semantics* (React, Vue, Solid) is a different undertaking, and it is **third-party by name**: the engineering risk of tracking a target framework's minor versions transfers with ownership, the reputational risk does not, so such connectors must never be presented as first-party support.

*The bet a connector must honour, and its acceptance criterion.* The project's thesis is that what conventionally requires a JSON payload, JS-ified templates and a framework runtime is replaceable by HTML plus a small runtime that addresses elements, harvests initial state from the DOM and applies fine-grained effects. Everything is representable: subtree-shape variance ships as inert `<template>` tags, and state with no DOM home goes in a component-local attribute payload. Neither is a ceiling — the combinatorial case (n independent booleans → 2ⁿ shapes) costs a framework's own approach the same n templates, and the real combinatorial scale is on the data side, which is holes. So the ceiling is not expressive but **economic**, and it is falsifiable: *emitted bytes + the Le Truc runtime, against the target framework's payload + runtime, measured on real components.* A connector whose output approaches what it replaces has failed the bet for that component while technically working. This is the connector-facing analogue of [ADR 0027](0027-server-simulation.md) s2's substrate criterion, and it is measured before any connector is contemplated (LT-266).

*The interface's gap is documentation, not design.* The contract is internal, unversioned, undocumented and unexported. That — not a plugin API, a registry or lifecycle hooks — is the whole deliverable (LT-265). The refusal channel a connector needs already exists: `routingSignals` and the [ADR 0028](0028-tiered-error-surfacing.md) tiers let a front end say "I cannot answer this" and get a designed outcome rather than a silently wrong component.

*A foreign-runtime "Mounted" tier is an escape hatch, recorded and not adopted.* Routing an uncompilable component to static markup with the target framework's own runtime mounted over it (the Astro-islands shape) would ease incremental migration and is a useful measurement baseline. It is **not** a reuse of the refusal channel — Folded/Simulated/Static all emit Le Truc, whereas this is a fourth tier that changes distribution, putting a foreign runtime in the consumer's bundle. As a permanent state it is the worst case: the consumer pays for every framework at once and interoperability degrades. That configuration is common in corporate settings where each team picks its own stack — which is the strongest form of the motive here: **the value is compiling several surfaces away to one runtime, not adding support for each.** Any adoption is a separate decision with its own ADR.]

**[Amended 2026-09-21, owner, at LT-238: sub-design 6's one-source-per-tag rule is relaxed to canonical-plus-variants.** A corpus folder may carry a **variant set** — the hand-written `.ts` twin plus `.tsrx` and `.tsx` spellings, at most one per surface, all declaring one canonical tag — with the served surface build-selected, `.tsx` by default ([ADR 0039](0039-canonical-plus-variants-authored-surfaces.md)). LTC048 narrows rather than retires: it still fails a tag declared by two same-surface sources or by sources that are not a folder-local variant set. The closed two-surface set and the parity suite's standing equivalence contract are unchanged; the example spec joins it as the runtime equivalence contract.]

## Consequences

**Good:** editors work through plain tsserver for `.tsx` (LT-014 retires as moot); the React JSX prior becomes *correct* instead of diagnosed on `.tsx`; compose type-flow runs through real parameter types with errors on the authored file; the `.tsx` front end has no upstream dependency at all; attribute/internationalization/reactivity semantics and every shipped contract are unchanged (byte-identical renders proven across all three tiers' mechanisms); **no forced corpus migration** — the 22 `.tsrx` components stay as they are, green and pinned by the parity suite's goldens; the two parser dependencies isolate each other's churn; TSRX's authoring ergonomics and the upstream format bet survive; "the door stays open" is a mechanical contract (parity + shared modules), not a promise.

**Bad:** every new front-end capability is built and paid twice (both surfaces must express it — the imports filter widening is the first concrete instance); the `.tsrx`-specific costs are retained, not deleted (the `@tsrx/core` pin + shim + `newerGrammarHint`, TSRX018/021–024 — TSRX020 retired at the 0.2 pin bump, `REACT_ATTR_RENAMES`, `.tsrx` authored-code span tables, pin-upgrade reviews); two parser dependencies to track (`typescript` majors AND `@tsrx/core` 0.x); the corpus is permanently mixed-surface and every "which surface?" answer needs the default rule (`.tsx` unless statement-context control flow argues otherwise); on `.tsx`, grammar-native statement arms are gone (ternaries/`&&`/IIFEs instead — the ergonomics loss the dual ruling accepts for `.tsx`-authored components), `boundary({ … })` is host vocabulary an author must learn, CSS requires template-literal wrapping inside `<style>`, and the `{count}` shorthand is gone; the converter must track `typescript`-major AST drift (`IfStatement.thenStatement`, `isSequenceExpression`/`isAssignmentExpression`/`isJsxMemberExpression` dropped from the d.ts) — the same discipline the old pin had, at a slower-moving target.
