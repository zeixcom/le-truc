# ADR 0033: Scope Component Styles by Custom Element Name; Shadow DOM as the Opt-in; TSRX Style Composition Translated to It

## Status

🔄 Proposed — parked as a direction, deliberately not committed. Drafted by the architect during LT-210 (2026-09-18) at the owner's direction to support scoped styles and style composition, "not in the same way as Ripple or Octane"; refined the same day by the owner: scoped styles and TSRX style composition ARE wanted — frictionless parity for TSRX-fluent authors is the goal — but delivery is a [ROADMAP.md](../ROADMAP.md) backlog item, likely 3.1, gated on TSRX 1.0, because `.tsx` (the primary surface) has no such construct and v3 carries no parity debt. The ADR graduates to ✅ Accepted when the project commits to adopting these TSRX features; until then nothing here is scheduled work.

**[Amended 2026-09-19, owner, at the LT-239 follow-up: the CSS side gets a compiler model, and the composition gate narrows.]** Four sub-designs added (7–10). The finding that changes this ADR's shape: the compiler has never parsed the authored stylesheet at all, and once it does — via the `lightningcss` swap already on the table — three separate wants become small (sub-design 7). Two of them are ruled here as valuable: **dead-rule detection** (8) and the **typed custom-property seam** (9). The third is the gate itself: sub-design 6's premise that `.tsx` has no construct for style composition holds only for *standalone* blocks; **assigned blocks and `class={theme.dark}` are ordinary TSX, and they are where the anti-drift property lives** — so the typed-handle half is unblocked from TSRX 1.0 and the generate-CSS half is not (sub-design 10). Status stays 🔄 Proposed: the gate moved, nothing was scheduled.

## Context

Le Truc's host profile has always emitted compiled stylesheets **verbatim, unscoped, light DOM** — a deliberate divergence from Ripple, the one other profile that scopes via generated class hashes (`HOST_PROFILE.md` § Styles are unscoped, light DOM). In its place stands a convention: lead every stylesheet with the component's own tag name. The convention is documented, not enforced — an author who forgets the prefix gets a globally-leaking stylesheet, not a build signal; the profile's open-questions section flags selector-scoping enforcement as unaddressed.

The LT-210 pin upgrade (`@tsrx/core` 0.1.63 → 0.2.3, corpus verified byte-identical) shipped upstream's scoped-styles machinery into reach: scope-hash classes stamped by the client JSX transforms (`transform/jsx/style-scopes.js`, `add_scope_classes`), `prepareStylesheetForRender(sheet, mode)` with three render modes (`scope` / `class-map` / `theme`), `:global(...)` as first-class CSS grammar, `apply={theme}` style composition, and the `TSRX_STYLE_*`/`TSRX_CSS_*` error family. The owner's direction: support scoped styles and style composition — but the two native models, not Ripple's. Both are already taught in [Styling](../docs-src/pages/styling.md): **tag-name nesting** for light DOM (unique by custom-element registry; `>` for direct descendants; proven where one team authors the site's components) and **Shadow DOM via declarative shadow roots** (`<template shadowrootmode="open|closed">`) for native encapsulation.

The question this ADR answers: which of the three scoping models is Le Truc's, what is the escape hatch to unscoped rules when scoping is the default, what does upstream's machinery contribute — and on what schedule the composition part is delivered.

## Decision

**Tag-name nesting is the compiled scoping model; the escape hatch is structural — an unprefixed selector IS a global rule; Shadow DOM is the sanctioned per-component opt-in for true encapsulation; upstream's style-composition PATTERN is the adopted direction for TSRX parity, translated through Le Truc's scoping vocabulary and delivered on the backlog — its hash-class realization is not adopted; the authored stylesheet becomes a parsed compiler artifact, which is what makes selector and type checking possible at all.** Sub-designs:

1. **Tag-name nesting, formalized.** Stylesheets keep emitting verbatim; the taught convention becomes the profile's ruled answer: `my-element { … }` as the outermost selector, `>` where only direct descendants must match. Uniqueness needs no machinery — the custom-element registry guarantees no other component registers the name — and the cascade stays untouched. This is the owner's proven same-team model, already universal in the corpus (all 22 components lead with their tag) and already the documented advice; the ruling makes it the *profile* rather than a habit.

2. **The escape hatch is structural, not grammatical.** Because scoping lives in a convention and not in a transformation, the opt-out is free: a selector that does not lead with the component's tag name is a global rule, full stop — exactly how CSS behaves today. There is no `:global()` to learn, and none is added. Upstream's own answer for genuinely hash-scoped sheets is `:global(...)` wrapping (validated: start or end of a selector sequence only — `TSRX_CSS_GLOBAL_MIDDLE_PLACEMENT_ERROR`; not bare-nested in a pseudoclass), recorded here as upstream's mechanism and as the shape to borrow IF sub-design 5's enforcement ever needs an explicit exemption syntax. Genuinely page-global rules also always have the plain route: a global stylesheet outside the component.

3. **Shadow DOM via declarative shadow root is the opt-in for native encapsulation** — sanctioned as a direction, **not scheduled**. The library already runs shadow-aware: `first()`/`all()`/`query()` are root-relative — `const root = host.shadowRoot ?? host` (`makeElementQueries`, `src/helpers/dom.ts`, since 0.14.0) — event scoping derives the same root, and `dangerouslyBindInnerHTML` even accepts a `shadowRootMode` option that attaches a shadow root and renders into it, so no runtime change gates the door. What is missing is compiler-side only: an authored spelling/config for the shadow mode, and the server render emitting the declarative form — `<template shadowrootmode="open">` wrapping the stylesheet and internals — which is plain markup. The structural notes: composed children stay light-DOM slot content, so the data account (harvest from owned children) is preserved; slotted content is styled by its own component, with `::slotted` the only reach, so theming crosses by custom properties (the docs' token story); context requests dispatch on the host in light DOM, so the CG protocol is unaffected. Shadow-root addressing bugs, if any surface, are ordinary defect tasks, not design debt. A future task amends this ADR when the feature is actually wanted.

4. **Upstream's hash-class scoping is not adopted.** Four reasons: (a) it is a client-transform mechanism — `add_scope_classes` stamps hashes onto JSX `openingElement.attributes` in the React/Solid transforms, and core owns no server-render counterpart ("the platform's runtime compiler owns the real semantics"); Le Truc renders once on the server, so adoption means reimplementing the stamping in `emit-server.ts`. (b) It pollutes every served byte with hash classes — against the library's lean-markup posture. (c) It erodes the compose-site addressing convention: `class`/`id` on a compose site are the documented discriminators (`first('form-spinbutton.lightness')`), and hash soup in the same attribute destroys the readability that convention buys. (d) The genuine isolation demand it serves is the opt-in Shadow DOM's job, where encapsulation is native and free. Consequently the `TSRX_STYLE_STANDALONE_*` diagnostics never fire on this corpus — they run in upstream's full compile pipeline, which this host does not invoke (the bump's byte-identical corpus confirms it). What Le Truc adopts from 0.2 is the authoring PATTERN, not this machinery — sub-design 6.

5. **Enforcement: the prefix graduates from docs to a compiler check.** "Supporting" scoping in the light-DOM model means making the convention hold: the compiler parses the authored stylesheet (upstream exports reusable CSS analysis: `parseStyle`, `analyzeCss`) and **warns when a top-level selector neither leads with the component's tag name nor is an at-rule** — the exact leak the profile's open question described, and the last silently-drifting contract in REQUIREMENTS' v3 criterion ("every markup/selector/style contract error … is a build failure"). **Channel: compiler; tier 2 Contained (ADR 0028 s1) — a warning, not an error, because a deliberately global rule must stay possible (sub-design 2); Tech Writer owns the message copy.** The check also answers the profile's upstream open question for this host: enforcement is host-owned, and this host chooses lint-grade, not refusal. It lands with the package's acceptance (see Status) — not before.

6. **Style composition: upstream's pattern, Le Truc's vocabulary — backlogged.** The composition mechanism TSRX authors know — scoped style blocks composed with style variables, consumed as `class={theme.dark}` — is the adopted direction for this host; frictionless parity for TSRX-fluent authors is a stated goal. What changes is the realization: `class={theme.dark}` translates through OUR scoping vocabulary — `my-element .dark` in light DOM, `:host(.dark)` under a shadow root — never upstream's `tsrx-1a2b3c4d dark` hash classes. The cost is acknowledged, not wished away: CSS must be **generated** from composed variables and scoped style blocks, replacing copy-verbatim for composing components — a machinery step up, and the reason this is not v3 work. Scheduling is a [ROADMAP.md](../ROADMAP.md) backlog item, likely 3.1, taken up when TSRX reaches 1.0: the format is no longer a v3 blocker (`.tsx` is the primary surface and has no such construct), so v3 carries no parity debt. Until it lands, CSS custom properties remain the only composition mechanism — the v3 behavior is exactly today's.

7. **The authored stylesheet is parsed, not merely dedented — the shared prerequisite.** `css.ts` (38 lines) dedents and emits verbatim; the compiler holds no model of the CSS at all, which is why sub-design 5 could only be specified as a *spelling* lint. Sub-designs 8, 9 and 10 each need the same missing thing: the component's own sheet, parsed, with its top-level selectors and declarations reachable from the IR. **`lightningcss` is already a devDependency and already the build's CSS effect** (`server/effects/css.ts`, `server/SERVER.md`), and `COMPILER_REFLECTION.md`'s library table already proposes it as `css.ts`'s replacement; `css-tree`'s `lexer.matchProperty` is the alternative where per-declaration value-grammar diagnostics are wanted rather than a whole-sheet parse failure. **Spec-grammar validation of authored CSS — unknown property, invalid unit, malformed value — rides that swap and gets no task of its own**: it is table stakes every CSS toolchain provides, not a reason to go deeper into styling. **Channel: compiler; tier 1 Prevented (ADR 0028 s1) for a parse or grammar error — the sheet is the compiler's own input and a malformed one has no correct emission; Tech Writer owns the copy.**

8. **Dead-rule detection: selector-uniqueness inference answers "does this rule match anything I render?"** With sub-design 7 in place, the IR can be asked a stronger question than sub-design 5's prefix rule: `matchesSelector` and `countForSelector` (`server/compiler/analysis/selectors.ts`) already decide, structurally, how many elements of the rendered template a given selector matches — they are exported and load-bearing for LT-118's branch-root collision check. **A top-level rule under the component's own tag that matches zero elements is warned on**: a typo, a renamed class, or a rule left stale by a markup refactor — a defect class the prefix rule cannot see. The check must stay conservative, because light-DOM markup is not closed: exempt any subtree holding a compose node or `dangerouslyBindInnerHTML`, exempt `::slotted` and reaches into composed children, and remember that LT-124 widened class matching *deliberately* to serve page-authored enhancement. **Channel: compiler; tier 2 Contained — a warning, for the same reason sub-design 5 is one: an unmatched rule is evidence, not proof; Tech Writer owns the copy.** Sequencing note: `COMPILER_REFLECTION.md` proposes replacing much of `selectors.ts` with `css-select` + `parse5`; if that spike lands this check gets *cheaper* (a real CSS engine answers the question directly), so no bespoke CSS matcher is to be written for it first.

   **Explicit non-goal, recorded so it is not re-litigated:** uniqueness inference does **not** yield collision-free CSS. Collision has two directions, and the IR sees one. *Outward* leakage is already solved by the tag prefix through registry uniqueness — and auto-prefixing a top-level selector needs the tag name and no IR whatsoever. *Inward* capture (the page's own `my-element .foo` reaching a component's internals) is what hash classes buy, and no inference helps, because the colliding rule lives in CSS this compiler never sees. Shadow DOM (sub-design 3) remains the only answer there. What `countForSelector` proves is *intra-template* uniqueness — "this query binds exactly one element in my own subtree" — a different proposition from isolation.

9. **The typed custom-property seam: `@property` derived from both sides of a boundary only this compiler sees.** `bindStyle` (`src/bindings.ts`) takes `string`, so every value crossing from a signal into CSS is stringly-typed at precisely the point where both sides are known at compile time: `infer-type.ts` already carries the signal's value type, and the stylesheet is in the same file. The ruling: **where a signal drives a custom property, the compiler checks the two agree and emits a registration — `@property --lightness { syntax: '<number>'; inherits: false; initial-value: … }`** — which hands enforcement to the browser as well (invalid-at-computed-value-time rather than a silently dead declaration), and brings interpolation and animation along. This is the part no library supplies: `vanilla-extract` is the closest typed CSS-in-TS with composition, and it is the wrong fit for exactly sub-design 4's reason — it reintroduces hash classes and a bundler plugin in order to deliver the type safety; `csstype` types property names and keyword values but leaves every value `string | number`, so it does not know units and does not answer the question. Two constraints stated rather than wished away: (a) `inferType` returns only `string`/`number`/`boolean`/`unknown`, and `<length>` versus `<number>` is exactly the distinction CSS makes and TypeScript does not — so the syntax is to be inferred from the **CSS side**, where the property is consumed (`width: var(--w)` implies `<length>`), which needs no new author-facing types and reuses sub-design 7's parse; (b) **there are no consumers today** — `bindStyle`/`setStyle` appears nowhere in the corpus or the docs components — so by this project's own standard this is a direction, not a task. It is nonetheless the one item here that improves the mechanism v3 *already ships*, since custom properties are today's only composition mechanism (sub-design 6). **Channel: compiler; tier 2 Contained for the TS↔CSS type disagreement, with the emitted `@property` registration carrying the runtime half; Tech Writer owns the copy.**

10. **The composition gate narrows: the anti-drift half is representable in `.tsx` today.** Sub-design 6 parks the whole package behind TSRX 1.0 on the grounds that `.tsx` "has no such construct". That is true of one construct and false of the one carrying the value. Upstream's three pieces separate cleanly: **standalone blocks** — a `<style>` sitting in a children list, scoping its siblings, with raw CSS as *template syntax* — are genuinely TSRX-only (`{`/`}` are expression delimiters in JSX, which is why this host's `.tsx` surface already spells the sheet `<style>{css`…`}</style>`, `compiler-tsx.ts`), and Le Truc wants them least, since one tag-scoped sheet per component leaves sibling-scoping no role. **Assigned blocks** (`const theme = <style>{css`…`}</style>`) and **`apply={theme}` / `class={theme.dark}`** are ordinary TSX: a JSX element bound to a `const`, a JSX attribute, a member expression — upstream's own README records that plain-TSX `<style>{css}</style>` is an ordinary element, i.e. the syntax is shared and only the meaning differs. And the anti-drift property that makes composition worth having lives entirely in the assigned block: the class map is minted by the compiler from the sheet it parsed (`build_style_class_map` — one key per top-scoped class), so `theme.dark` cannot name a class the sheet does not define; a typo is a compile error instead of a silently dead class. **Therefore the work splits in two, and only the second half stays gated.** *Stage 1 — the typed handle:* with sub-design 7's parse, an assigned block becomes a compile-time map over its own sheet's class names, `theme.dark` lowering to the literal `"dark"`. Verbatim emission is untouched, output stays byte-identical, no hashing and no selector rewriting — the whole anti-drift benefit for the price of a parse that sub-designs 8 and 9 already pay. It uses no TSRX construct, so **it does not wait on TSRX 1.0**; the one real surface change is accepting a `<style>` in setup position, since today the sheet must be the root fragment's second child. *Stage 2 — composition proper:* `apply={theme}`, several sheets merged, selectors regenerated into `my-element .dark` / `:host(.dark)`. That is where sub-design 6's "CSS must be generated" cost actually sits, and it stays backlogged on the original terms.

## Alternatives Considered

- **Defer style composition indefinitely (custom properties forever)** — the original draft's posture, reversed by the owner the same day: TSRX-fluent authors would meet a foreign composition pattern in Le Truc, against the frictionless-parity goal. Recorded because the reversal defines this ADR's scope — everything else in the draft stands; only the composition posture changed, from "no mechanism without a corpus need" to "upstream's pattern, translated, on the backlog".
- **Adopt upstream hash-class scoping (Ripple parity)** — rejected per sub-design 4: wrong rendering model (client transform vs server render), served-byte cost, addressing-convention erosion, and redundant with a stronger native opt-in. The pattern is adopted (sub-design 6); the hash classes are not.
- **Shadow DOM as the default** — rejected: it would force slots onto every composition for a benefit only uncontrolled third-party environments need; the light-DOM data account is one of Le Truc's main advantages — and where a component wants encapsulation, it is available today (root-relative queries already support shadow roots).
- **Adopt only the `:global()` grammar** — rejected as redundant while scoping is conventional (unprefixed already means global); revisitable if sub-design 5's enforcement lands and authors ask for an explicit marking syntax.
- **Synthesize collision-free selectors from the IR's uniqueness inference** — rejected per sub-design 8's non-goal: it does not reach the case hash classes exist for (inward capture), and letting synthesized selectors into the *emitted* sheet would end verbatim emission, make the stylesheet break on markup edits the author never touched, and reimport sub-design 4(c)'s readability objection in a new costume. The inference is reused for *verification* (8) and for addressing in generated CSS (10, stage 2), never for minting the served selectors.
- **Adopt `vanilla-extract` for typed styles** — rejected: it is the closest existing typed CSS-in-TS with real composition (`createVar`, `createTheme`, zero-runtime, static `.css` output), and it is wrong here for exactly sub-design 4's reason — it reintroduces hash classes and a bundler plugin in order to deliver the type safety. `csstype` was considered and does not answer the question either: it types property names and keyword values, leaving every value `string | number`, so it does not know units.
- **Treat "type-safe CSS" as one thing** — rejected as a conflation that hid the only part with leverage. Validating authored CSS against the spec grammar is table stakes and rides the `lightningcss` swap (7); typing the *boundary* between a signal and a custom property is the part no library can do, because it needs both sides, which only this compiler sees (9).
- **Status quo (no validation)** — rejected: it is precisely the "documented stand-in" posture; the owner asked for scoping to be supported, and unenforced it remains a habit.

## Consequences

**Good:** zero served-byte cost and byte-identical rendered output for everything that ships in v3 (the convention changes nothing the compiler emits); scoping strength matches the audience — registry-unique names for the same-team corpus, native encapsulation available where pages are hostile; TSRX-fluent authors get their composition pattern back (the direction) while served markup keeps Le Truc's vocabulary — no hash classes either way; upstream's CSS analysis is reusable for the validator without adopting upstream's scoping; parking the whole package as Proposed-backlog keeps v3's scope honest while the direction is on record; parsing the sheet (7) turns three separate wants into one prerequisite already funded by a swap the reflection wanted anyway, and brings spec-grammar validation along free; the dead-rule check (8) converts sub-design 5 from a spelling lint into a check that catches stale rules, reusing machinery already proven on branch-root collisions; the `@property` seam (9) is the rare item that improves the mechanism v3 already ships rather than one it might; and narrowing the gate (10) means the anti-drift benefit — the part the owner values — no longer waits on an upstream 1.0 it never actually depended on.

**Bad:** tag-name nesting is weaker isolation than hashes or shadow — page CSS can still target `my-element .foo`, so cross-team clash risk remains (the docs' existing caveat); when composition lands, CSS generation from composed blocks replaces copy-verbatim for composing components — the largest compiler change in this ADR, unbuilt and unscheduled until the backlog commitment; until then none of upstream's style machinery (`prepareStylesheetForRender`, themes, `apply`) is reused, so 0.2.x's headline stays unreached-for; the declarative shadow-root spelling is unbuilt compiler surface — the runtime is already shadow-aware, so the residual work is the authored shape plus the server emission, taken when a task wants it; sub-designs 8 and 9 both depend on 7, so a stylesheet parse that never lands silently takes all three with it; the dead-rule check has an irreducible false-positive surface because light-DOM markup is not closed — compose sites, `dangerouslyBindInnerHTML` and page-authored enhancement all produce rules that legitimately match nothing in the template, which is why it stays a warning and why an over-eager version would be worse than none; the typed custom-property seam has **zero consumers in the corpus today**, so it is the item most likely to be built for an audience that does not exist — it should follow a real use, not precede one; and stage 1 of sub-design 10 adds a second legal position for `<style>` (setup as well as the root fragment), which is authored-surface drift between the two front ends unless `.tsrx` accepts the same spelling.
