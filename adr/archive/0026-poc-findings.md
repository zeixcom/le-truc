# ADR 0026 — ARIA-Reflection PoC Findings

Historical record of the proof-of-concept behind [ADR 0026](../0026-aria-reflection-via-elementinternals-and-bindaria.md). Each LT task probed one channel of the two-channel policy against its hardest case and recorded what it observed here; this file is the running log the LT-006 decision gate read. It is not documentation of shipped behavior — see the ADR and `examples/test/aria/` for that.

> **Gate outcome (LT-006, 2026-08-31): GO.** ADR 0026 is ✅ Accepted, targeting v3.0. Per-channel verdicts are distilled into the ADR's **PoC validation** section; these raw findings remain the evidence behind it. Three findings changed the ADR rather than merely confirming it: the stale-attribute mitigation (LT-002 finding 4) became an explicit §1 rule and **part of `bindAria()`'s contract**; the signature gained a map form and a documented type constraint (§2 a–b); and LT-005 finding 2 **falsified** the ADR's claim that internals registration restores the nested-element safety net — it restores attribute-validity checking only. LT-004 finding 2 (`watch()`'s array-source form cannot carry `SingleMatchHandlers`) was deliberately kept *out* of ADR 0026 — it is a `watch()` API question, filed separately.
>
> **LT-014 (2026-08-31): the `test/poc/` workspace this file describes has been torn down.** Every finding below that described still-relevant platform/library behavior now has a live Playwright assertion in `examples/test/aria/test-aria.spec.ts` (CDP computed-tree tier, the axe-core registry gate, override/reassert, stale-attribute mitigation, and the `:not(:defined)` element-reference edge case). This file is kept as the evidence trail the LT-006 decision rested on, not as a pointer to working code — the `poc-*`/`test/poc/*` paths named throughout no longer exist.

## Infrastructure (LT-001)

- `serve.ts` — Bun server on **:3100** serving `pages/*.html` and bundling `*.ts` PoC modules on demand (`Bun.build`, `DEV_MODE="true"`, cached by mtime). Deliberately separate from the docs server (port 3000): `examples/` is the published demo surface.
- `fixtures/aria.ts` — three observation tiers:
  1. **`computedAriaTree(page, selector)`** — the engine's own accessibility tree via CDP `Accessibility.getFullAXTree`, sliced to the element's subtree. **Chromium only** (Playwright exposes no computed-tree API for Firefox/WebKit). This is ground truth: what AT consumes.
  2. **`ariaSnapshotOf()` / `getByRole`** — Playwright's injected ARIA engine. All engines, but a *tool's* view of the DOM, not the platform's.
  3. **`runAxe()`** — axe-core ≥ 4.13 in-page, reading ElementInternals through the ElementInternals declaration registry (`globalThis._elementInternals`, populated by the probe).
- Run with: `node node_modules/.bin/playwright test --project=poc-chromium` (or `poc-firefox` / `poc-webkit`).

## ⚠️ Correction (2026-08-31, during LT-002)

LT-001's original baseline wrote `internals.ariaValuenow = '42'` in `poc-basic.ts` — lowercase `n`. The real `ARIAMixin` IDL attribute is **`ariaValueNow`** (capital `N`; likewise `ariaValueMin`, `ariaValueMax`, `ariaValueText`). Since JS objects accept arbitrary property assignment, the mis-cased write silently created an inert data property instead of calling the real setter — no error, no effect on ARIA state. This produced a false negative: the original finding "internals-set `aria-valuenow` does not reach the AX tree" was an artifact of the typo, not a platform gap.

Fixed in `poc-basic.ts`, `poc.spec.ts`, and this file. **Corrected finding**: internals-set `aria-valuenow` (and `aria-valuemin`/`aria-valuemax`/`aria-valuetext`) reach the Chromium AX tree exactly like `role` and `aria-label` do — see the LT-002 findings below, which re-verified this on the harder slider case with the correct property names. `ariaExpanded` and `ariaLabel` were never affected (no casing mismatch possible — single-word suffix). **Lesson for LT-003/LT-004**: the `ariaXxxYyy`-shaped `ARIAMixin` properties (the value-class and element-reference-class ones) are easy to mis-type against the hyphenated attribute name; TypeScript only catches this when the target is typed as `ElementInternals`/`ARIAMixin`, not `any` — keep PoC probes strictly typed.

### The load-bearing discoveries

1. **Chromium maps internals-set `role`, `aria-label`, AND `aria-valuenow` into the AX tree.** All three reach the computed tree identically to their attribute-set equivalents (verified via the corrected `ariaValueNow` property). The internals channel is proven for role, name, *and* live numeric/range state in Chromium — the two-channel policy's "component-owned default semantics on the host" row (ADR 0026 §1) holds for the progressbar case without qualification.
2. **Playwright's tooling tier ignores ElementInternals entirely** — `getByRole('progressbar')` counts only attribute-carrying probes, and `ariaSnapshot` of the internals-only probe is empty, identically on all three engines. Testing-library-style queries cannot see internals semantics; assertions on internals-driven state must go through `computedAriaTree()` (Chromium) or the registry/IDL (all engines). This is the tooling-introspection gap w3c/aria#2663 describes, seen from the test-runner side.
3. **The override/reassert semantics are real** (Chromium, name AND value): a host `aria-label`/`aria-valuenow` attribute beats the internals default, and `removeAttribute` restores the internals value — the platform behavior ADR 0026 §1's consumer-override story rests on. (Also confirmed as a *risk*: stale server-rendered attributes permanently shadow reflection — the no-mixing rule and the LT-002 SSR probe exist because of this.)
4. **axe-core 4.13 + registry produces zero internals-related violations** on the probe page in all three engines — including no `aria-required-attr` complaint for the internals-only progressbar (axe skips internals elements in rules it does not support, rather than false-flagging them). Whether axe *positively* honors internals `role` (the trap test: reflected `role=button` with the native child dropped must be flagged) is LT-005's explicit check; this baseline only proves the pipeline runs silently.
5. Engine-level ground truth for **Firefox/WebKit computed trees is unobservable** through Playwright (no CDP equivalent). Any cross-engine semantics claim beyond the tooling tier needs manual VO/NVDA verification or a dedicated out-of-Playwright harness — recorded as a standing limitation of the PoC.
6. **CDP's `Accessibility.getFullAXTree` does not surface a node's `valuetext` property reliably**, even for pure attribute-set `aria-valuetext` with no internals involved — confirmed as a fixture/tooling artifact, not a channel distinction (see LT-002). Do not read `computedAriaTree().props.valuetext` as ground truth; use the IDL (`internals.ariaValueText`) or the content attribute directly.

## Findings matrix — LT-002 (host default-semantics channel: hue slider)

Hardest case: `internals.role = 'slider'` with all four range properties (`ariaValueMin`/`Max`/`Now`/`Text`) internals-only, reactive at pointermove frequency via `throttle()` — `poc-hue-slider.ts`, modeled on `form-colorgraph`'s real hue slider.

1. **Internals-only fully maps for the slider case.** Role, static bounds (`valuemin`/`valuemax`), and the live `valuenow` all reach the Chromium AX tree correctly (`0`/`360`/`120` for a `setHue(120)` call) — extending finding 1 above from `progressbar` to `slider`, and from static to reactive, throttled updates. There is no engine gap to route around; a mirrored-to-attribute variant tried during development turned out to be solving a problem that didn't exist (see the correction note above) and would have violated the no-mixing rule for nothing. Dropped.
2. **Consumer override and reassert hold for numeric state, not just name/role.** A static `aria-valuenow="270"` attribute wins over the component's internals default (`0`); removing it restores `0`. Same mechanism as LT-001 finding 3, confirmed on the harder continuously-updating case.
3. **No glitching under high-frequency updates.** 50 synchronous `setHue()` calls (simulating a fast pointermove burst) collapse into exactly one throttled flush via cause-effect's `throttle()` (per-animation-frame dedup, M5) — the same primitive `form-colorgraph`'s real drag handlers use. The scheduler-dedup concern in the LT-002 Check criterion is unfounded for this pattern.
4. **The no-mixing wrinkle is real and the mitigation works** (`poc-stale-expanded.ts`): a server-rendered `aria-expanded="false"` attribute permanently shadows a component's runtime `internals.ariaExpanded` reflection — calling `expand()` has zero effect on the computed tree as long as the stale attribute survives. Mitigation confirmed: the component removing its own attribute for the property it manages, on connect and before first reflecting via internals, restores internals authority. **Consequence for ADR 0026 §1**: components that reflect a property via internals and *might* receive a same-named SSR/consumer-authored attribute for that property should proactively `removeAttribute()` it at connect time, or the no-mixing rule is only aspirational — nothing on the platform enforces it. Candidate follow-up for LT-006: should this attribute-drop-on-connect become part of the `bindAria()` contract (LT-004) or stay an author responsibility documented in the policy table? — **Resolved at the LT-006 gate: part of the `bindAria()` contract.** A one-time removal at binding activation, for `ElementInternals` targets only, ordered after parsers: the server-rendered attribute is the initial value, post-connect overrides still win. See ADR 0026 §1.

## Findings matrix — LT-003 (element-reference channel: combobox)

Hardest case: `poc-combobox.ts`, a real Le Truc component (unlike LT-001/LT-002's raw custom elements — the thing under test, `all()`'s reactive Cell retargeting `ariaActiveDescendantElement` per keystroke, is a library integration concern, not a pure-platform one). Wires `ariaControlsElements`, `ariaDescribedByElements`, `ariaLabelledByElements`, `ariaErrorMessageElements` (static) and `ariaActiveDescendantElement` (reactive). `poc-late-ref.ts` isolates the `:not(:defined)` edge case.

1. **All five `aria*Elements` relationships reach the Chromium AX tree — but as `relatedNodes`, not a plain string.** CDP's `Accessibility.getFullAXTree` reports element-reference properties (`idrefList`/`nodeList` types) with an empty `value` string and the actual relationship in a separate `relatedNodes` array (`{ backendDOMNodeId, idref?, text? }` — `idref` present only when the target happens to have an `id`). LT-001/LT-002's `computedAriaTree()` fixture only read the flat string and so would have reported these as invisible — a second false negative of the same shape as the LT-001 `ariaValuenow` typo, caught before it was ever pinned. **Fixed in `fixtures/aria.ts`**: `propValue()` now falls back to `relatedNodes` (`idref` or `#<backendDOMNodeId>`), and `AriaNodeSnapshot` gained a top-level `description` field (see finding 3). Re-verify any LT-004+ fixture reading against the raw CDP shape before trusting a "not visible" result — this is now the second instance of the same failure mode.
2. **`aria-errormessage` only surfaces once the field is marked invalid.** `ariaErrorMessageElements` is wired unconditionally in `poc-combobox.ts`, but `errormessage` is absent from the AX tree's `properties` until `ariaInvalid = 'true'` is also set — an ARIA-spec-level gate, not a channel gap. Any component using `ariaErrorMessageElements` needs `aria-invalid` state management too, or the relationship is wired but silently inert.
3. **The AX-tree shape for a "description" relationship depends on the node's role.** `combobox`/`textbox`-like roles expose `aria-describedby` as a `describedby` entry in `properties` (with `relatedNodes`, per finding 1). A `button`-role node instead exposes it as a top-level computed `description` field, with no `describedby` property at all. Both are the *same* `ariaDescribedByElements` wiring; the AX-tree shape it produces is role-dependent, not something a single `props.describedby` check can uniformly assert across widgets. `computedAriaTree()`'s `description` field (added this task) captures the button-role case.
4. **`:not(:defined)` targets are immune to Le Truc's dependency-timeout system, confirming the ADR 0026 Context's claim.** `poc-late-ref.ts` wires `ariaDescribedByElements` to `<late-target-el>` — a tag no script on the page ever registers — synchronously in its constructor. The relationship is already correct in the AX tree (`description: "a not-yet-defined description"`) with the target still `:not(:defined)`. Unlike `first()`/`all()`, which collect undefined custom-element targets as dependencies and defer effect activation up to `DEPENDENCY_TIMEOUT` (200ms, `src/helpers/dom.ts`) so a child's own exposed properties are ready, an element-reference property only needs the target's identity as a DOM node — nothing here reads the target's class behavior, so there is nothing to wait for.
5. **The spec side effect is real, but "clears" means emptied, not removed.** `poc-combobox.ts`'s textbox starts with a stale `aria-describedby="stale-id"` attribute in the HTML. Assigning `ariaDescribedByElements`/`ariaControlsElements`/`ariaLabelledByElements` via the IDL sets the corresponding content attribute to `''` (present, empty) rather than removing the attribute node — `getAttributeNames()` still lists it. A component switching a property to element-reference wiring can't accidentally leave the attribute channel holding stale content, but authors checking "did this property get set via attributes" need `getAttribute() === ''` semantics, not `hasAttribute()`.
6. **`all()`'s reactive Cell only updates for effects that actually subscribe to it — reading it inside a `watch()` handler body does not.** `watch()` wraps its handler in `untrack()` (`src/helpers/reactive.ts`) precisely so incidental reads don't become accidental dependencies. An early draft of `poc-combobox.ts` called `options.get()` only inside the `watch(activeIndex, ...)` handler body; because that read was untracked, the Cell's `MutationObserver` (lazily activated only by a genuine subscriber) never turned on, and the option list stayed frozen at its first-query snapshot even after DOM removal/re-add. Fix: pass `options` as a `watch()` source directly — `watch([activeIndex, options], ([i, list]) => ...)` — so `all()`'s Cell gets a real tracked reader. This is a library-usage finding (a trap for `bindAria()`/LT-004 to watch for too: any handler that reads a second reactive value only inside its body, rather than declaring it as a source, will silently see stale data), not an ARIA-reflection finding, but it directly gates whether "activedescendant retargeted per keystroke across an `all()`-backed list" (the LT-002/LT-003 Context's own hard-case framing) is even correct.

## Findings matrix — LT-004 (`bindAria()` contract prototype)

`poc-bind-aria.ts` prototypes the ADR 0026 §2 signature (`bindAria(target: ARIAMixin | null | undefined, name: keyof ARIAMixin & string): SingleMatchHandlers<...>`), mirroring `src/bindings.ts`'s existing `bind*` shape (map-form precedent from ADR 0023, `SingleMatchHandlers`, DEV_MODE debug-attribution WeakMap) closely enough that landing the real helper should be "move this file," not "redesign it." Verified by `bind-aria.test.ts` (bun:test, no browser needed — pure logic) and by re-wiring LT-002's `poc-hue-slider.ts` and LT-003's `poc-combobox.ts` through it; the full poc Playwright suite (26 tests, 3 engines) stayed green and stable across repeated runs after the rewire, confirming no behavior change.

1. **`SingleMatchHandlers<T extends {}>`'s generic constraint cannot include `null`/`undefined` in `T`, even though ADR 0026 §2's mapping table explicitly wants `ok(null | undefined) → assigns null`.** `{}` excludes both under `strictNullChecks`; a first draft typed `AriaValue` with `| null | undefined` and got `TS2344: Type 'AriaValue' does not satisfy the constraint '{}'`. Resolved the same way `bindAttribute`'s/`bindStyle`'s existing map-form `ok(map)` already resolves the identical tension for absent keys: the *type* is optimistic (`AriaValue` excludes null/undefined), the *implementation* still guards `value == null` at runtime. This is not just defensive dead code — confirmed against `@zeix/cause-effect`'s `match()` source that `nil` only fires on `UnsetSignalValueError` (pending/unset), never because a resolved signal value happens to be JS `null`; a `Signal<Element | null>` source genuinely reaches `ok(null)`. The real `bindAria()` in `src/bindings.ts` will need the identical split when implemented for real — this is a "prove the signature" catch specifically about *this* helper family's relationship with cause-effect's generic constraint, not an ARIA-specific finding.
2. **The array-source `watch()` form cannot carry `bindAria()` (or any `SingleMatchHandlers`-returning helper) at all — only the string/Signal/thunk single-source overloads accept `SingleMatchHandlers`.** This forced (in a good way) the LT-003 finding-6 fix to be redone as a single tracked *thunk* source — `watch(() => { const i = activeIndex.get(); const list = options.get(); return i >= 0 ? (list[i] ?? null) : null }, bindAria(textbox, 'ariaActiveDescendantElement'))` — instead of the array-source `watch([activeIndex, options], handler)` form the LT-003 fix used. Both fixes are correct (the thunk's reads are tracked in the pure phase, same as the array form's), but only the thunk form composes with `bindAria`. Confirms the LT-003 finding-6 prediction ("a trap for `bindAria()`/LT-004 to watch for too") was right, and resolves it by construction: reaching for `bindAria()` on a multi-signal-derived ARIA property naturally steers toward the thunk form, not the array form.
3. **`bindAria()`'s `SingleMatchHandlers` return value works standalone, invoked imperatively, with no `watch()`/signal graph at all.** `poc-hue-slider.ts` is a raw custom element (LT-002's deliberate choice, to isolate the platform channel from the library) whose reactive state lives in a plain class field behind `throttle()`, not a cause-effect signal — there is no `watch()` source to hand `bindAria` to. Calling `.ok(deg)` / `.ok(text)` directly inside the throttled callback works exactly like calling it through `watch()` would; `SingleMatchHandlers` is just a plain object with `ok`/`nil` functions, nothing about it requires the `match()`/`watch()` machinery. This is useful signal for LT-004's "prove the signature" goal: `bindAria()` composes with imperative call sites too, not only reactive ones — though ADR 0026 §2 is explicit that *static* one-time ARIA (role, bounds) should stay direct `internals.role = 'slider'` assignment, not wrapped in a helper call for its own sake; only the LT-002 slider's reactive `valuenow`/`valuetext` writes were rewired here.
4. **Every mapping-table row is real and independently testable without a browser.** `bind-aria.test.ts` exercises boolean→`'true'`/`'false'`, number→decimal string, string/`Element`/`readonly Element[]` pass-through, `null`/`undefined`→clear, `nil`→clear, and the `target == null` no-op degradation — all against a plain fake object, no DOM. Confirms the helper's core coercion logic is pure and has no hidden DOM dependency beyond the final property assignment.
5. **The debug-attribution split (register `Element` targets, skip `ElementInternals` targets) is a real, testable branch** — proven with a PoC-local mirror of `src/bindings.ts`'s private `debugBindingTargets` WeakMap (not importable from the library; module-private). The real implementation in `src/bindings.ts` will register directly into the existing registry rather than a second one, but the branch condition (`target instanceof Element`) is proven here.
6. **Compile-time pins hold**: `bindAria(internals, 'aria-expanded')` (the content-attribute string, not the IDL property name `ariaExpanded`) and `bindAria(internals, 'textContent')` (not an `ARIAMixin` member at all) both fail to typecheck, confirming `name: keyof ARIAMixin & string` actually constrains the second argument rather than silently widening to `string`. `handlers.ok({...})`/`handlers.ok(Symbol())` also fail, confirming `AriaValue` rejects values outside its union. Verified each pin is load-bearing (not accidentally always-passing) by temporarily removing one `@ts-expect-error` comment and confirming `tsc --noEmit` then reports the expected `TS2345`, before restoring it.

## Findings matrix — LT-005 (ElementInternals declaration registration + axe-core gate)

`poc-truc-registration.ts` prototypes the exact addition ADR 0026 §3 proposes for the real `Truc` constructor: after a successful `attachInternals()`, also `globalThis._elementInternals ??= new WeakMap()` then `.set(this, internals)`, unconditionally — no `DEV_MODE` gate.

1. **The trap is real and reproduces exactly.** `<poc-reg-button-trap>` sets `internals.role = 'button'` (no native `<button>`) plus a content attribute (`aria-checked="true"`) that is invalid for the button role — a consumer/SSR authoring mistake on the *attribute* channel, deliberately independent of the internals wiring (ADR 0026 §1's two channels stay separate even in this adversarial probe). Registered, axe-core 4.13 computes `role: 'button'` via `elementInternals.role` and `aria-allowed-attr` correctly flags `aria-checked`. `<poc-unreg-button-trap>` — byte-for-byte identical `internals.role`/attribute setup, deliberately never calling `registry.set()` — stays silent on the same page, in the same `axe.run()` pass. This is the literal "silent-pass → flagged" flip ADR 0016's original advisory worried about, not a synthetic approximation.
2. **Only a subset of axe-core's role-aware rules can ever see an internals-only role — the rest are gated by a `[role]` *attribute* CSS selector, independent of role computation.** Confirmed empirically (not from axe's docs alone) by reading the compiled rule metadata in `node_modules/axe-core/axe.js`: `aria-required-attr`, `aria-required-parent`, and `aria-required-children` all declare `selector: '[role]'` — an attribute-presence selector that excludes internals-only elements from the rule's element-selection pass *before* role computation (and its `elementInternals` fallback) ever runs. `aria-allowed-attr`/`aria-prohibited-attr` declare no `selector` at all (run on every element, matched via `aria-allowed-attr-matches`), so they are the only reliably internals-visible rules among the four ADR 0026 named as axe's supported subset. An earlier draft of this probe tried the `list`/`listitem` case from that same named subset (`internals.role = 'listitem'` with no `role="list"` ancestor, expecting `aria-required-parent` to flag it) — it stayed silent regardless of registration, exactly because of this selector gate. Dropped in favor of the `aria-allowed-attr` button case, which is verifiably real. **Consequence for LT-006/documentation**: "axe supports this rule subset for internals" (ADR 0026 Context, from axe's own docs) is accurate for what the rules *check*, but `aria-required-parent`/`aria-required-children` cannot act on it in practice — their selector never admits an internals-only element in the first place. Worth a precise footnote wherever this subset is cited.
3. **Registration does not blanket-flag internals-role elements.** `<poc-reg-button-ok>` — identical `internals.role = 'button'` registration, no invalid attribute — stays clean. The flag in finding 1 is specific to the actual violation, not an artifact of merely being registry-visible.
4. **Deleting a registry entry mid-session and re-running axe does *not* reproduce the "before" state — axe-core caches `elementInternals` per DOM node across separate `axe.run()` calls on the same page.** Discovered while building this probe: `registry.delete(el)` followed by a fresh `runAxe()` call still returned the earlier violation, even though `registry.has(el)` was confirmed `false` immediately after the delete. The valid "before" comparison needed a node that was *never* registered in the first place (`<poc-unreg-button-trap>`), not a same-session revert — recorded here so a future LT doesn't waste time on the same dead end.
5. **One WeakMap entry per instance, no leaks across connect/disconnect/reconnect.** Not because of any cleanup logic — because there isn't any to write. `attachInternals()` (and the registration line riding along with it) lives in the constructor, which the custom-element upgrade algorithm calls exactly once per instance, never again on reconnect. A probe instance moved out of and back into the DOM twice (`el.remove()` / re-`appendChild()` × 2) confirms `attachCount === 1` and `registry.get(el)` returns the identical `ElementInternals` object throughout. The real `Truc` constructor already has this shape (`src/component.ts`'s `internalsMap.set(this, this.attachInternals())`, in `constructor()`) — LT-005's registration line is additive to a call site that is already leak-proof by construction, not something that needs its own disconnect-time cleanup.

## LT-013 — manual AT test fixtures + pre-migration baseline

LT-009's manual VoiceOver/NVDA pass needs fixtures that actually exercise the internals-set channel under an AT, not just under Playwright's DOM/CDP inspection. Three gaps found while scoping LT-009, fixed here:

1. **`poc-hue-slider` had no box.** No CSS shipped on `/hue-slider`, so the element rendered at zero size — a zero-area element is a coin flip for AX-tree/AT exposure regardless of what `internals.role`/`aria*` carry. Fixed: `pages/hue-slider.html` now gives `poc-hue-slider` a visible `16rem × 2rem` box with a hue-gradient background.
2. **No keyboard path to trigger reactive updates.** `setHue()`/`expand()`/`collapse()` were only reachable from a console or Playwright — a manual pass had no way to trigger the live `valuenow`/`valuetext` announcements or toggle the button in place. Fixed: `poc-hue-slider.ts` now drives `setHue(hue ± 5)` on ArrowLeft/ArrowRight (focus-scoped, not pointer-capture-scoped); `poc-stale-expanded.ts` now has `tabIndex = 0` plus click and Enter/Space handlers toggling `expand()`/`collapse()`.
3. **The PoC pages exercise a throwaway `bindAria()`, not the shipped one.** `test/poc/poc-bind-aria.ts` is LT-004's prototype; LT-007/LT-008 landed the real `bindAria()` and registry in `src/bindings.ts`/`src/component.ts`. `examples/test/aria/` (served at :3000 via `bun run serve:examples`) exercises the real helper and is the more faithful target for a second AT pass — see the manual procedure below.
