**Area:** compiler
**Needs:** LT-254 (planning, 2026-10-09: the check reads its declaration build)
**Context:** ADR 0034 s8 (2026-10-01): no TypeScript type appears in the public API, so the
engine can move to TypeScript 7.1 or a native parser without a major. ADR 0032 s4 already
confines `typescript` API use to the converter. Add a contract check that the package's
emitted `.d.ts` files import nothing from `typescript` or `@typescript-eslint/*`. Lands with or
after LT-254's declaration build.
**Channel/tier:** none (a build check).
**Verification:** the check fails on a planted `ts.Node` in a public type; full gates.


**Changed:** `check:contract` gained a second phase that pins D-33 (ADR 0034 s8, ADR 0032 s4): it rebuilds the package (`build:compiler`, so no stale `compiler/dist` can pass) and scans every emitted `.d.ts` under `compiler/dist` for imports from `typescript` or `@typescript-eslint/*` — any hit fails the gate naming file and specifier. The emitted `.js` is exempt by design: the converter runs the engine at build time; only the type surface must be engine-free. The whole emitted tree is scanned, not just the exports-map entries — every file ships in the tarball and can surface through a future re-export, so a leak is caught at its source. LE_TRUC_COMPILER.md §2's standing-acceptance-run paragraph documents the phase.

**How:** `scripts/contract-check.ts` — a module-specifier regex (`from '…'`, `import(…)`, bare `import '…'`, both quotes, multi-line statements; mirrors `build-compiler.ts`'s relative-specifier matcher) over each `*.d.ts` after a `bun run build:compiler` spawn whose output surfaces only on failure. Phase order: designated-surface consumer first (unchanged), declaration phase second; `process.exitCode` accumulates so one run reports both phases.

**Check:** Task verification proven both ways: a planted `import('typescript').Node` on `contract.ts` (the designated surface) fails the gate with `contract.d.ts: typescript`, and a planted multi-line `import type { Node } from 'typescript'` on `pipeline.ts` fails with `pipeline.d.ts: typescript`; both reverted, check green again. Gates: `check:contract` exit 0 (both phases); biome clean on the changed script; `build:docs` + `check:links` exit 0 (782 links). `typecheck` is RED for a pre-existing reason: one TS2769 in `server/tests/compiler/corpus-config.test.ts:83` (`expect(LOCALES).toEqual(DEFAULT_LOCALES)`, the LT-480-review pin test) — reproduced identically on clean v3 HEAD 4a7bf85f in the main checkout, so it is LT-480 review residue, not this branch; zero errors from this change's files (owner may want a one-line fix on v3). Minor doubt for review: the scan regex also matches engine specifiers inside JSDoc examples of a public type (no such comment exists today); a failure there would be a loud false positive reworded at the comment, which seemed right for a gate — flag if you want comments excluded.

**Review (Architect, 2026-10-10): reviewed ✓ — both gates re-verified live; no branch nits.** `check:contract` exit 0 with both phases; the failure mode re-proven independently (a planted `import("typescript").Node` appended to `contract.ts` fails with `contract.d.ts: typescript`, exit 1, then clean after revert); `typecheck` carries only the one pre-existing TS2769 (identical on v3 HEAD — LT-480 residue, not this branch); biome clean on the changed script. The JSDoc doubt is **ruled as built**: a public type whose docs teach an engine import is itself engine coupling on the surface — a loud false positive that forces a reword is the right failure for a gate; no comment exclusion.
