# The Le Truc Host Profile

> This file states Le Truc's host-profile decisions for both authored component surfaces — `.tsx` (the default) and `.tsrx` — the parts of the language a host declares rather than a grammar core. See `ARCHITECTURE.md` for the runtime library, the adjacent `LE_TRUC_COMPILER.md` for the compiler that implements this profile, and [ADR 0032](../../adr/0032-adopt-tsx-as-the-authored-component-surface.md) for the dual-surface decision.

Core TSRX (`@tsrx/core`) defines the `.tsrx` parser and grammar. It does not define attribute semantics, style scoping, or a class-generation strategy — each host declares its own. TSRX has at least six named host profiles: React, Preact, Solid, Vue, Octane, and Ripple. All six render and hydrate client-side — Octane also does SSR and streaming, but still hydrates in the browser. Le Truc renders once on the server and enhances a light-DOM tree with signals by default, which none of the six do — different enough from every existing profile's model that several "host-defined" gaps in the draft spec only became visible while building this one. The `.tsrx` sections of this document are also the artifact to hand TSRX core maintainers when raising those gaps upstream: fixing ambiguities now, while host profiles are still few, costs less than fixing them after more hosts exist.

The `.tsx` surface has no core-TSRX relationship — it is standard TypeScript JSX, parsed by the repo's `typescript` dependency — but it inherits every host decision below that is not grammar-shaped: styles, the data account, the evaluation-tier posture, `truc:pass`, locale, and element references are profile decisions, not grammar decisions.

## Two surfaces, one profile

Since [ADR 0032](../../adr/0032-adopt-tsx-as-the-authored-component-surface.md) Le Truc compiles two authored surfaces through one machinery layer: **`.tsx` is the default for new authoring**, and **`.tsrx` stays supported** where its statement-context control flow (`@if`/`@for`/`@try` arms) reads better than expression shapes. The choice is per component. The corpus scan globs both extensions into one registry. A folder may carry a variant set — one `.tsrx` and one `.tsx` spelling of one tag, same base name, same directory — that compiles both, requires byte-identical CSS (LTC051), and serves the selected surface, `.tsx` by default ([ADR 0039](../../adr/0039-canonical-plus-variants-authored-surfaces.md)). Any other tag that two files declare fails the build naming both (LTC048).

Most of this profile is grammar-independent, and both surfaces live under it: styles, the data account, the evaluation-tier posture, `truc:pass`, locale, and element references. The grammar-shaped remainder is split: "The `.tsx` surface" below, and the `.tsrx`-specific sections marked as such further down.

## The `.tsx` surface

### Module shape

One exported component function per file:

- The function's first parameter is the destructured **server args**. Its TypeScript type is what compose sites check against — a wrong or missing arg at a parent's compose site is a `tsc` error on the parent's authored file, with no span table in between.
- **The second, optional parameter is the typed factory context** (LT-209) — the author's opt in to precise context typing:

  ```
  export function FormCombobox(
    { name, label, options }: FormComboboxArgs,
    { host, first, expose }: FormFactoryContext<FormComboboxProps>,
  ) { … }
  ```

  Form-associated components annotate `FormFactoryContext<Props>` (host: `FormAssociatedElement & Props`); plain ones `FactoryContext<Props>` — annotating the wrong one is a compile error (LTC050), as is destructuring a name that is not factory vocabulary (LTC049). The precision covers everything: `watch`/`on`/`pass` prop-key overloads, `host.setCustomValidity(…)` on form components, and a mistyped `expose()` key against `Initializers<Props>` is a free `tsc` error. **Wave-4 rule: destructure every factory name you use from the context param.** The `Record<string, any>` ambient `host` stand-in the profile started with is what this replaces; the ambients remain legal until the ambient retirement question is settled (owner, 2026-09-18: deliberately deferred until this convention has had use). `i18n` is NOT part of this parameter — it stays in the args destructure (the generated client has no `i18n` record; it is server-render-time data, and a client `t.<key>` read compiles against the generated message preamble instead).
- Statements before the single `return` are the **setup** — the `.tsrx` `@{ }` block's replacement. `export const i18n`, `export const config`, type declarations, and `declare global` interface augmentations carry over from `.tsrx` unchanged.
- The returned JSX is the **template**. **Its root is the host element**, spelled as the component's custom-element tag; there is no fragment root (owner, 2026-09-29) — a `<>…</>` output fails the compile (LTC060, LT-375), on `.tsrx` too. The stylesheet is the root's single direct `<style>` child; any other `<style>` fails (LTC073, LT-417). The root tag names the component — renaming it is a breaking change, renaming the function is not.
- The stylesheet is a `<style>` child of the root, carrying a `css`-tagged template literal: ``<style>{css`…`}</style>``, with `import { css } from '@zeix/le-truc-compiler/macros'` at the top of the file. JSX text cannot hold raw CSS braces, and the tag is what makes editors highlight the block as CSS. A bare template literal is accepted, and so is an empty `<style>`; the `css` spelling is what this profile teaches. The tag is a compile-time marker (see *Imports* below) — evaluated by nothing, so a `${}` substitution inside is refused (the tag's substitutions are also typed `never`, a `tsc` error). Any other content — another tag, a `css` that is not the marker, a substitution, any other expression or text — fails the compile (LTC078, LT-444) rather than shipping an empty sheet; on `.tsrx`, an expression in place of the CSS body does too.
- There is no `{count}` attribute shorthand. Spell `count={count}` — it lowers to the same server-attribute IR.

### Control flow is expression-shaped

`.tsx` has no directives; branch and loop shapes are plain JSX expressions, and the compiler lowers each to the same IR the `.tsrx` directives produce:

| Authored shape | Lowers to |
| --- | --- |
| `{cond ? <a/> : <b/>}`, `{cond && <a/>}` | `conditional` (`if`) — template-cloned arms when the test reads a signal or `host` |
| `{items.map((item, i) => …)}` | `for` — `each()` over server data, the `reconcile()` path over a declared `createList` or `deriveList`; decided by the iterable's type, not the spelling. The second parameter follows the same rule: the index over an Array, the item's stable key over a List (`items.map((item, k) => …)`, the `.tsx` spelling of `@for`'s `key k`; ADR 0046 s4) |
| `{items.length === 0 ? <empty/> : items.map(…)}` | `for` with an empty arm — the spelling of `.tsrx`'s `@for … @empty`. It is recognized by shape: the test compares the map receiver's own `length` to `0`. A `.map()` in any other conditional arm is an error (LTC005), including one wrapped in a fragment arm (`{c ? <>{xs.map(…)}</> : …}`, LT-301) |
| An IIFE whose body is a `switch` returning JSX per arm | `conditional` (`switch`) — literal case values when the discriminant reads a signal |
| `<truc:try catch={e => …}>…</truc:try>` | the error boundary |
| `<truc:try pending={…} catch={e => …}>…</truc:try>` | the async boundary |

`<truc:try>` is the spelling of `.tsrx`'s `@try`/`@pending`/`@catch` ([ADR 0041](../../adr/0041-truc-intrinsic-elements-for-compiler-consumed-constructs.md)). The children are the success content and the arms are attributes, so `tsc` checks each arm's type and rejects a repeated one. With `catch` only, it is the error boundary. With `pending` as well, it is the async boundary: the winning arm renders live and the others ship as inert templates, cloned in on a state change ([ADR 0037](../../adr/0037-reactive-conditions-via-template-cloned-arms.md) s4). `pending` renders while the task has no value yet, the narrow case of `isPending()`. `catch`'s callback receives the rejection as an `Error` (cause-effect wraps non-Errors before dispatch, so an unannotated `e => <p>{e.message}</p>` type-checks). The arms are typed `JSX.Element`, a branded interface an element expression satisfies by construction, so a string or function arm is a plain `tsc` error (LT-208).

The compiler learns the boundary's task from the success content's root: a direct lazy child (`{data}`), or a reactive `truc:html={() => data.get()}` on the root (LT-449), the task being a `deriveCell(async …)` or a `createTask(…)`. Through the `truc:html` channel the root's other client constructs, such as an `isPending` style thunk, mount as the ok arm's effects and die with the arm. The `catch` arm reads its parameter once: directly in its root, or in one child element of the root (the per-arm callout shape, `<card-callout class="danger"><p>{e.message}</p></card-callout>`). Both at once is refused (LTC005), because the arm has a single text target.

There is **no `stale` arm** — the owner withdrew the four-arm boundary (LT-211): a re-fetching task with a retained value keeps its `ok` arm, and the client never re-renders an arm's content. Both surfaces are three-arm; the s6 asymmetry ADR 0032 recorded is dissolved. The idiom for the in-flight state is a reactive `isPending(signal)` read beside the boundary:

```
<p role="status" class={() => (isPending(data) ? 'pending' : null)}>…</p>
```

`isPending` is a real `@zeix/le-truc` re-export (import it, either surface). Two authoring rules make the idiom work: the binding must be the **arrow thunk** — the reactive spelling; a bare `class={isPending(data) ? … : null}` expression is a render-time `server` attribute and never updates once connected. A condition may read a signal or `host` on either surface since LT-274 ([ADR 0037](../../adr/0037-reactive-conditions-via-template-cloned-arms.md)): its arms become template-cloned branches — the winner live, the others inert `<template>`s — switched by `reconcile()`'s arm form, so the arm's DOM is created on entry and disposed on exit rather than toggled.

The one thing `.tsx` cannot express is a **statement** in branch position: every arm must return JSX, and there is no directive block to hide a bare client-side statement in. Statements live in setup. A reactive list's item is the exception on both surfaces: the block body of the `map` callback, like the statements of an `@for` body, is the item's own setup (ADR 0046 s5, below). Where statement-context arms read better — a branch that mutates — author `.tsrx`; that is the surface split's whole point.

### Types and editors

Authored `.tsx` is checked **directly** by `tsc` — no generated module, no span-table remapping, and editors work through plain tsserver with no projection plugin. The strict ambient profile `server/compiler/frontend/tsx/host-profile.d.ts` is the authoritative light-DOM contract:

- `JSX.IntrinsicElements` is a **strict per-element table**: each entry names that element's light-DOM attributes, with `Reactive<T>` thunk overloads where a value may react. `class`/`for` are the spellings — `className`/`htmlFor` have no entry, so the React prior produces a plain `tsc` error instead of a diagnostic family.
- `data-*` is open through a pattern index signature.
- **`truc:pass` is deliberately absent from the common set.** A pass replaces the child's Slot, so only pass targets declare one — on their own args types (`'truc:pass'?: { value?: () => number }`). A parent's `truc:pass={{ … }}` checks against the child's real shape, and an excess pass key is a `tsc` error.
- **A migration to `.tsx` extends the table in the same commit** — the entry IS the migrated tag's light-DOM contract.
- The `host`/`first`/`all`/`watch`/… ambients come from the same file. Since LT-209 the convention is to **annotate a second, typed context parameter instead** — see the module shape above — and destructure every factory name you use from it; the wide ambients remain for the migration period, their fate deferred (owner, 2026-09-18).

The two ambient profiles — this one and `frontend/tsrx/globals.d.ts` — declare the same global names and **must never share a `tsc` program**: an authored-`.tsx` tsconfig includes `host-profile.d.ts`, a raw-`.tsrx` view includes `globals.d.ts`, never both.

## Styles are shadow-root CSS, scoped in light DOM

[ADR 0033](../../adr/0033-scope-component-styles-by-custom-element-name.md) (✅ Accepted, ships in 3.0) rules the model for compiled components: the stylesheet is authored as **shadow-root CSS** — `:host` for the host element, bare selectors for its internals — and the compiler scopes it in light DOM so rules stop at every custom element the template renders: native `@scope` where the configured `cssTargets` support it, a flat `:where()`-led lowering where not. Page styles still win over `:host` rules, as they do over a component in a real shadow root — the zero-specificity emission is what keeps that true. Authored forms with no meaning under the contract are tier 1 errors (Prevented): a rule led by the component's own tag (LTC066, fix-it `:host`), `::slotted()` in light mode (LTC067), `:host-context()` in either mode (LTC068), `:global` in any form other than the two whole-rule forms (LTC069 — a top-level `:global(<whole selector>) { … }` rule or a bare `:global { … }` block, both hoisted out of the scope and emitted unwrapped; an at-rule-conditioned global rides in the bare block, `:global { @media … }`), `:host` directly followed by a qualifier (LTC070, fix-it `:host(<qualifier>)`), and a selector that descends past a boundary tag (LTC071 — `child-tag .x`: the scope stops at the child's tag, so the rule matches nothing; the child's own tag and its siblings stay legal). The sheet must parse (LTC064); a declaration outside the property dictionary's grammar warns (LTC065) and ships as written — the dictionary lags the platform.

The compiled contract differs from a real shadow root exactly where ADR 0033 s7 pins it: **inward reach** — page CSS can still reach a light-DOM component's internals, and only a real shadow root prevents that; **page-authored children** are styled by the component's rules (intended where nothing is slotted); **template-authored content inside a composed child** — content the component's own template places inside a composed child is outside its scope, though a real shadow root would style it; it styles from a top-level `:global { … }` block; **a custom element inserted at runtime is no boundary** — the boundary set is fixed at compile time, so the component's rules reach such an element's internals in either emission form, while a plain element inserted at runtime is styled (the rules are live CSS); and on targets without native `@scope` there is no scope-proximity step — a self-nested boundary (`A > B > A′` with B in A's boundary set) computes from the outer instance, so the lowered guard also excludes A′'s internals and its non-bare `:host` rules where native proximity would style them. Shadow mode is the per-component opt-in (ADR 0033 s8) and changes more than the wrapper: the same sheet emits verbatim into the shadow root, `::slotted()` becomes legal, `:global` rules move to the document stylesheet, page-authored content renders only through slots, the children-are-data harvest stops at the shadow boundary, `id` references (`<label for>`, `aria-labelledby`, `aria-describedby`) no longer cross it, and Declarative Shadow DOM is Baseline 2024. Hand-written CSS for runtime-only components keeps its 2.x meaning: tag-led, emitted verbatim (see [Styling](../../docs-src/pages/styling.md#scope-styles-to-custom-element)).

This is a deliberate divergence from Ripple, the one other profile, which scopes via generated class hashes; ADR 0033 declines them (a client-transform mechanism with no server-render counterpart, hash classes in every served byte). A tool or agent trained on Ripple's CSS model will misdescribe Le Truc's — state this profile explicitly wherever such tooling might be pointed at a compiled source. Style composition is split out: the typed class handle is a recorded direction ([ADR 0042](../../adr/0042-the-component-stylesheet-as-a-compiler-artifact.md) s3), composition proper stays on the ROADMAP.

## The data account: server props, client markup, boundary-only composition

Where component data lives — ratified by the 2026-08-29 owner review (LT-112/113), binding every Le Truc component, hand-written or compiled:

1. **Compiled server components get all necessary data as props (server args).** When a component is composed server-side, data reaches it through its props contract only; the generated server render materializes those props into the child's markup. There is no server-side harvesting — the server composes declarations, it does not inspect DOM.
2. **Client Web components can place server-known initial data anywhere in their owned markup, not just in the attribute contract.** A hydrated component owns its light-DOM children: initial state may be encoded as text content, descendant structure, or attributes, and the component harvests it there (`expose` initializers and Parser fallbacks may read `first()`-bound children). A component should not demand as a host attribute what its owned children already carry — avoiding passing template and data twice is one of Le Truc's main advantages over JS frameworks. A host attribute is a legitimate *override* where the contract defines precedence (host attribute wins over the harvested value), not a second copy.
3. **Reaching into sub-components' owned markup is a no-go — only via the declared public interface of the Web Component, or declared config attributes at the boundary.** A parent, server- or client-side, composes through the child's public props and methods, or through attributes the boundary declares (the child's exposed Parser attributes; the compose-site `class`/`id`/`data-*` discriminators). If the child's contract can't express what the composition needs, fix the child: expose a writable prop (`createCell`-backed) when consumers own the value, a self-derived one (`deriveCell`, or a bare thunk — `expose()` wraps it) when the component computes the value itself from its own state (e.g. a remaining-character count from `maxlength`, or the subset of its own rendered items currently passing its filter), or a METHOD (`defineMethod`) when the parent needs the child to *act* on markup it owns rather than to read it. The method form matters as much as the prop form: focus management is the common case, and it is the one where the parent's only alternative is a `querySelector` into the child's control (LT-120). Reaching into the child's DOM from the parent (`first()` on the child's template internals, `querySelector` inside a composed child) is an ownership violation even when it works — see the pass write-ownership section below for the signal-level corollary.

4. **A harvested prop's render site is the one channel — the arg renders it, the prop binds it.** A component that harvests a prop from its owned children renders that value into the site from its SERVER ARG (`<span class="label">{label}</span>`), harvests it back out of that same site at connect (`expose({ label: labelSpan?.textContent ?? … })`), and rebinds the site when the prop is written afterwards. One site, three roles: the server's render target, the client's harvest source (ADR 0003, DOM-is-truth), and the client's binding target. Writing `{host.label}` instead renders an EMPTY site on the server, which is what pushed LT-092 into duplicating the value onto a host attribute; a Parser-exposed prop whose value is also rendered into an owned site from a same-named arg is the duplication smell and warns at compile time (LTC039, LT-122) — but only genuine duplication should warn: a Parser whose fallback expression READS the site being rendered is bullet 2's sanctioned override, and a site whose value is deliberately *different* from the prop (form-spinbutton renders the control's `step` as `'1'`-or-`'any'` derived from its own `step`) is a related value, not a second copy. The first shape stopped warning in LT-129 — LTC039 now skips a site whose own element the Parser's fallback reads, per SITE rather than per prop, so the same prop rendered onto a different element is still a duplicate and still warns. LT-139 extended it from attribute sites to TEXT-CHILD sites, so the identical override written as `expose({ label: asString(labelSpan.textContent ?? '') })` over `<span class="label">{label}</span>` is silent too. **`formAssociated()` is a standing exception to this bullet, not a smell:** on a form-associated host the content attribute is the RESET BASELINE (`defaultValue`/`defaultChecked`, installed by the extension — LT-056/LT-057) and the owned control's rendered value is the CURRENT value. Two channels carrying deliberately different things, exactly as native `<input value>` splits the content attribute from the IDL property, so neither is removable and LTC039's fix-it ("drop the attribute") would break form reset. `value` under `formAssociated()` and `checked` under `formAssociatedCheckbox()` are therefore exempt (LT-141).

Server rendering does not penalise the harvest route. A `hidden={() => …}` thunk over a HARVESTED prop folds to an initial value on the server from the arg that renders its site, and a thunk over a `first()`-bound ref's PRESENCE folds from the `@if` condition that decided whether the server rendered the element (LT-118, the adjacent `LE_TRUC_COMPILER.md` § 5). This matters for the authoring surface, not just for a flash: without it, an author who wants an optional affordance gated on a local ref — `const zero = first('.zero'); if (zero) { … }`, the hand-written idiom — would be pushed into exposing a reactive public prop purely so the compiler had something server-known to read. A component's public surface is a contract, not a compiler workaround. Under tiered server evaluation ([ADR 0029](../../adr/0029-tiered-server-evaluation.md)) this generalises: a shape the fold cannot follow no longer costs the author an error — it routes the component to a phase that runs the code for real. See the next section.

5. **A per-document `id` in a template belongs to whoever instantiates the component.** An `id` is unique per DOCUMENT; a template is a per-INSTANCE thing. A constant `id` in a template is correct for exactly one instance on a page and silently wrong for the second — every `aria-labelledby`/`aria-describedby`/`<label for>` pointing at it resolves to the FIRST instance, which is invalid HTML and, for `aria-*` wiring, an accessibility defect. The compiler does not generate one: a counter or hash would make the server render non-deterministic across pages and give the client nothing stable to re-derive. So the id is a **server arg with a documented default**, and every reference in the template is wired from that one arg — one value, several sites, the SAME channel (not bullet 4's duplication shape, which is one value through two channels). This is bullet 3's ownership rule applied to identity: the instantiator owns the discriminator. Warned at compile time (LTC042, LT-131); `basic-gauge` and `basic-hello` are the corpus references.

6. **A formatted reactive value keeps a raw value source.** Text formatted for display (`1’234 articles`, a localized date) does not parse back into state, so the harvest cannot read it. A formatted reactive value has a canonical raw source the client harvests instead: `value`, `valuenow` or `datetime` on an owned descendant (`<data value>`, `<time datetime>`), or a host attribute. The formatted text renders beside it; the raw source is the harvest site, and both rebind together. Template emission relies on the same rule: a pre-formatted value supplied by the CMS has no raw source, so it is refused ([ADR 0043](../../adr/0043-the-target-emitter-interface-for-template-emission.md) s6). Endorsed 2026-10-01 (`COMPILER_SPEC.md` D-20); enforced as LTC059 (LT-374). **What counts as formatted** is decided syntactically, over a reactive text child and the setup consts it reads (transitively): any `Intl` read, a `toLocaleString()`/`toLocaleDateString()`/`toLocaleTimeString()` call, or a call of a declared message whose pattern takes a `number`/`date` argument (`plural`, `selectordinal`, `number`, `date`, `time`). A formatter reached through an import is not recognized — the compiler reads no other module — but that costs only the diagnostic's precision: a computed text thunk is never a harvest site, so such a signal still fails to seed (LTC005) rather than harvesting formatted text. LTC059 fires when a signal **seeded from server args** has a formatted text site and no raw source; a literal seed needs none, since the client reuses the initializer. **Raw sources the harvest reads:** a reactive attribute whose arrow reads exactly the signal (`<data value={() => n.get()}>`, `<time datetime={() => d.get()}>`, `aria-valuenow`), parsed by the signal's type; or the seeding arg rendered as an attribute on an owned element or the host, which a `number` arg reads back through `Number()`. A raw source rendered from the arg alone (`<data value={count}>`) seeds correctly but does not rebind — prefer the reactive form.

Corpus anchors: `basic-button` is the harvest reference (label ← `span.label` with fallback to the button's own text, missing-span tolerated — no attribute duplication); `form-textbox`'s `description` is the boundary-fix reference (a writable prop whose remaining-count display the component derives itself, so parents like `module-coloreditor` compose through the public prop instead of poking the `.description` paragraph). For the derived-prop and method forms (LT-119/LT-120): `form-listbox`'s `options` projects its own rendered option buttons back out as `{ value, label }` pairs, and `visibleOptions` is that list filtered by its own `filter` — bullet 2's children-are-data rule turned outward into a public contract; module-listnav maps the URL hash onto `options` rather than querying the buttons (LT-332) — and `form-listbox.focusFirstOption()` / `form-textbox.focusControl()` are the method anchors. Note what `focusControl` is NOT: it does not shadow the native `HTMLElement.focus()`, which form-associated internals and the browser both call on the host; a boundary method adds to the element's surface, it does not redefine the platform's.

Migrations preserve the hand-written contract unless a reshape was explicitly decided with architect sign-off (the LT-095 checkpoint pattern); a documented-in-comment deviation is not an acceptable outcome — restore the contract or escalate.

## What you write decides your evaluation tier, not whether you get an error

Le Truc evaluates a component's reactive initial values server-side in one of three tiers, chosen statically by the compiler ([ADR 0029](../../adr/0029-tiered-server-evaluation.md); `ARCHITECTURE.md` § Server Evaluation Tiers has the table). The template is always lowered to markup — tiering only decides how much of the *reactive* state is resolved before JavaScript loads.

The authoring consequence is a posture change, and it is the point of the decision: **a shape the server cannot fold is not an author error.** It used to be. `LTC004` (a signal with no harvestable render site), `LTC034` (a semantically-loaded attribute with no server-renderable value), `LTC043` (a setup const reading a `first()`-bound ref) and the server-evaluation members of `LTC013` all refused to compile a component whose setup the DOM-less value harness could not run. They now route it to a phase that runs it against a real (simulated) document instead, and the compiler records the tier rather than raising a diagnostic. `LTC043`'s old fix-it — restructure the component to harvest through a rendered site — is still *good advice* where it fits bullet 4's one-site-three-roles shape, but it is no longer a requirement imposed by the server's limitations. The posture change stops at a rendered value: a client-only const that is merely declared routes the component Simulated, but one whose value is spliced into the markup as a static site still fails the build (`LTC046`) — no tier can evaluate the splice, and no client binding ever corrects a static one, so render the site from a server arg or signal or make it reactive.

Two rules of thumb remain worth knowing while authoring, because tier still costs something:

- **The Folded tier is the majority path, and cheap.** Twenty-seven of the corpus's thirty-five components qualify: every reactive value that reaches a rendered site comes from server args, from signal initializers over those args, from the `i18n` record, or from `host.<prop>` reads of Parser-exposed props whose fallbacks read no element reference. A `first()` reference in a `watch()`/`on()` position is a client concern that reaches no served byte and does not route — only a rendered value the fold cannot follow routes Simulated. Do not contort a component to reach the Folded tier — the difference is about a millisecond of build time per occurrence, and a contorted public surface is a permanent cost against a temporary one.
- **Some expressions have no server answer in any tier, and the compiler stops guessing.** Two kinds: values reachable only through layout geometry, `internals`, or a stubbed sensor (`matchMedia`, `ResizeObserver`, `IntersectionObserver`); and values whose input is *the moment the page is viewed* rather than anything the server knows — the wall clock (`Date.now()`, `new Date()`), the RNG (`Math.random()`, `crypto.randomUUID()`, `crypto.getRandomValues()`), a locale falling back to the runtime default. These are omitted in every tier, including simulated ones, and the client fills them at connect. The server no longer refuses to compile them (it used to) and no longer bakes the build machine's answer into the page (it briefly did): a build-time timestamp is not a flash the client corrects, it is a plausible-looking stale value served for the life of the page. **This is per-expression, not per-component** — a component can be simulated for everything else and carry one suppressed thunk. If a blank site is not acceptable for your no-JS story, give it a static or server-rendered default; that is the authored mitigation, and it is yours to choose rather than the compiler's to guess.
- **The Static tier is the component-level version of that.** A component whose unresolved values are *all* of the above kind is never simulated at all. That is usually right — a scroll-overflow state genuinely has no server answer. But it means the pre-JavaScript HTML shows the *absent* state, and for a semantically-loaded attribute on a real submittable form control that is a correctness problem rather than a flash. That case still raises `LTC034` — scoped per-expression like bullet 4's suppression, so it fires for any such site no server phase can resolve, including on a component the realm simulates for everything else — and the fix is bullet 4's: give the element a static or server-rendered default so the no-JS state is the one you chose.

The one thing tiering never changes is what the component does once connected. The client is ground truth in every tier ([ADR 0003](../../adr/0003-attributes-drive-state-at-connect-time-only.md)); no serialized state payload ever ships.

## `truc:pass` is host-owned, not a TSRX deviation

Core TSRX defines no attribute semantics at all — every attribute's meaning is host-defined. Le Truc uses the namespaced form `truc:pass={{ ... }}` (`JSXNamespacedName` is grammar-native) for client-side signal interop with a custom-element target. The namespace prefix avoids collision with a user-defined prop literally named `pass`, and matches the ecosystem convention of namespacing host-owned attributes. It lowers to a `pass(target, { ... })` call (ADR [0011](../../adr/0011-throw-on-pass-binding-failure.md), ADR [0012](../../adr/0012-deprecate-unrestricted-write-short-forms-in-pass.md)).

### When an attribute earns the `truc:` prefix

The prefix marks attributes whose semantics **Le Truc owns and core TSRX does not define**. Applied to the current non-standard surface (owner review, 2026-08-30; `html` bullet reversed 2026-08-31 after the upstream claim behind it was checked and disproven):

- **`truc:pass`** — namespaced, correctly. Signal interop with a custom-element target is entirely a host concern; core defines nothing here.
- **`ref={}` on a composed element** — host-owned, and deleted rather than prefixed (LT-127, landed). It supplied only the query variable's name; the selector (`form-spinbutton.lightness`) was already synthesized from the compose registry and the site's own discriminator, and `first()` types it through `HTMLElementTagNameMap` with no library change. It was also the one place TSRX declared a binding by attribute instead of by statement — with it gone, composed and raw elements share one addressing mechanism and the attribute KIND is gone, not renamed.
- **`truc:html`** — host-owned, and prefixed (LT-128, decided 2026-08-31; renamed from bare `html={}` by LT-137). The earlier reading — that it stood in for an upstream `{html expr}` keyword too new for the pinned parser — was checked against the published packages and is false: no such keyword exists in `@tsrx/core` 0.1.60 or 0.1.63, nor in `@tsrx/ripple` or `ripple`. Core defines nothing here and says so, delegating raw markup to "each target framework's native raw HTML prop"; the reference host answers that by special-casing the literal attribute name `innerHTML` in both its transforms. Le Truc does not borrow that name, because Le Truc's semantics are not the DOM property's: the value is routed through `sanitizeHtml` rather than assigned raw — the library's fail-closed wrapper (LT-138): the configured default from `configureHtmlSanitizer`, else escaped text, safe but inert; configuring it once per realm (DOMPurify over jsdom at build, plain DOMPurify in the browser) switches both halves — and a reactive thunk (`truc:html={() => …}`) is accepted, which a property assignment does not imply. Borrowing `innerHTML` would promise raw trusted assignment we deliberately do not perform. If Le Truc ever adopts trusted-by-default raw semantics, `innerHTML` becomes correct and `truc:html` retires into it.
- **`truc:text`** — considered and dropped as speculative. The case it was meant to serve, overriding a server-known empty string with a client-only binding, is already spelled `{host.X}` (what managed form props do — server-renders empty, binds on connect) or `{() => …}`.
- **Any other `truc:` name is rejected** (LT-353). The namespace carries only the names above, so the classifier reports any other name as LTC006 on both surfaces, naming the accepted vocabulary (`truc:pass` and `truc:html` on a raw element, `truc:pass` on a compose site). Before, a typo such as `truc:htm` rendered as a dead literal attribute. The retired `truc:case`/`truc:case-type` get a pointer to the ICU pattern that replaced them ([ADR 0030](../../adr/0030-internationalization-as-build-time-server-data.md) s4).

A new non-standard attribute answers one question first: does core TSRX define this, or borrow-and-polyfill it? If core owns it, no prefix and no invented spelling. If Le Truc owns it, prefix it — unless, as with `ref`, an existing mechanism already covers it and the attribute can simply go away.

### Pass write-ownership

A pass replaces the target's Slot for that prop — the child's own writes to the prop route through whatever the parent passed. A **getter-only** thunk (`{ value: () => host.value }`) therefore makes every child-side write to that prop throw `Signal is read-only`: the child's own event handlers, its exposed methods, even the library's built-in `formResetCallback` baseline restore. Getter-only passes are only safe when the child provably never writes the prop itself.

One more sharp edge (found in LT-113, verified live): a getter-only pass into a prop whose exposed `createCell` feeds an internal `deriveCell` display **disconnects the derivation** — the pass swaps the Slot's backing while the derivation keeps reading the internal cell, so the display freezes on its seed. Direct writes and `watch()` + `bindProperty()` pushes both flow correctly (they write through the Slot into the cell). Until/unless the compiler routes such derivations through the exposed Slot, the commit-on-change shape below is not just preferred for form children — it is required whenever a parent-derived value feeds a child's derived display.

When a composition needs a child-writable prop whose value the parent derives (a spinbutton that steps its own value inside a color graph, a textbox the parent pre-fills but the child edits), use `watch()` + `bindProperty()` + commit-on-change instead: the parent pushes the derived display value down with `watch(() => derived, bindProperty(child, 'value'))`, and commits the child's committed result back up from a `change`-style event, reading `child.value`. Ratified in LT-091's review after the form-colorgraph spec caught the throw (`examples/form/colorgraph/form-colorgraph.tsrx` is the reference composition; `examples/form/inplace-edit/form-inplace-edit.tsrx` applies the same pattern to a composed textbox). A mediated `{ get, set }` descriptor is the middle ground — the parent intercepts writes — but note it re-enters on the library's own internal writes (form reset re-commits a stale baseline through the setter), which is why the commit-on-change shape is preferred for form-associated children.

## Locale and translations arrive as server data, through the reserved `i18n` parameter

The client is the wrong layer to answer "what language is this page in" — by the time a component runs, the answer is already in the DOM, put there by whoever rendered the page. So locale is **build-time server data** ([ADR 0030](../../adr/0030-internationalization-as-build-time-server-data.md)), and it reaches a component the way all server data does: as a server arg.

**The reserved parameter.** A component that needs locale data declares a parameter named `i18n` and the compiler supplies it — the same reserved-name mechanism as `children` (ADR 0024 sub-design 10). **Callers never pass it** — on `.tsx` the host profile's `JSX.LibraryManagedAttributes` omits `i18n` from a composed child's props, so a JSX parent that leaves it out typechecks — so composition does not thread it through the graph by hand, and a component that does not declare it receives nothing and pays nothing. It destructures like any other arg, so the source stays honest TypeScript:

```
export function BasicPluralize(
  { count, i18n: { t, lang } }: { count: number; i18n: I18n<typeof i18n> },
)
```

The record carries `lang` (BCP 47), `t` (this component's resolved messages), `timeZone`/`currency` for `Intl` consumers, and `dir`. `dir` is there for components whose *logic* is direction-aware — do not render it, direction belongs on the page's `<html>` and a component writing it on its own root fights the page.

**Locale precedence: authored `lang` wins, and the locale inherits.** `basic-pluralize` and `basic-number` declare `lang` as a public attribute, and those contracts stand. Precedence at a render boundary: an explicit `lang` arg at the compose site, else the **parent's own effective locale** (compose-graph inheritance — the SSR analog of the DOM ancestor walk, since the composition tree is the rendered ancestor chain; LT-191), else the component's authored default, else the page locale. That is bullet 2's sanctioned override, not a second copy — and the *effective* locale is what renders onto the root `lang` attribute, which bullet 4's duplication rule already exempts because the root is the channel (ADR 0024 sub-design 3).

**`lang` is a config attribute, not a reactive property.** It is a built-in IDL property, so `expose()` cannot install an accessor over it (`prop in this` skips it silently) — a compiled component MATERIALIZES the walked locale onto the attribute at connect instead: own attribute first, else the nearest ancestor `[lang]`, else `en` (`getLocale(host)`'s walk includes the element). This is the same thing the server render does for SSR'd instances (root attr = effective locale), so both paths converge on one DOM shape, and the walk can never disagree with the build — a rendered instance's root attribute terminates it. Deliberately NOT restored: re-walking on ancestor changes — the materialized locale is fixed at connect, because the catalog never ships and the server-rendered messages hold one locale's translations.

**Messages: you declare the keys, the build fills them.** A component declares the keys it needs and the build supplies the locale's catalog. A caller never passes translations — a `t={{ … }}` at the compose site would make every parent know its child's internal keys, which is bullet 3's ownership violation. Keying is **explicit**: literal prose stays literal until you route it through `{t.key}`, and the compiler warns on literal prose in a component that otherwise uses the catalog, so a forgotten string is build-visible. **A message value is an ICU MessageFormat 1 pattern** ([ADR 0030](../../adr/0030-internationalization-as-build-time-server-data.md) s4): `t.<key>` is a string when the pattern takes no arguments, and a call — `t.key({ … })` — when it does. Plurals, `select` and inline number/date formatting live inside the pattern, so one key covers every form and word order is the translator's to choose. Variance a pattern cannot express — different markup per case, not different words — is ordinary control flow: a ternary, or `@if`/`@switch` on a server-known value. The source locale declares every key its template references, so the fallback bytes always exist. Concretely:

```
export const i18n = {
	done: 'Well done, all done!',
	tasks: '{count, plural, one {# task} other {# tasks}} remaining',
} as const                                                            // keys + source patterns
…
<p class="none" hidden={() => host.count !== 0}>{t.done}</p>         // route prose through t
<p class="some">{t.tasks({ count })}</p>                             // arguments are checked against the pattern
```

The declaration must be an object literal of string literals (they are the fallback every locale resolves against, and the bytes the staleness manifest hashes).

**`t` is typed per key** (LT-308): declare the catalog `as const` and annotate `i18n: I18n<typeof i18n>`. Each `t.<key>` is then `string` for a pattern without `{` and `(args: MessageArgs) => string` for one with `{`, so an undeclared key (`t.fliter`), a bare argument message in an attribute, and a call on an argument-less message are all `tsc` errors — and attributes are plain `Reactive<T>`, so a possibly-undefined `aria-label` is one too. Forget the `as const` and every value widens to the `string | function` union: the first attribute read fails instead of passing silently. The authored-side classification is by brace only, so an ICU-escaped literal brace (`'{'`) in an argument-less message misreads as a function — accepted, since the corpus has no such pattern and the compiler's argument check (LTC055) and the generated modules are exact: the server module rewrites the annotation to the inline record (`I18n<{ done: string; tasks: (args: { count: number }) => string }>`), which `check:corpus` typechecks with the real argument names. The untranslated-literal warning fires on template text containing two or more adjacent letters — a single-letter fragment is page data, not prose. Every locale carries the same key set, and the census checks each translation's argument set and its `plural` arm coverage against the locale's CLDR categories (ADR 0030 s5). The census also walks the other way (LT-196): a catalog entry nothing declares — a translator's typo, a renamed key, a deleted component — reports as `orphaned`, and `i18n:sync` prunes it, so catalog residue never outlives the declaration it was written against.

**Source strings stay in your component; translations are separate files.** You declare each key together with its source-locale string in the component source itself, either surface — the component remains the single source of truth for the source language, and there is deliberately **no sibling catalog file** for it, because that would reintroduce the three-file drift the isomorphic format exists to cure. Translations are additive override files, one per locale, component-namespaced (`i18n/de.json`, keys like `basic-pluralize.remaining`). There is **no catalog tiering** — no global/page/component override stack — so a key resolves in exactly one place; page prose is translated by having a per-locale page source, not by a catalog override.

**A missing translation is not your problem to fix.** It falls back to the source-locale string and is recorded in the build report's translation census — deliberately not a compile warning, because a missing key is the translator's work and not author-fixable. An `i18n:sync` placeholder (the empty-string entry the sync script writes for keys a locale has not translated yet) falls back to the source string too, so a mid-translation locale never renders empty markup. Mixed-language pages are shippable mid-translation, on purpose. An untranslated *literal*, by contrast, IS yours to fix, which is why that one is a real warning.

**The catalog never reaches the browser.** The locale reaches the client through the rendered root `lang` attribute, its only carrier (DOM-is-truth; ADR 0030 s6). Serialized messages bake in `timeZone` and `currency`, never the locale, and the client evaluator reads the locale from its `closest('[lang]')` walk at the first format. A component whose client messages format (number, date, plural) but that renders no `lang` of its own gets the render locale on its root, written by the compiler. A message with a client-reactive argument is **recomputed, not selected** — the server renders it for the initial arguments, and the client re-evaluates the build-parsed pattern when an argument changes ([ADR 0030](../../adr/0030-internationalization-as-build-time-server-data.md) s9). A static `t.<key>` read of a declared key (`t.done`, or a string-literal key `t['a.b']`) compiles in any client position: a reactive thunk, a handler, an `expose()` entry, a client-only setup statement, a list-item handler. An argument message is called in place: `() => t.tasks({ count: host.count })`. The server then serializes those keys' messages, as parsed ASTs, into a per-instance root `i18n` attribute, and the generated factory merges it over the build-parsed source record, with the evaluator inlined and narrowed to the constructs those patterns use. The attribute carries only the keys the render locale changes, so a source-locale render usually writes none. A client-created instance speaks its creating parent's locale (ADR 0030 s9, LT-355). A composed child inside a reactive-list item renders once into the extracted `<template>`, at the parent's effective locale; ADR 0030 s3's precedence applies, so the compose site's own `lang` wins. Every clone copies the child's root `lang` and `i18n`. The child's args and content therefore cannot read the item or key (LTC075); a per-item value reaches the child through `truc:pass`. An instance created outside any compiled parent formats in its walked locale and speaks the source strings. Everything else about `t` stays server-only (LTC005): a computed `t[key]`, a bare `t`, the whole-record spelling `i18n.t.<key>`, and `lang`, whose client spelling is `host.lang`. The corpus's event-time strings ride the attribute: `form-tokenbox`'s status and duplicate messages, `form-colorgraph`'s out-of-gamut validity message, `form-spinbutton`'s increment label. Inside a reactive-list body's attributes, by contrast, a `t.…` read is a build-time constant like any server-known value (LT-215): it folds per render call and bakes into the extracted `<template>`, so client-cloned items carry the translated value with no client binding — `form-tokenbox`'s per-pill remove label is the corpus's case. Item-derived values are the item's own signal reads: the bare `{item}` child is the signal shorthand, everything else is the arrow over `.get()` (a store item's fields are cells), and a `server` attribute over the key binding alone is set once at clone (ADR 0046 s1, LT-423). The item is a Mount Scope — reactive attributes, maps, `truc:pass`, events and composed children plan inside `bindItem`, and arm sets and lists nest inside it (LT-424) — while a host-level `first()` into an item and an item with other than one root element stay refused.

**Per-item setup** ([ADR 0046](../../adr/0046-reactive-list-items-as-mount-scopes.md) s5, LT-426). The statements before the output — the block body of `items.map((item, k) => { … return <li/> })`, the statements of an `@for` body — are the item's setup, classified by component setup's rules with the item and key as known names. Each runs in both phases: once per initial item in the server's loop, once per entering item in `bindItem`, where it is disposed with the item. So a plain `const` and a signal declaration read only what both phases bind — the item and key, an enclosing item's names, signals, setup consts, imports — and never a server arg (the client has none) or a client-only name (`host`, a ref, `on`); the one exception is a position the server defines but never calls, a function const's body or a `createSensor` start callback, whose client-only names the server stubs or leaves out. A `createSensor` needs its `{ value }` seed, which is what the server renders every initial item from. A per-item const is a value fixed per item: an attribute over the item's consts and key alone is set once at clone, like a key-derived one; anywhere else it is read in an arrow. A condition over a per-item name switches arms in the item. `first()` resolves against the item's own content — a selector naming the item root resolves at build time to `bindItem`'s element parameter (`first` searches descendants only), one reaching into a nested arm or nested item is refused. A client-only side effect (`watch`, `on`, `pass`) runs in `bindItem` only, and a `deriveList` declared in the item drives a nested list. `expose()`, `requestContext()` and any other statement are LTC005; arms take no setup statements. On `.tsx`, a `watch`/`on` called directly in the callback body is in `bindItem`'s collector, not deferred (no LTC045).

**Per-field harvest** ([ADR 0046](../../adr/0046-reactive-list-items-as-mount-scopes.md) s7, LT-429). A list seeded from server args (`createList(rows, …)`) has no literal the client could reuse, so the client rebuilds each server-rendered item from its markup, field by field — the data account's bullet 4 applied per field. A field's site is the first, in document order within the item, of a text child or an arrow attribute that reads exactly the field: `item.f.get()` on a store item, `item.get().f` on any, optionally through `String()`, the serialization the server applies anyway. Conditions, nested lists and composed children are not searched, since an adopted item need not carry them. The field `keyConfig` returns verbatim (`row => row.id`) comes from `data-key`. A dirty-flag attribute (`value`, `checked`) reads the live property, as the scalar harvest does. Each field reads through a parser: a `harvest()` entry when there is one, else the one its type infers (`string` and string-literal unions → `asString`, `number` → `asNumber`, since `String(n)` round-trips, `boolean` → `asBoolean`). An optional field (`note?: string`) infers none — the server may hold `undefined`, which an inferred parser would read back as its fallback — so its entry is required, and may return `undefined` (`note: v => v ?? undefined`). The item type is read without a checker: the declaring call's first type argument, else the element type of the seed arg's annotation, followed through a same-file `type` alias or an `interface` without `extends`. A field with no site fails the compile (LTC072; LTC059 when its only site formats it), and so does a field with a site but no parser (LTC076). An item type the compiler cannot read — imported, generic, a union — lists its fields only through `harvest()`'s keys: `createList(harvest(rows, { id: asString(), due: asParser(v => new Date(v ?? '')) }), …)`. The rebuilt item is annotated with the item type, so a wrong parser or a field missing from the map is a `tsc` error, mapped to the authored entry (or seed) on both surfaces; on `.tsx`, `harvest()`'s own typing (each entry a `FieldParser<T[K]>`, which a `Parser` of the field's type satisfies) catches a wrong parser before the compiler runs. A `string` item keeps the whole-item read of its bare `{item}` hole, and a literal seed is reused as written, so `harvest()` around one fails the compile (LTC005).

**Scalar harvest** (ADR 0046 s7, LT-443). A scalar signal seed declares its parser the same way: `createState(harvest(price, asNumber()))`. Every scalar harvest read goes through a parser — the direct text or attribute site, the substituted DOM read of a seed that IS the arg (`createState(price)`), a membership value read — the marker's parser when declared (spliced as authored; its free names must resolve on the client; a number-valued one — `asNumber`, `asInteger`, `asClampedInteger`, matched by name — also makes a reactive attribute site over the signal coerce through `String()`, as an inferred `number` does, since the marker does not inform inference), else the one the seed's bare `string`/`number`/`boolean` keyword infers (`number` → `asNumber`, since `String(n)` round-trips). A seed that DERIVES from the arg (`createCell(value.length)`) needs no parser: the substitution reproduces the derivation identically on both sides, so its value is never a bare site string — and a marker on one declares a parser nothing reads, which is refused. A seed whose type the compiler cannot read — an alias (`price: Price`), a union, an imported type — infers no parser, and the inferred-string fallback would silently connect e.g. `2.5` as `'2.5'`, so a harvest site over one is refused (LTC077) until the marker declares the parser. Only the harvest needs one: a signal with no raw site (a Parser-exposed prop, a context, a sensor), and a seed the client re-evaluates verbatim (a literal) are never refused — and a marker whose parser would never run there is refused in turn. This is the shape a `Date` seed round-trips through: a `Date` cannot pass a typed sink raw, so its signal renders only computed positions while the marker's parser reparses the arg's rendered attribute.

**`getLocale()` is the client-side route again** (LT-191 restored what LT-173 retired): its `closest('[lang]')` walk — which includes the element itself — is how a compiled component resolves the locale for client-authored markup, materialized onto the element's own attribute at connect. The reserved `i18n` parameter remains the canonical route for RENDERED pages: the record's locale is a build-time fact, and the rendered root attribute is what terminates the walk. The one caveat stands: the realm parses one component's markup, so a fixture's ancestor chain must be authored into the markup itself (the driver seeds `<html lang>` for the page-level answer).

Two payoffs worth knowing: because the page's locale is a build-time constant, `Intl` calls fold server-side, so an i18n component is **Folded-tier eligible rather than the Simulated tier** — internationalization makes a component cheaper to render, not more expensive — and an explicit `timeZone` from the record is what makes date formatting foldable at all. For a date-only value use `Date.UTC(y, m - 1, d)` with `timeZone: 'UTC'`; it never shifts the day and reads no build-machine state.

## Element references are `first()`-based, never `ref={}`

Le Truc has no `ref={}` binding, on raw or composed elements. An author declares `const el = first(selector, required?)`, resolved structurally against the template on the server and via the DOM on the client. The client emits the authored selector when it verifies structurally — unique over the template, with a `:not(<child-tag> *)` exclusion where a composed child could match — and falls back to a synthesized one only when it does not (LT-316). Selector-literal types infer precise, non-nullable element types through `HTMLElementTagNameMap` (e.g. `first('input, textarea', 'required')` → `HTMLInputElement | HTMLTextAreaElement`).

A COMPOSED child is addressed by the tag it renders plus the compose site's own discriminator — `first('form-spinbutton.lightness', 'the lightness axis')` — never by the PascalCase name in the template. The child's tag lives in another file's registry entry, so the match is made in the compiler's second, registry-aware pass rather than in the single-file front end (LT-127). This promotes one previously incidental fact to an invariant: **`class`/`id`/`data-*` on a compose site reach the served DOM**, spliced onto the child's rendered root, because they are now the only way to tell two same-source compose sites apart. A compose-site `data-*` is a host attribute, never forwarded as a server arg, and only a literal value is a discriminator candidate (LT-320). A `truc:pass` site needs no `first()` of its own: the compiler addresses it by the same tag-plus-discriminator selector and names the query after the tag (LT-338). Declare the reference only when the factory reads the element, or to give it a required-reason text. Sites that share a class and carry textually identical `truc:pass` objects share one query: they lower to a single `pass(all('child-tag.class'), …)` (LT-319). Sites whose objects differ need a distinct class each.

## Lazy destructuring does not apply (`.tsrx`)

Core TSRX's `&{` / `&[` lazy-pattern introducers (`LazyObjectBindingPattern`, `LazyArrayBindingPattern`) have no role in this profile. Le Truc's server composition requires eager snapshot evaluation to generate markup — a lazily-destructured binding has nothing to evaluate against at render time. The rejection is enforced, not just documented, and since the 0.2 pin it is the GRAMMAR's own: `@tsrx/core` 0.2 dropped lazy destructuring, so `&{ … }`/`&[ … ]` in binding position no longer parse and fail the build as a syntax error (surfaced as LTC008; the dedicated TSRX020 scan retired with the LT-210 bump — same tier-1 guarantee, one link earlier). The one surviving diagnostic is TSRX018 for an `&{expr}` sigil in template-child position, which still parses as an ordinary expression and must still be named to the author. See the adjacent `LE_TRUC_COMPILER.md`.

## Statements before output are legal (`.tsrx`)

`TemplateBlock : { StatementListItemList TemplateOutput }` is grammar-native and Le Truc uses it as-is: an `@if` / `@for` / `@switch` / `@try` body may contain statements before its single output node. This is already true in the compiler and needed no change — it is listed here because it is easy to assume otherwise coming from a host that forbids it. What a body's statements may be is host-owned: a reactive `@for` body's are the item's setup (ADR 0046 s5, above), a server-data loop's are `const`s, and an arm's are refused. The `.tsx` surface's branches are expressions and must return JSX; statements live in setup, or in a reactive `map` callback's block body.

## Imports: real exports explicit, FactoryContext vocabulary ambient

A compiled source imports the real `@zeix/le-truc` exports its setup code references — signal constructors (`createCell`, `deriveCell`, …), parsers (`asString`, `asNumber`, …), `defineMethod`, form utilities — with an ordinary `import { ... } from '@zeix/le-truc'` naming only what is used. These are true module exports, so an authored source is valid TypeScript by construction, on either surface. The effect machinery — `watch`, `on`, `pass`, `each`, every `bind*` — is never authored at all: template syntax lowers to it in generated code. A function-valued attribute becomes `watch()` plus a `bind*` helper, `on*` attributes become `on()`, `truc:pass={{ ... }}` becomes `pass()`, and a loop becomes `each()` (the `reconcile()` path over a declared list). The compiler errors when a real export is used without its import (LTC036) and when a FactoryContext name appears inside an authored import (LTC037), both with fix-its (ADR [0024](../../adr/0024-adopt-tsrx-as-isomorphic-component-format.md), sub-design 16).

An ordinary module import is a known name in a client-only setup statement ([ADR 0046](../../adr/0046-reactive-list-items-as-mount-scopes.md) s5), so logic shared between surfaces can live in one helper module: `setupReorder(host, items)` compiles on both surfaces. The server never runs the statement, and the import is placed into the client module only (ADR 0024 sub-design 14). A component import is not a helper, and calling one from setup is still LTC005.

**Compile-time markers are imports, never ambients** ([ADR 0034](../../adr/0034-distribution-tsx-only-compiler-package-and-template-emission.md) s1, LT-442). A call the compiler consumes and never runs — the `css` tag and `harvest()` — is imported from `@zeix/le-truc-compiler/macros`: a `.tsx` source is plain TypeScript, so the import is the only sign that a compiler reads the call. The compiler recognizes a marker by module specifier and imported name, never by bare name: `import { css as style }` makes `style` the tag, and a `css` that is not the import — no import at all, another module's `css`, or a component-scope declaration that shadows it — is not the marker. Both front ends read the same bindings (`parseMarkerImports`/`markerOf` in `imports.ts`). The marker import never reaches either generated module: a declaration of markers only is dropped whole, and a mixed one loses only its marker specifiers. A `css` tag that is not the marker — a missing import (also `tsc`'s "Cannot find name 'css'"), another module's, or a shadowed one — fails the compile (LTC078, LT-444): the compiler decides the drop, so it reports it. `harvest()` is read only as the seed of a component-setup `createList` or a scalar signal declaration (`createCell`/`createState`/`createStore` — see *Per-field harvest* and *Scalar harvest* above); it resolves through a list item's own scopes too, so an item-setup declaration named `harvest` shadows it there, and a marker call in any other position fails the compile (LTC005). Each form is matched to its constructor — the map on a `createList` seed, the scalar parser on a scalar seed — and a mismatched pairing is refused. That last rule is generic: after extraction the compiler walks the component function, and every reference to a marker binding that no consumer read — a `harvest()` in a handler or a template expression, a `css` tag outside the root's `<style>` — is LTC005, since the stripped import would leave it unbound. The exports of `server/compiler/macros.ts` are typed stubs that throw when a source reaches them uncompiled. Until the package exists (LT-254), every tsconfig that checks authored `.tsx` resolves the specifier to that file through a `paths` entry beside `@zeix/le-truc`; `check:corpus` and the pipeline never resolve it, because the generated modules do not import it.

The FactoryContext vocabulary an author actually writes — `expose`, `first`, `all`, `host`, `internals`, `requestContext`, `provideContexts` — stays ambient, with the `.tsx` parameter convention (LT-209) layered on top: a source that annotates the second, typed context parameter destructures these names from it, shadowing the ambients at function scope (the annotation types are `import type`-only and never reach generated output). The ambients remain the fallback for sources that omit the parameter — and the whole vocabulary on `.tsrx`, whose grammar has no parameter form. Each surface declares the ambients in its own profile file: `server/compiler/frontend/tsrx/globals.d.ts` for the raw `.tsrx` view, `server/compiler/frontend/tsx/host-profile.d.ts` for authored `.tsx` (which adds the strict `IntrinsicElements` table and the typed `boundary` ambient).

The editor story differs by surface. Authored `.tsx` type-checks through plain tsserver against `host-profile.d.ts` — no projection, no plugin; this is what retired the planned span-table editor plugin, whose premise was `.tsrx`-everywhere authoring. The `.tsrx` grammar is not TS syntax — `@{ }` blocks and `@for`/`@if` directives parse only through the pinned core — so its editor surface is a projection over the generated client, and the ambient globals are the fallback that keeps the identifier set honest. A TSRX language service cannot resolve even explicit imports, which is why the ambients stay ambient rather than imported; the explicit-import policy earns its keep in the one benefit that holds regardless of editors: authored sources that are honest TypeScript the moment a working language service arrives.

## Open questions for upstream

- The draft TSRX spec (dated June 2026) under-specifies several host-owned areas in practice — attribute semantics, style scoping, class generation — because few host profiles existed to specify them against. Ripple and Le Truc diverge sharply enough on some of these (style scoping in particular) that the spec text alone doesn't settle a new host's design.
- Whether "host-owned" extends to selector-scoping *enforcement* (should a host be allowed to lint or reject non-conforming CSS, or only to declare its own default) is not addressed at all. For this host [ADR 0033](../../adr/0033-scope-component-styles-by-custom-element-name.md) s6 answers it (see the styles section above): enforcement is host-owned, and this host refuses — an authored form with no meaning under its shadow-root contract is a compile error (channel compiler, tier 1 Prevented).

As of 2026-09-21 the reactivity questions lead this list. Among the named host profiles, Solid (signals from the start) and Octane (signals as of its new API) both render at least once on the client and both compile templates to direct DOM operations — yet they still mean different things by "signals," and this host uses the same surface for a third thing. In Octane a signal read in the template subscribes the component's **render scope** and re-runs it: signals are state containers feeding a compiled re-render pipeline, with direct bindings (`value={draft$}`) as the per-binding escape hatch. In Solid the component runs once and signals ARE the DOM-update engine: per-binding effects over a live runtime graph, with reactive control flow creating and disposing DOM. In Le Truc the client never renders at all: the signal graph executes at build time to produce the initial markup (tiered server evaluation, [ADR 0029](../../adr/0029-tiered-server-evaluation.md)), and client-side a signal exists to keep already-rendered DOM truthful — it creates DOM only for declared lists and for the arms of a condition over a signal, cloned from server-baked templates (ADR 0037), and no state crosses the server→client boundary ([ADR 0003](../../adr/0003-attributes-drive-state-at-connect-time-only.md)). The same authored shapes — a `{expr}` child, an attribute thunk, an `@if` arm — carry all three contracts, and nothing in the grammar tells a reader, a tool, or an agent moving a component between hosts which one applies.

What we'd ask the spec to settle is not which model wins but that every host profile must **declare** its answers, the way it already declares attribute semantics and style scoping:

1. **Evaluation model of a template expression** — when a `{expr}` child or an attribute thunk evaluates: once at build or request time (folded into markup), once at mount, or per update.
2. **The subscription unit** — what a signal change re-executes: a render scope, an individual binding, or nothing (build-only). The reactive-vs-static distinction in attribute values (this profile's arrow-thunk rule) is host-owned today only by omission; the spec should name the distinction and hand it to profiles explicitly.
3. **Branch DOM lifetime** — whether a conditional arm's DOM is re-created when its condition flips (Octane's re-render, Solid's reactive control flow, and since ADR 0037 this host, cloning server-baked arm templates) or rendered once and toggled via `hidden`. This decides whether an `@if` condition over a signal is legal, a compile error, or a silent trap — today it is all three depending on host.
4. **The server→client state boundary** — whether component state crosses it at all. Octane ships versioned seed manifests and adopts streamed results; this host ships no state ever ([ADR 0003](../../adr/0003-attributes-drive-state-at-connect-time-only.md)), and ADR 0034's template emission can delegate rendering to a non-JS backend entirely — the one case where a profile's assumption of a client-side signal graph existing on the server is guaranteed false.

*(Direction note, 2026-09-21: [ADR 0037](../../adr/0037-reactive-conditions-via-template-cloned-arms.md), ✅ Accepted, answers items 2 and 3 for this host's conditional constructs — named compile-time arm keys, created from an inert template on true and disposed on false — without changing the demand that every profile declare.)*
